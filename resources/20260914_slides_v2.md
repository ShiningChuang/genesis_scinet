# 分点总结一下KK的所有问题，以及改法

## 1. 为什么只谈 transfer window，compute 呢？

**KK 的问题**：workflow 里既有计算又有传输，scheduler 生成 transfer window 之前必须先考虑 compute 的调度和完成时间。

**判定**：接口层面已被接受；设计上有真缺口。

**改法**：

- 后向推导**减掉排队时间**：`latest_finish(T) = latest_start(下游) − queue_wait(下游)`，`queue_wait` 从历史 `startedAt − readyAt` 学
- S1 **显式分配 slack**：先算关键路径总 slack，留一份给 compute，剩下的才进 transfer window，不再让网络独吞
- 边界说清：**规划 compute 的时间，不分配 compute 的资源**

## 2. 遥测分流后，谁关联整个 workflow 的运行状态？

**KK 的问题**：计算信息走 WMS、网络信息进 network agent，理由是什么？每个组件只知道自己那部分，谁知道整体发生了什么？实验设备呢？

**判定**：一半表达，一半真缺。

**改法**：

- **讲清分流理由**：按真相源分——谁拥有这份事实、谁能据此行动
- **新增关联实体**（Workflow Execution State）：运行时 DAG，节点三类（设备 / 计算 / 传输），每个节点挂"计划、实际、偏差、原因"，是全系统唯一的跨组件关联点
- **network agent 上报结论而非原始指标**：`at_risk` / `repaired` 加 `cause`（`end_host | network | foreign_traffic | unknown`），传输结束后补一条归因结论
- **把实验设备接进来**：至少"数据产出时刻 + 实际数据量"两个事件，来源是 WMS 或独立的 facility adapter（需向 Rafael 核对 schema）



## 3. 链路故障后，怎么知道哪些任务受影响？

**KK 的问题**：带宽减半后，哪些传输受影响、属于哪个 workflow、耗时变化怎么传给 scheduler、没受影响的怎么避免误伤？光有静态 DAG 不够。

**判定**：关联的键都有，但过程没设计。

**改法**：

- **写出关联链**：故障 → (src, dst) / circuit → commitments → `commitmentRef` → transfer → DAG 节点 → 下游 tasks
- **故障触发主动扫描**：`observed` 下降时，重算该路径上所有 `own` 记录，一次性找出保不住的承诺（含尚未开始的），不等逐条跑慢
- **定义** `at_risk` **格式**：`commitmentRef`、新的 `predicted_finish{p50, p95}`、`cause`、受影响时段
- **DAG 上传播影响**：由关联实体把偏差推到下游，判断哪些 deadline 会破
- **直说信息边界**：SENSE 不给 link 级拓扑，按 (src, dst) 建账会漏报或误报；用 `ProbeResult.path` 和 `WfPlatform.routes` 缓解



## 4. 遥测应该先汇总到 WMS 或专门的 telemetry entity

**KK 的问题**：建议遥测先到一个共同实体，放进 workflow 上下文，再分发给各 agent。

**判定**：需求和第 2 点是同一个真缺口；放 WMS 不合适。

**改法**：

- **不放 WMS**：它是别人的现成系统、没有 commitment 这半的键、会破"只有 network agent 碰网络侧"的边界
- **指出集中采集 ≠ 关联**：关联靠键链，谁持有键谁才能关联
- **采纳"独立关联实体"这个方向**，但它收**事件和结论**，不收原始指标；原始网络指标留在 network agent，需要时按需去拉



## 5. advisory 角色与直接采集遥测矛盾

**KK 的问题**：既然 agent 只是给建议，凭什么直接采集遥测？

**判定**：表达问题。

**改法**：讲清两种角色——**对计算是顾问**（`taskSchedule` 可以不听），**对网络是所有者**（自己预约、自己下发、自己监测）。

**真正要新增到设计里的，归结为四样**：排队估计与 slack 分配、Workflow Execution State 关联实体、`at_risk` 格式与故障扫描、设备节点接入。

# Workflow execution state

**是 DAG，但不只是 DAG。** 三个区别：每个节点挂**三份时间**（计划 / 实际 / 预测）；传输和设备也是**一等节点**，不只是 task；它是事件日志上的**物化视图**，有版本。

## 格式

```jsonc
{
  "workflowId": "1000genome-crosslab-001",
  "campaignRef": "wfcampaign:summer26-run17#sub-003",
  "planVersion": 3,                          // 每次重排 +1
  "asOf": "2026-08-20T09:36:00Z",            // 这份视图对应的时刻
  "deadline": "2026-08-20T09:40:00Z",
  "priority": 3,

  "nodes": [
    { "id": "inst:primary-detector#b17",     "kind": "instrument",
      "plan":     { "producedAt": "…08:30Z" },
      "actual":   { "producedAt": "…08:31Z", "sizeInBytes": 5.0e11 },
      "status":   "done" },

    { "id": "xfer:input.txt:aps-beamline-8id>anl-n01", "kind": "transfer",
      "commitmentRef": "cmt-7f3a91",         // ← 与 network agent 关联的键
      "window":   { "earliestStart": "…08:31Z", "latestFinish": "…09:00Z" },
      "plan":     { "start": "…08:31Z", "finish": "…09:00Z" },
      "actual":   { "startedAt": "…08:31:12Z", "finishedAt": null },
      "forecast": { "finish": { "p50": "…09:05Z", "p95": "…09:12Z" } },
      "slack":    { "allocated": 600, "remaining": -720 },
      "status":   "running",
      "cause":    "network" },               // 来自 network agent 的归因

    { "id": "task:ID0000001", "kind": "compute",
      "placement": "anl-n01",
      "plan":     { "start": "…09:00Z", "finish": "…09:00:10Z" },
      "actual":   { "readyAt": null, "startedAt": null, "finishedAt": null },
      "forecast": { "finish": { "p50": "…09:05:10Z", "p95": "…09:12:10Z" } },
      "slack":    { "allocated": 300, "remaining": -420 },
      "status":   "pending",
      "cause":    "upstream" }                // 被上游拖累，本身没问题
  ],

  "edges": [
    { "from": "inst:primary-detector#b17", "to": "xfer:input.txt:…", "fileId": "input.txt" },
    { "from": "xfer:input.txt:…",         "to": "task:ID0000001",   "fileId": "input.txt" }
  ]

```



## 几个设计选择

**三类节点，传输显式成节点。** 同一站点内的文件流动不产生 transfer 节点，边直连；跨站点才插一个 transfer 节点。这样 DAG 本身就表达了"哪些依赖要过网"，也就是 S0 拆解的结果。

**三份时间各有来源。**


|            | 来自                | 用途               |
| ---------- | ----------------- | ---------------- |
| `plan`     | 执行计划              | 对照基准             |
| `actual`   | Telemetry Service | 已发生的事实，一旦填上就不再预测 |
| `forecast` | 传播计算              | 未发生节点的当前最佳估计     |


**传播和 S1 是同一个算法。** 规划时 S1 用估计值做前向推导；运行时对 Execution State 做同样的前向推导，只是**已有** `actual` **的节点用实际值，其余用** `forecast`。一个算法两处用，不用另写。

`slack.remaining` **为负就是受影响。** 受影响集合 = `remaining < 0` 的节点，加上从它们沿边可达、且 `forecast.p95` 越过自身窗口的节点。其余一律不动——这就是"避免误伤"的判据。

`cause` **区分自身问题与连带影响。** `network` / `end_host` / `foreign_traffic` 是 network agent 给的归因；`upstream` 是传播时自动标的。scheduler 重排时据此判断：该动的是出问题的那条，还是只需把下游整体平移。

## 它不是什么

- **不存原始遥测**：原始数据在 Telemetry Service，这里只有从事件聚合出的 `actual`
- **不存网络资源耦合**：两个 workflow 共用一条路径不是 DAG 边，那在 network agent 的账本里；故障的第一轮扫描在那边做，这里只接收结果
- **每个 workflow 一张图**：跨 workflow 的取舍由 scheduler 同时看多张图完成，不把它们连成一张大图

**版本化**：每次重排 `planVersion + 1`，旧版本保留。事后解释"为什么当时这样排"和长回路校准都需要回放当时那一版。

# 链路故障后的动作

> 链路故障后，network agent先看能不能直接修，如果可以就直接向sense修改intent，然后给schedule agent发出repaired；如果不可以，就给scheduling agent发出at risk让它重排？它重排了之后，怎么告诉回network agent呢，重新quote-hold-commit吗



## 前半段的三处补充

**1. 先扫描，再逐条判断。** 故障后第一步不是"修这一条"，而是找出这条路径上**所有**受影响的 commitment——包括正在跑的和还没开始的。然后每条按自己的 slack 单独判断，所以一次故障通常会同时产出几条 `repaired` 和几条 `at_risk`，应该**成批**发上去，让 scheduler 一次性看到全貌再重排，而不是一条条被动反应。

**2. 自修不一定碰 SENSE。** 吃自己的 slack 往后挪只是账本操作；提速和换电路才要 `modify` 或切电路。另外之前那张表里"加并行流 / 调传输参数"其实有问题——那是数据面的传输参数，由 WMS 那边的搬运工具控制，network agent 改不了，只能通过更新执行计划让 WMS 去做。

**3.** `repaired` **也要带新的** `predicted_finish`**。** 虽然还在窗口内、下游不受影响，但 slack 被吃掉了，scheduler 需要知道这条现在没有余量了。

## network agent 看不到的东西

network agent 判断"能不能自修"，用的只是 scheduler 给它的那条窗口 `[earliest_start, latest_finish]`——DAG 的信息已经压缩在窗口里，但**它看不到窗口背后的依赖**。所以有三件事它做不了：

1. **下游的连带影响**。上游传输 T1 晚了，下游 task 晚开始，下游传输 T2 也得挪——**但 T2 走的是一条健康的路，network agent 根本不会把它标出来**。这正是 KK 问"谁知道整体"的要害
2. **哪些 at_risk 属于同一条链**。一批事件里，两条可能是同一个 workflow 的上下游，应该一起重排，而不是当作两件独立的事
3. `repaired` **的隐患**。自修吃掉了 slack，窗口内没问题，但如果那份 slack 本该留给下游 compute 的排队（KK 第 1 点），下游照样会破



## 重排之后怎么告诉 network agent：对，走同一套协议，不加新动词

scheduler 的每种应对都能映射到已有动词：


| scheduler 的决定 | 协议动作                                                  |
| ------------- | ----------------------------------------------------- |
| 接受更晚完成        | 对原 commitment `quote` 新窗口 → `modify`                  |
| 抢占低优先级的       | 为自己 `hold` 新放置 → 对被抢者 `modify` / `release` → `commit` |
| 重排下游传输        | 下游那些 transfer 以平移后的窗口重新 `quote` → `modify`            |
| 换副本源          | 新 transfer 走 `quote → hold → commit`，成功后 `release` 旧的 |
| 放弃            | `release`，通知人并给 counter-offer                         |


**一条关键纪律：先占新，再放旧**（make-before-break）。

绝不能先 `release` 旧的再去抢新的——释放那一刻容量可能被别人拿走，最后两头落空。正确顺序永远是：新方案 `hold` 成功 → 放掉旧的 → `commit`。这也是 `hold` 这个动词在故障场景下的第二个用途，不只是 admission 时用。

## 还有两件事容易漏

**执行计划要同步更新给 WMS。** 重排改变了传输时间窗、可能换了端点、下游 task 的建议启动时间也变了——这些都要作为新的执行计划推回 WMS，否则 WMS 还按旧计划跑。

`at_risk` **需要一个响应期限。** 如果 scheduler 迟迟不决定，network agent 不能无限等。要约定默认行为，比如超时后按 best-effort 继续传、并标记该承诺已违约。这是之前列在"错误路径"里还没设计的一项。

## 完整流程

```
① network agent   扫描受影响路径上的所有 commitment
                  逐条按窗口判断 → 能修的修 → 成批发 repaired / at_risk
                  （每条带新的 predicted_finish{p50,p95} 和 cause）

② Execution State 用 commitmentRef 挂到 DAG 节点上
                  叠加实际运行状态（哪些 task 已完成 / 在跑 / 未开始）
                  把新的 p95 沿依赖往下推：下游 task 开始时间 → 下游 transfer 窗口 → 各 deadline
                  输出：受影响集合 = 直接受影响的 + 传递受影响的；以及哪些 deadline 会破

③ scheduler       在受影响集合上重排（接受延后 / 抢占 / 重排下游 / 换副本 / 放弃）
                  跨 workflow 用 utility 与 priority 取舍

④ 协议            先占新、再放旧：quote → hold → release 旧的 → commit
                  下游那些健康路径上的 transfer 也在这一步 modify

⑤ WMS             推送更新后的执行计划
```

# compute计算超时的动作

和网络故障对称，但有两处本质不同：**检测靠"该来的事件没来"**，**应对主要是挪网络预约，而不是修计算**（计算不归我们管）。

## 检测：超时是"事件缺席"，只能靠 Execution State 自己计时

Telemetry Service 只能推送发生了的事，"本该完成却没完成"不会有任何消息。所以 Execution State 要给每个节点挂一个**看门狗**，到点没收到 `actual` 就判超时。分两种：


| 类型       | 判据                                                              | `cause`   |
| -------- | --------------------------------------------------------------- | --------- |
| **排队超时** | 有 `readyAt`，但 `now > readyAt + queue_wait.p95` 仍无 `startedAt`   | `queue`   |
| **运行超时** | 有 `startedAt`，但 `now > startedAt + runtime.p95` 仍无 `finishedAt` | `compute` |


`queue_wait` 和 `runtime` 的分布都从历史 `report` 学（Tier 2.5 的估计模型）。

**检测的一个盲点**：没有进度信号就分不清"慢但活着"和"已经挂了"。两个 schema 字段能补上，都不在 20260910 里：`tasks[].status`（之前列为待定，这个场景说明它其实需要）和 `tasks[].progress` / 心跳（可选）。

## 动作

```
① Execution State  判定超时，节点标 status=overrun、cause=compute|queue
                   更新 forecast.finish：
                     有进度 → 按进度外推
                     无进度 → v1 规则：now + (runtime.p95 − runtime.p50)，每个周期重评

② Execution State  前向传播（同 S1 算法，已完成节点用 actual）
                   → 下游 transfer 的 earliest_start 后移
                   → 下游 compute、deadline 依次后移
                   输出受影响集合

③ Scheduling agent 对受影响的下游 transfer 逐条处理（见下表）

④ 协议             先占新、再放旧：quote 新窗口 → hold → modify / release 旧的 → commit

⑤ WMS              推送更新后的执行计划（新的 taskSchedule 与 transferWindows）
                   附带建议（如换节点重跑）——只是建议，WMS 决定

⑥ Telemetry        写入超时事件；runtime / queue_wait 的尾部分布进长回路

```



## 第 ③ 步：下游 transfer 怎么处理

这是和网络故障最不同的地方：**计算晚了，网络预约如果不动，电路按时开着、数据却没到——容量白占。**


| 情况                                     | 动作                                                                                 |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| 平移后仍在 `latest_finish` 内                | `modify` 往后挪，**并把前面空出来的时段放回账本**给别的 workflow——超时反而释放了容量                             |
| 平移后超出 `latest_finish`，但换更快的 offer 能赶回来 | 要一个更高速率的 offer——**用网络容量把计算耽误的时间买回来**                                               |
| 更快的 offer 也不够                          | scheduler 在 utility / priority 下取舍：接受延后、抢占低优先级 workflow 的容量换高速、或放弃并给 counter-offer |


第二行是这个架构里一个很好的演示点：计算和网络在同一张时间线上，**一侧的延误可以由另一侧的余量吸收**——这恰好回应了 KK 第 1 点"scheduler 必须同时考虑 compute 和 transfer"。

## 我们不做的

- **不杀、不重启、不迁移计算任务**。那是 WMS 和集群调度器的权力，我们只在执行计划里给建议
- **不因一次超时就改窗口来回抖**。任务最终完成、`actual` 到达后会再传播一次；若之前预测过于悲观，把窗口提前要过 `refine` 的容差阈值，否则不动



## 与网络故障的对比


|         | 网络故障                                   | 计算超时                 |
| ------- | -------------------------------------- | -------------------- |
| 谁先发现    | network agent（指标 / 探测）                 | Execution State（看门狗） |
| 检测依据    | 有信号：容量下降、吞吐偏低                          | **无信号**：事件缺席         |
| 第一步     | network agent 扫描 own 记录，能修就修           | 直接传播，没有"自修"阶段        |
| 主要应对    | 修路径、换电路、重排                             | **挪下游网络预约**，必要时提速补时间 |
| `cause` | `network / end_host / foreign_traffic` | `compute / queue`    |

# 和Pegasus的差别

**不是子集，但重叠是真的，而且重叠的部分我们确实该让出去。** 分开说。

## 属实的部分

那篇是 Pegasus 2015 年的 FGCS 综述，Sourabha 读到的内容准确：

- **Mapper** 把抽象 workflow 映射成可执行 workflow：选站点、选副本、**插入数据传输节点**、清理、任务聚簇
- **DAGMan** 按依赖执行、失败重试、rescue DAG
- **监控**：`pegasus-monitord` 把任务状态、runtime、传输统计写进数据库，有 `pegasus-statistics` / `pegasus-analyzer`

这意味着我们设计里有两块**确实和 Pegasus 重复**：

1. **S0 拆解（task DAG → transfer 集合）**：Mapper 本来就会插入跨站点传输节点，这正是 S0 做的事
2. **副本选择**：Pegasus 有 replica selector

## 不准确的部分

**"HTCondor negotiator 决定最佳 compute / network 资源"——据我所知说过头了。** negotiator 做的是 ClassAd matchmaking：把作业匹配到计算槽位。网络不是它的一等资源——它不预约带宽，也不在时间轴上规划容量。HTCondor 和 Pegasus 对传输的控制主要是**并发数上限**这类静态节流。建议 Sourabha 继续看的时候专门核对这一点，这是整个判断的关键。

另外，你们自己在 0818 那份调研里已经指认过：**Pegasus 的五种 site selection 算法全部是 network-blind 的。**

## Pegasus / HTCondor 没有的——这才是我们的东西


| 能力                         | Pegasus / HTCondor                                     |
| -------------------------- | ------------------------------------------------------ |
| 向 SENSE 预约带宽（circuit、时间窗）  | 无                                                      |
| 时间轴上的容量账本、错峰               | 无                                                      |
| 为传输推导时间窗、分配 slack          | 无（有 runtime 估计，但不产出网络时间窗）                              |
| **跨 workflow 仲裁网络容量**      | 无（Pegasus 按单个 workflow 规划；HTCondor 的 fair-share 是计算侧的） |
| reservable → achievable 校准 | 无                                                      |
| 网络故障的快回路（L3 重定向、电路池）       | 无（只有任务级重试）                                             |
| counter-offer 协商           | 无                                                      |


**所以准确的说法是：Pegasus 管"做什么、在哪做、按什么顺序做"，我们管"网络什么时候、以多大带宽、在多个 workflow 之间怎么分"。** 这是互补，不是包含。

## 但设计要据此改三处

**1. S0 和副本选择让给 Pegasus。** Scheduling agent 直接读 Mapper 产出的**可执行 workflow**（传输节点已经插好了），不再自己拆。它真正独有的是**时间窗、slack、跨 workflow 的网络仲裁**，不是 DAG 映射。

**2. Telemetry Service 的计算侧直接接** `pegasus-monitord`**。** 我们设计的 `report` 里的 task 时间，Pegasus 已经在采了——接过来，不重新造。

**3. "agent 是 WMS 的一部分还是独立实体"是部署问题，不是贡献问题。** 完全可以做成 Pegasus 的扩展（比如通过 site selector 的外部 callout 接入）。**这反而是更好的落地路径**——接入门槛最低，而且 Rafael 本身出自 Pegasus 团队。贡献在于网络侧那几项能力，不在于它是否单独部署。

## 需要核实后再下结论的

- **那篇是 2015 年的**。Pegasus 5.x 这几年有没有加入网络感知能力，要查当前文档，不能拿十年前的论文断言"没有"
- **Panorama 项目**：印象中是 Pegasus 团队与 ESnet 相关的 workflow 性能监控与异常检测工作，**恰好贴近 KK 关心的遥测关联问题**——我不确定具体做到了什么程度，值得 Sourabha 顺着查

# 我们这个项目只是在设计一个更好的scheduler吗

> 我们这个项目只是在设计一个更好的scheduler吗，相对于目前的WMS，比如它们没考虑workflow重排。



**不是，也不该是。** 如果项目被理解成"比 Pegasus 更好的 scheduler"，基本是输的：Pegasus 成熟了十几年，而且"WMS 不会重排"这个论据本身就站不住——DAGMan 有重试和 rescue DAG，HTCondor 有跨用户的优先级和 fair-share，Pegasus 也支持分层 workflow 和延迟规划。拿这点做卖点，Rafael 一句话就能驳回。

## 项目真正在补的缝

```
WMS（Pegasus）          把网络当成一根静态管道：尽力而为 + 并发数节流
                                ↕   ← 没人负责这一层
SENSE                   把每条流当成孤立的电路：不知道它属于哪个 workflow、晚了会怎样

```

**workflow 的 deadline 和依赖，没有人翻译成网络预约；网络的实际状态，也没有人翻译回 workflow 的影响。** 我们的两个 agent 就坐在这条缝里。这也正是项目名 *Science-Aware Network Operations* 的字面意思——主体是网络，不是 workflow。

## 和"更好的 scheduler"有三个结构性区别

**1. 调度的资源不同。** WMS 调度的是"作业 → 计算槽位"。我们调度的是**带宽 × 时间**：要提前预约、会被别人占、会降级、会失效、而且名义值和实际值不一样（reservable ≠ achievable）。这是一类 WMS 从未建模过的资源。

**2. 网络是多个 WMS 共享的。** 这是最硬的一条。一个 Pegasus 实例只看得见**自己**的 workflow；而 ESnet 上同时跑着不同机构、不同 WMS 提交的流量。**跨 workflow 的网络仲裁，任何单个 WMS 从结构上就做不了**——它看不到别人。这也顺带回答了 Sourabha 的问题：agent 为什么不能只是 WMS 的一部分。

**3. 做承诺并兑现承诺。** 不只是排个顺序，而是给出"几点能到、有多大把握"，并在网络出问题时维持住它（快回路、电路池、achievability 校准）。proposal 的 gate 4（5 秒检测、30 秒恢复）就是在考这个，这完全不是 scheduler 的范畴。

## 但要诚实面对一个风险

**如果 Phase 1 的 demo 只做"单个 WMS、两个 workflow、把传输错开"，它看起来就会像一个更好的 scheduler。** 要让区别在 demo 里可见，至少得出现：

- 真实的**预约**，而不只是排序
- **多个 workflow 共享同一段网络**时的仲裁，最好来自不同提交方
- **网络故障后**承诺被维持住
- **预测完成时间 vs 实际完成时间**的对照（achievability 在起作用）

对照组也要有两个：Pegasus 默认行为（network-blind），和贪心预约（B1）。只打赢前者，确实只能说明"加了网络感知的 scheduler"；打赢后者，才说明网络侧这一层有价值。

**一句话定位**：*不是更好的 workflow scheduler，而是让网络成为 workflow 可以预约、协商和依赖的资源。* 这句话和 KK 在 0907 说的"SENSE 只提供 primitive，其余是我们在上面建的"是一致的。
