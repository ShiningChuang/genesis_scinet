## 一句话结论

学生已把收到的 VIT 在本地跑起来，确认它能复现现成拓扑、连通 vhost 并执行基本网络操作；但当前版本还不能直接接收标准 workflow，
多 workflow / 多用户并发、deadline / science SLA、调度以及远程服务化都需要额外的翻译层、scheduler 和 service layer。
会议因此没有放弃 VIT，而是把它降为 agentic system 中一个可替换的工具组件：接下来要以 **agent harness** 为主线，比较 Mininet/VIT、
Containernet、Containerlab/Clabernetes、QualNet 等路线，并优先复用 **SENSE** 已有的网络 intent/API，而不是自行实现底层路由。

## 三、学生实操结果：现有 VIT 能跑，但本质仍是手写拓扑的 Mininet 环境

KK 请 Sourabha 与 Linxuan 介绍两人这一周的实操观察。他说明自己从上周四起在外，主要通过聊天与学生沟通，尚未逐页细审 slides，
所以这是一版用于讨论的初步报告。

学生对收到的 VIT image 做到的事情包括：

- 启动一个**简单的 two-cluster topology**；
- 从各个 vhost 测试到其他 vhost 的连通性；
- 在节点之间做简单数据传输；
- 执行基本的网络参数修改命令。

从实现看，现有环境以 **Mininet** 为核心：一部分 endpoint 是经 **Containernet** 接入的 Docker container，另一部分只是 Mininet vhost。
节点和链路在给定脚本中**显式硬编码**。因此对一个新 workflow，当前没有“提交描述即可运行”的入口；使用者仍需修改或重写脚本，
明确它从哪个 vhost 到哪个 vhost、哪些任务在哪里执行，以及如何安排这些任务。

KK 的阶段性概括是：**VIT 高层上更像“一个 Mininet VM 加上外围组件”**。这个判断不是说外围组件没有价值，而是提醒团队：
目前真正复用到的主要仍是 Mininet 的网络仿真能力，VIT 额外贡献了什么还需单独识别。

## 四、围绕四个问题评估 VIT

学生没有只问“demo 能不能启动”，而是围绕 SciNet 场景列出四个问题：

1. **怎样表示并运行一个 workflow**：如何从 workflow 描述映射到 VIT 中的 vhost、任务与传输；
2. **怎样同时运行多个 workflow**：这些 workflow 是否能在相同 vhost / link 上并发执行；
3. **怎样表达每个 workflow 的网络属性**：能否为不同 workflow 指定不同 link properties，并把 deadline 等 science SLA 带入执行；
4. **怎样服务多个用户并扩展规模**：每位用户可能一次提交一组 workflow；平台是否能同时处理这些提交，并映射到接近真实 DOE 链路的规模。

后续所有讨论——WfFormat、TaskVine、custom scheduler、service layer、100 Gb/s 链路、VIT as a service——都在回答这四个问题，
而不是在重新评价“现有 sample topology 能否 ping 通”。

## 五、从 WfFormat 到可执行任务：需要一个翻译层

团队把 workflow 接入拆成两层：

1. 用标准格式描述 workflow；学生提出采用 **WfCommons 的 WfFormat**；
2. 增加一个 translation / execution layer，把标准描述变成 VIT vhost 上真正可执行的任务和脚本。

学生把 **TaskVine** 作为候选的 workflow management / execution system：它采用 manager–worker 结构，可把任务分发给 workers。
会上有人一度以为 TaskVine 属于 VIT 或 Rafael 的工作；学生澄清它是另一个项目，并与 WfCommons 工具链存在受支持的 backend 关系。
**具体是 WfCommons 哪个组件直接对接 TaskVine，转写没有说清，不能仅凭本次会议下结论。**

这条路线也给 agent 留出了明确角色：agent 读取标准 workflow 描述和已有示例，生成 VIT 所需的 topology / execution scripts。 学生认为功能上可行；但这只回答“能否生成”，没有回答生成、启动与运行是否足够快。会上有人追问“能否在有限时间内跑完”<a id="k-1"></a>【K-1】， 得到的回答是当前先验证功能，效率仍是另一个问题。

## 六、多 workflow、deadline 与 science SLA：缺的是 scheduler 和服务层

TaskVine 的 manager–worker 机制可以作为并行执行多个任务或 workflow 的起点，但学生指出它没有直接提供项目需要的：

- 基于 science SLA 的调度；
- 每次 workflow submission 各自不同的 deadline；
- 面向共享网络链路的 workflow-aware policy。

因此团队预期至少还要实现或扩展一个 **scheduler**。Mininet 的 `TCLink` 能设置带宽、延迟等 link properties，
但“这个 workflow 要在 10 分钟还是 10 小时内完成”不是一条静态链路属性，而属于 scheduler 的决策输入。
此外可能还需要一层较薄的 **service layer**，让 scheduler 通过稳定接口控制 Mininet/VIT，而不是每次直接改拓扑脚本。

对 multi-user 场景，会上采用的是“一名用户可提交多个 workflow”的模型。能否高效排这些 workflow、能否并发运行、
以及本地 Mininet 实例如何表示真实的 **100 Gb/s** 级链路，均未得到验证。一个可能性是按比例缩小链路参数，
但会议没有决定缩放方法，也没有证明缩放后仍能保留目标系统行为。

现阶段的实测体验也提示性能风险：VIT 必须在学生 laptop 本地启动以显示 GUI，运行速度被形容为 **“slow as molasses”**；
如何远程运行与服务化尚未解决。因此“功能路径已跑通”不能写成“已经具备可扩展执行能力”。

## 七、VIT 仍可能保留的独特价值：真实 DOE 映射与 instrument simulator

Mariam 提出 **VIT as a service** 的目标形态：agent 调用 VIT，在 digital twin 中测试候选方案，再根据仿真结果决定怎样配置 workflow。
学生的调查表明，这个可远程调用、可扩展的 service **当前并不存在**，需要项目自己增加。

与从零搭 Mininet 相比，VIT 可能真正有价值的部分是它已经做过的 DOE 场景映射，包括：

- 采集并写入模型的真实网络数据和带宽；
- 真实 DOE 站点 / self-driving lab 之间的连接关系；
- 对科学仪器控制接口的模拟。

因此关键问题变成：**这些数据和模型能否从 VIT 中独立导出，或由新平台复用？** 如果可以，团队可考虑换掉外围执行平台而保留资产； 如果不可以，就要衡量继续改 VIT 与重新建模的成本。<a id="k-2"></a>【K-2】

学生还从 VIT 论文和环境中确认了两类 instrument simulator：

- **EPICS simulator**；
- **Nion Swift simulator**。

这些 simulator 被封装成 Docker container，并通过 Containernet 接入同一个 Mininet topology。示例中，一个站点的 vhost 与另一 vhost 上暴露的 EPICS API 显式连接，前者发送 EPICS 命令，数据再返回用户侧 vhost。会上随后追问：这些 simulator 是真正模拟仪器行为， 还是只带 delay / CPU-consumption characterization 的轻量 container？**该问题没有在会上回答，需继续查代码或论文。<a id="k-3"></a>【K-3】**

## 八、运行环境澄清：不是 Windows 依赖，VM 也未必是必需品

John 迟到加入后问，自己是否记错了上次会议提到的 Windows 依赖。学生用实操结果纠正了这个印象：

- 两人在 Apple Mac laptop 上使用 **UTM**；
- UTM 模拟 x86 架构，能够启动对方提供的 VIT VM；
- 这条路径不需要 Windows，也没有在 Mac 宿主上自行编译 custom kernel。

Nagi 在 meeting chat 中补充，真正的环境约束来自 **Mininet 的 Linux kernel hooks**。如果宿主机原生运行兼容的 Ubuntu，
安装 Mininet 后可以直接运行 VIT 的 Python scripts，**不一定需要对方提供的 VM**。Windows/WSL2 若要原生支持 Open vSwitch 与所需网络过滤，
可能要自行编译 WSL2 kernel；更常规的做法是运行预构建 Mininet VM，或在 Multipass 的 Ubuntu VM 中运行。

所以本次澄清出的边界是：**VM 是封装兼容环境的一种交付方式，不是 VIT 逻辑本身的必需架构；Mininet 对 Linux kernel 能力的依赖才是根因。**

## 九、替代平台与规模化路线：先比较，不把 Mininet/VIT 当成唯一选择

Harvey 建议养成“先问还有哪些替代方案”的习惯。他现场读取了一份“Mininet alternatives”列表；录音能可靠辨认的包括 **OMNeT++**、<a id="k-4"></a>【K-4】 **GNS3**、**Containernet**、**Containerlab**，其余名称受 ASR 影响无法确认。选择标准不只是仿真精度，还包括：

- 是否已有和 generative / agentic AI 结合的使用方式；
- 是否便于被 agent 通过 API 调用；
- 是否能扩展到更多 endpoint 与更高抽象带宽；
- 是否支持容器化、Kubernetes 编排或地理分布；
- 是否已有真实网络设备/协议的高保真实现。

Harvey 特别读到 **QualNet**：meeting chat 中的介绍称它是 Keysight 的商业网络模拟器，采用 parallel discrete-event simulation， 可支持数千节点，并覆盖 physical、data-link、network 等多层模型。Harvey把它和自己早年接触的 battlefield simulation 及 LHC 初期的 discrete-event simulation 思路联系起来：仿真时间由事件推进，不必逐时刻复现系统。他认为这至少说明团队不应把选择范围锁死在 Mininet。<a id="k-5"></a>【K-5】

但会上**没有验证** chat 中那段 QualNet 说明的来源，也没有比较许可证、可编程接口、agent 集成、科学 workflow 支持或与 DOE 数据的兼容性；
因此 QualNet 只是候选调研项，不是选型结论。

John 随后给出更贴近现有资产的迁移建议：如果 VIT 的 topology / network data 已经是 Mininet 可消费的格式，
那么 **Containernet** 以及 **Containerlab + Clabernetes** 可能更容易承接这些数据，并更好地适配 container orchestration。 “能否无缝导入”仍是建议，会上没有展示转换结果。<a id="k-6"></a>【K-6】

Harvey 给出的选型原则是：每发现一个 promising system，先查是否已经有人把它与 agentic-AI architecture 结合；
如果已有部分成果，就从那里继续，而不是默认重新构建整套系统。

```text
workflow / science SLA
        ↓

        ↓               ↓
```

## 十三、容器化、远程访问与安全边界



### 1. 从 VM 转向 container / Kubernetes

John 建议尽量减少对整台 VM 的依赖<a id="k-12"></a>【K-12】：

- **Containernet** 可承载 Docker endpoint；
- **Clabernetes** 可把 Containerlab topology 接入 Kubernetes；
- Kubernetes 路线有利于 portability、programmability、priority queues 和 geographic distribution。

会上进一步提出一个可成为研究 demo 的压力场景：把不同 scientific researcher / workflow 作为产生不同需求的组件，
测试例如 **100 名用户同时提交 jobs** 时系统的极限。这仍是概念性 use case，没有形成具体负载、指标或实验计划。

### 2. 远程 GUI：Selkies

针对学生当前只能在 laptop 本地显示 VIT GUI 的问题，John 在 chat 中分享了 **Selkies** 及其 NRP 使用文档。<a id="k-13"></a>【K-13】

他将其描述为带音频的高性能 Linux remote desktop，NRP 已用于 AR/VR development environment；如果 digital twin 有音频或 GUI 组件， Selkies 可帮助远程呈现完整 workflow。会上还提到 South Korea 合作者 **Sangman Kim** 熟悉 Selkies，必要时可咨询定制。

Selkies 解决的是 remote desktop / GUI 可达性，**不等于解决 VIT 的调度、API 或仿真性能问题**。

### 3. Agent 的安全约束

随后有人追问 agentic framework 是否需要安全层，避免 agent 执行未授权操作。讨论提到现有服务使用会过期并自动刷新的 token，
由 agent 在需要时取得凭据；过去某种基于证书的方案维护较繁琐，转写未保留完整细节。

本次没有形成完整安全设计，但至少确认安全不是后补功能：agent 调用 VIT、SENSE 或真实基础设施时，必须有权限边界、短期凭据和可控的 key retrieval。<a id="k-14"></a>【K-14】

## 十四、SENSE 的角色：申请路径，不自己重写网络工程

团队此前讨论 agentic framework 时已经采用一个重要假设：**大量底层 network engineering 由 SENSE 完成**。
SciNet agent 不自行计算和下发所有底层 route，而是声明 endpoint、带宽等 intent，向 SENSE 请求 path，由 SENSE 执行 provisioning。
