## 一句话结论

本次会议的实质是**降低对 SENSE 的期待、把设计重心上移**：SENSE 只提供一个基本 primitive——按 source→destination、给定 bandwidth
与 deadline 预约一条 virtual circuit，成或不成给回答。因此"SENSE 还缺什么"不再是关键问题，关键是在这个 primitive 之上建两层：
**network agent**（把单个 workflow 拆成 tasks、处理依赖、组合多条 virtual circuit、判可行性并给 counter-offer）和
**scheduler agent**（跨多个 workflow 决定谁先跑、几个并发、按 deadline / priority 仲裁）。9/8 全体会议不讲这套 slides，
只由 KK 口头抛出这个方向听反应；下周把 slides 重构成"SENSE primitive → network agent → scheduler agent → workflow format 提供什么"。

## 一、Sourabha 汇报：SENSE 现在到底给了什么

Sourabha 的 slides 分两部分：SENSE API 当前为运行 workflow 提供了什么，以及还需要补什么。第一部分核对下来，SENSE 提供的能力是：

- 指定一对 endpoint（两个 site）作为数据传输的两端；
- 请求容量 / bandwidth capacity；
- 指定时间约束：start time 与 end time，其中 end time 即 deadline。

KK 当场追问 start time 是否可以是"I don't care"，认为**应当**可以只给 deadline 而不约束起始时间（会上未从文档确认，属推断）。

SENSE 收到这些参数后与真实网络交互，provision 出连接这两个节点的**整条 path**，并保证路径上每条 link 都留出所请求的容量。
即：SENSE 同时做两件事——判断能否在 deadline 前按该容量完成，以及为你把资源分配下去。KK 把它概括为
**network resource reservation**：能做就预留，不能做就明确告诉你不能做。

会上另确认一处术语：SENSE 自己把请求叫 **intent**，但这个 intent 最终被翻译成"为**单条** virtual circuit 做 provisioning"。
KK 因此强调这不是 SENSE 的缺陷——它本来就只打算管到单个 connection / virtual circuit 这一层。

## 二、缺口在 workflow 层，不在单次传输

Sourabha 用自己 slides 里的例子说明：单独一个 task（把一定量数据从 A 搬到 B）用现有 SENSE 完全可做，没有问题。问题出现在 workflow 层：

- 一个 workflow 是**一组带依赖关系的 task**，SENSE 无法表达和处理任务间依赖；
- 多个 workflow 同时存在时，**谁更重要、谁让位**，SENSE 不做仲裁。

结论是需要上面一层 controller / workflow orchestrator，同时管两件事：workflow 内部 task 依赖，以及跨 workflow 的优先级仲裁。 KK 明确说这正是"我们的 network agent"该做的事，而我们要提供的 API 是帮这个 agent 完成工作的；agent 则按 task 逐个调用 SENSE API 做分配——可以查询、得到"可以 / 不可以"的回答，再自行把整个 workflow 的 tasks 排出来。【K】

## 三、Rucio–SENSE / DMM 那篇论文能对照到什么

Sourabha 回顾了此前读过的 Rucio–SENSE 联动（Data Movement Manager, DMM）那篇论文：他们的 use case 是在同一条 link 上并发跑多个
**task**（不是多个 workflow），报告里跑到 10 个，并能给每个 flow 指定 priority，据此在 flow 之间分配容量。

KK 的判断是这**还不构成本项目要解决的问题**，理由是其中没有利用 statistical multiplexing：每个 flow 拿到的是一次性分配的固定容量
——例如某 flow 最多要 40，就从 100 里划走 40，剩下 60 给后续 flow，flow 之间并不复用。

> **Statistical multiplexing（统计复用）**：多个流量不固定独占带宽，而是根据实时需求动态共享同一网络资源。例如，两条 workflow 各自峰值需要 60 Gbps，但通常不会同时达到峰值，因此可以共享一条 100 Gbps 链路，而不必各预留 60 Gbps。
>
> 优点是提高链路利用率；风险是流量同时突增时会拥塞，所以需要调度、优先级或 admission control。

分工上会上澄清：Rucio 只负责"哪个文件从哪搬到哪"，**priority 是 DMM 处理的**。DMM 是否**动态**调整分配（还是只基于当前已知信息一次性决定）
双方都不确定，Sourabha 认为"有 dynamic 的部分但需要核对"，列为待办。

## 四、KK 的重构：不要再纠结 SENSE 缺什么，只要知道它给什么

KK 说得很直接：**"你们关心 SENSE 有什么、不能做什么，不如只关心 SENSE 做什么"**——它做的就是那个简单 primitive：
source 到 destination、带一定 bandwidth 的 virtual circuit provisioning。其余全部是我们在上面自己建的。
他甚至说自己原本关于"怎么设计一个 scheduler 来避免 contention"的问题**已经不再需要问了**，因为答案取决于我们自己建的那两层，
而不取决于 SENSE 的接口细节。

只要 workflow format 合适、能让我们**组合多条 virtual circuit** 去满足单个 workflow 以及跨多个 workflow 的需求，方向就是通的。

## 五、本次确定的两层 agent 分工（本次会议的核心产出）



### 5.1 输入：扩展后的 workflow format（上周已讨论）

- 存在多个并发 workflow；
- 每个 workflow 含一批 task；
- 每个 task 从网络角度有一个 source 和一个或多个 destination（也可能多源多目的）；
- 每个 task 声明这些端点之间要传多少数据、bandwidth 需求、deadline。

KK 确认这些正是上周设计的 workflow format 已经能表达的内容，因此 agent 可以知道每个 task 需要什么。

### 5.2 network agent（单个 workflow 内）

- 把 workflow **拆解成 tasks**（KK 明确纠正 Linxuan：admission 不是第一步，先做拆解）；
- 逐个判断这些 task 能否 provision、能否分到资源（调 SENSE primitive）；
- 理解并遵守 task 间依赖（A 完成才能 B、C 完成才能 D）；
- 在依赖约束下判断这个 workflow 整体能否被网络支撑，即 **workflow admission**；
- 给 **counter-offer**：依赖不严格时可否 reorder task；可否降低所需 bandwidth；能否利用 deadline 内的 slack
（某些 task 慢一点、某些早点完成，整体仍满足 deadline）；这条 deadline 到底有多灵活。



### 5.3 scheduler agent（跨多个 workflow，位于 network agent 之上）

- 处理 network agent 与更高层 user intent 之间的协商；
- 多个 workflow 争抢资源时决定谁先启动、能并发几个；
- 依据各 workflow 的 deadline 与资源需求做 priority 仲裁 / staggering。

> 我原本是这样想的：  
> 三个agent：workflow agent、network agent、scheduler agent。network agent是sense系统的代理，用于向sense系统发出请求和对接。但似乎kk的设计把我想的workflow agent和network agent混在一块了.
>
> 我的设计是：
>
> ```
> Workflow agent → Scheduler agent → Network agent → SENSE
> ```
>
> 而 KK 的设计更像：
>
> ```
> Workflow/API → Scheduling agent → Network agent → SENSE
> ```



### 5.4 失败恢复

Linxuan 提出还需处理故障后重调度（例如某节点进入 maintenance，或调度落在错误时间需要重排）。KK 认可这属于另一类 agent
的职责范围，可以是一个 **failure management agent**（会上未细化）。

## 八、WfPlatform 的去处：不进 workflow schema，但作为 agent 内部 cache 保留

Linxuan 提到上周结论是 WfPlatform 可能不需要（作为 workflow schema 的一部分），但主张它应以 **agent 内部 cache** 的形式活下来，理由：

- agent 可以把网络的 characterization 缓存下来；
- 一次调度决策必须建立在**一个一致的快照**上；
- achievability calibration 需要历史数据，历史要落在某个结构上。

KK 的回应是把这些都归为"以后可以考虑的 enhancement"，重申当下先做基本功能。**因此这条主张本次没有被否决，也没有被采纳，属悬置。**
