## 五、KK 的第一个纠正：网络环境 ≠ workflow 对网络的需求

这是本次会议**技术上最有价值的一处纠正**。

KK 指出，Mariam 的第二个 box 描述的是**网络环境**（拓扑、站点地址、真实网络长什么样），
而不是**workflow 对网络提出的需求**。这是两件截然不同的事：

- **网络环境**：拓扑、endpoint、地址——KK 假设这部分是**静态给定**的（"I'm assuming it is the former"），像 Mininet 那样先把拓扑指定好；
- **workflow 需求**：带宽、完成时间（deadline）、以及其他 SLA——这才应该是 workflow 推给网络的东西。

Mariam 接受了这个纠正："we could go with what you're saying"。

**Harvey 补充"动态性"到底指什么**：他回忆早年以非常抽象的方式仿真 LHC 网络时用的 **process-oriented approach**——
按某种基本方式共享带宽，跟踪每条流的 time-to-completion，需求变化时就更新完成时间。
他的结论是：**动态性体现在"调度流"，而不是"改拓扑"**。

> "that is scheduling the flows, right? Not changing the topology."

Harvey 由此给出具体建议：像 Mininet 一样指定拓扑、endpoint、地址；**利用 SENSE**；
以**跨多域的虚电路（virtual circuits）**为工作基础，需要多少带宽就申请多少分配，并在此之上做各种简单的 what-if。

## 六、虚电路 vs 分组交换：本项目工作在虚电路层

KK 追问："你是想把它当成分组交换网络，还是当成虚电路？"

- 结论倾向 **虚电路更容易**，也和 SENSE 的现状对齐。
- 两个 endpoint（如 ORNL 与 Caltech）之间，**中间路径是可变的**——可以根据 workflow 的需求改变中间的拓扑走法。
  KK 把这总结成："**你是在路由虚电路，而不是路由分组**（you're routing the virtual circuit rather than routing packets）"。
- 因此**这一层不碰 IP 路由**：不管 OSPF/BGP——那些是底层用来把虚电路建起来的机制。
- **对 ESnet/SENSE 的姿态**（Harvey）：不要指望他们为我们改变现有运行方式（"a big ask"），
  正确做法是**深入理解并对接 ESnet 和 SENSE 的接口**；Everson、Raimondas 和 John Graham 正是这方面的人。
- **SENSE 现状**：正从 pre-production 进入 **phase-1 production**，覆盖若干站点，聚焦 **CMS use case**，有一系列近期 milestone。
  Harvey 的判断：等它进入 phase-1 production 之后，**非平凡的决策才开始变得有意思**——那也正是 Genesis Mission 允许我们做点不一样的东西的地方。

## 七、workflow = 虚拟用户：多 workflow 竞争才是真问题

KK 提出的建模抽象，Harvey 立刻加码，这是本次会议第二个核心共识：

- 把系统看成**多个 workflow 同时跑在网络基础设施上**；
- 每个 workflow 有若干 endpoint，workflow 描述的是这些 endpoint 之间的交互：**数据量、时间、以及每条流的 SLA**；
- 因此 **一个 workflow ≈ 一个"虚拟用户"**——从网络视角看，它就是一组在收发流量的 endpoint 集合。

**Harvey 强调"用户的虚拟化"非常重要**：真实实体是一个**分布式的子社区（subcommunity）**，不是一个物理站点。
demo 里可以简化成两个点，但模型必须能表达分布式用户集合——
所以映射到网络上的是**一张复杂的图**，不是一条 ORNL→Caltech 的直线。

**为什么这才是真问题**（Harvey）：资源是有限的。他举例说 Genesis 的评审之所以喜欢这份提案，
部分是因为里面提到了 Summit 之类的大规模 GPU，但**现实是除非用户极多，否则不会用到大规模 GPU 集群，通常是每用户一到几块**。
真正的点在于：

- 有限资源（算力 + 网络）怎么**智能共享**；
- 优化目标怎么选：完成时间最小、平均完成时间、**尾部延迟最小化**；
- **组织之间的公平共享（fair sharing）**；
- **异常故障模式**的处理（网络侧或站点侧）。

> "These are all the real problems. If you can get there quickly, people will say, hey, they're really doing something."

Mariam 提到这些不同 workflow 的需求差异，已经写进了他们已投稿的那篇 paper 里。

## 八、KK 自陈的视角差异：传输层、边缘限速与 RDMA

KK 坦白他和其他人之间存在"一点小脱节"：

- 他长期思考的是 **TCP / MPTCP / MPQUIC 跑在分组交换网络之上**；而会上其他人想的是**站点之间的一条 pipe**。
- 但即便走虚电路，**端侧的工作一样跑不掉**：Everson 和 Raimondas 都很清楚，要让大流量跑稳，
  需要**协议栈调优 + 操作系统调优 + 大量参数**，才能得到想要的稳定大流。
- 端点**不需要知道网络内部拓扑**——这一点会上达成一致。
- **边缘限速**：当有大量竞争请求时，即使用虚电路，也仍然需要在**站点与网络之间**做速率调度。
  一种做法是**在边缘设备上控制发包速率**，而不是在端点上做——因为面对 400G、很快 800G 的流，端点本身压不住，必须借助边缘设备。
- **RDMA**：端点侧用 RDMA 才能在长距离上跑出平滑的大流。
- 这条线索也解释了 proposal 架构图里为什么要有加速器/SmartNIC（见第十节）。

## 十三、收敛出的两层 API 构想

会议尾声，KK 把讨论收敛成一个可操作的结构，Mariam 与 Harvey 都认可：

- **现状**：workflow 的设计与网络的配置是**分开的两件事**，workflow 的需求**并不会直接进入网络 API**——
  因为**这样的 API 现在根本不存在**（"unless we write an API right now, they don't"）。
- **第一层：workflow 侧 API**。表达 workload 是什么、需要什么 QoS；
  同时表达**客户类别**——有的客户有硬 deadline 并要能声明它；有的客户承认资源不是无限的、自己有弹性，
  **而正因为有弹性，他们反而可能拿到更好的服务**。
- **第二层：一组 agent**，把上面这套需求**翻译成对网络的具体需求**。
- **Harvey 的扩展**：按这些属性（有无 deadline、弹性大小、外部条件）划出**若干 class**，
  甚至可以让**每个 class 有自己的 agent**，agent 之间互相交互；
  再从**聚合视角**看每个 class 的处理情况，决定是否要**调整 class 之间的共享比例**。
- **不只是"能/不能"**：KK 强调和 AI 实体打交道不是"do this"，而是"我满足不了需求，现在怎么办"——
  它会综合各种因素给出理由和可能的方案，是一种**双向学习**；
  Mariam 补充了一个很具体的形态：**"我打算五小时后再调度这个任务，因为那时流量更少"**，把这类信息反馈给用户。
- **范围提醒**（Mariam）：除了网络，**计算和 self-driving labs 也在范围内**；
  并且她指出这**第二部分目前世界上还不存在**——没有这样的 agent。

## 十五、会后与 KK、Sourabha 的小范围对接

大会结束后，KK 与两名学生（Sourabha 和我）留下做了一次简短对接。KK 是主讲，内容全部是给学生的下一步布置。

**要的东西：workflow 侧那份"合理的 API"**

> "...a reasonable API about each workflow..."

这直接承接第十三节的两层 API 构想——KK 把第一层（workflow 侧）当成学生的活。

**怎么做：不要求逐字精读，要求快速拿到刻画**

> "I don't know if you guys have read those papers. I'm not asking you to sit and read it all manually,
> but you can use whatever methods you can to quickly get an understanding."

他明确允许用任何手段（含 AI 工具）加速读论文；目标不是读完，而是能说出**"一个 workflow 是怎么被刻画的"**。
他列出的刻画维度是这次对接里最具操作性的部分：

| 维度 | KK 的原话 |
|---|---|
| **端点** | in terms of the different endpoints |
| **负载特征** | the characteristics of the workload that is generated |
| **负载分布** | what's the distribution of the load that is generated |
| **SLA** | what are the SLAs that are needed **in terms of bandwidth, latency, completion times** |
| **论文自己用的刻画量** | what are the things that **they** characterize for each of these workflows |

最后一条值得单独注意：他不只要我们自己总结，还要我们看**论文作者本身用哪些量来刻画 workflow**——
这是在为 API 的字段设计找现成依据。

**交付形式与时间**

- 产出是**一组 slides**；
- KK 先据此建立理解，然后**下周二（2026-08-25）与所有人讨论**——与大会上"下周恢复到下午 1 点"的安排一致；
- **KK 本周剩余时间不在**，只能抽空看邮件，"看看你们发过来的东西"。

**同时进行的 VIT 判断**

> "these guys will also be looking for whether this ViT stuff that Anish has put together, if it is usable at all or not."
>
> "**I have a doubt that it is usable**, but please you guys tell me whether it makes any sense."

KK 在小范围里把大会上的措辞说得更直白：**他倾向于认为 VIT 不可用**，但结论仍然要学生给。
（"Anish" 应即大会转写中的 "Anise"/"Anees"，见文末核对表。）
