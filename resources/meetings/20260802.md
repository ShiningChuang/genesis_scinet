### 一、同学汇报的论文：分布式 Agent 框架

#### 用例 1：材料/化学发现（Materials Discovery）—— 重点

**原始工作流（纯计算，无真实实验）：**

1. 一个 AI 模型生成候选分子
2. 通过仿真把它们转换成另一种分子
3. 再一次仿真做筛选/验证（screening/validation）
4. 更多验证/实验步骤
5. **验证结果反馈给生成模型，持续再训练**（accumulated results → retrain generative model）

KK 追问："什么时候才变成真实实验？" —— 答案是**这个 use case 里完全没有真实实验设备的接入**，全是 compute-only。这是 KK 注意到的一个关键缺口。

**Agent 化后的架构：**

- 工作流的每一步被封装成一个 agent，**总共 6 个 agent**：generator、assembler、database、estimator、optimizer、validator
- **地理分散部署**：generator 在 **Aurora cluster**（因为需要大量 GPU），另外几个 agent 分布在 **Chameleon Cloud**（3 个）和另一个集群（2 个）
- 每个 agent 负责一个 system-intensive 的处理步骤

**KK 特别追问 generator agent 的性质：**

- KK 的判断：generator agent 背后**同时在调用多个 ML 模型**（跑在 Aurora 上），agent 可能和这些 ML 模型来回迭代（back and forth）来 refine 实验配置
- 最终输出应该是某种实验配置描述（"最笨的方式就是一个描述配置的 JSON 文件"），然后发给 assembler
- 同学不确定是 LLM 还是一组其他 ML 模型 —— **KK 让他去查证**
- KK 的动机："我真正关心的是这个 generator 怎么把东西**从 Aurora 通过网络运到 Chameleon Cloud 上的 assembler**"

#### Agent 之间的四种通信方式（重要，直接关系到你们的 API 设计）


| 方式                             | 场景                | 机制                                             |
| ------------------------------ | ----------------- | ---------------------------------------------- |
| **Thread exchange**            | 同一进程内不同线程，小规模测试   | 内存内数据传递（类似 HPC 节点内的共享内存）                       |
| **Hybrid exchange (direct)**   | 跨节点、两个 agent 都活跃  | 消息传递，推测是 TCP/port 通信                           |
| **Hybrid exchange (indirect)** | 跨节点、对方 agent 可能休眠 | **Redis 中心化 object store**，一方 post，另一方唤醒后 pull |
| **Cloud exchange**             | 跨站点/跨集群           | **HTTPS**，带认证要求（联邦认证 / 单点登录，KK 类比 UCR 的 SSO）   |


- 另外还有 **pass-by-reference 模式**：用于大数据传输，减少实际搬运的数据量
- 论文的说法有点混乱：hybrid 和 cloud exchange 用于**小消息、低延迟**；pass-by-reference 用于**大数据**。KK 指出 hybrid 走 HTTP/TCP + Redis 开销很大，所以大数据才用 RDMA
- **但论文实验里并没有真用 RDMA**，实际用的是 **ZeroMQ**（底下还是 TCP）

#### 其他几个 use case（快速带过）

- **天文光谱学（astronomical spectroscopy）**：没细讲
- **去中心化学习**：本质就是**联邦学习**——各 agent 持有自己的深度学习模型，在本地数据上训练，通过 Redis 交换并平均权重。KK 说这和实验室 2024 年发在 MLSys 的那篇 **LFL 论文**很像（用共享内存在层级 aggregator 之间做高效聚合），提到"需要重读那篇论文"。KK 也说联邦学习现在已经过气了，但 2022-2023 是热点，区别是 FL 强调隐私
- **信息抽取 / agentic workflow with LLM**：从大量论文语料里抽取特定事实，构建问答系统、生成多选题；每一步由不同 agent 处理。**KK 明确说这个对当前项目意义不大**

### 二、KK 阐述的项目定位（本次会议最核心的部分）

#### 要强调的核心贡献

> "我想强调的是：**agent 有一个到网络的接口，这个网络会有一个 API**，agent 通过它告诉网络所需的特性、性能、以及数据传输必须满足的 deadline。"

三个层次的复用/竞争关系：

1. 一个 experiment 内部有**多个 transfer** 共用一个网络
2. 一个网络同时被**多个 experiment** 使用
3. 这些 experiment 由分散在**不同国家实验室**的 agent 协调（不只是云平台，各 lab 有不同资源承担实验的不同部分）

#### API 应该暴露什么（KK 已经写进 Kiran 的论文里）

- 动态的 **latency 要求**
- **deadline**
- **需要传输的数据总量**
- **剩余待传输的数据量**

→ 由这些算出每个 application transfer 的**权重（weight）**，供 scheduler 决定优先照顾谁

#### 复用实验室已有工作

KK 明确点名：**MPQUIC for streaming** 里的 stream 机制 —— 一个 connection 内可以有多条并行传输，那里用的是 **deadline-driven + start-time fair queueing 调制**的方法来保证并发传输之间的公平性。现在要做的是：

- 跨不同 experiment 的 transfer 之间做优先级
- 同一个 experiment 在一个 connection 内多条 stream 之间做 **deadline-aware 的公平传输**

#### 统一传输协议的愿景

> "与其为不同类型的信息交换用一堆不同协议和框架（TCP 一个、HTTP 一个、RDMA 一个），我想看看能不能找到一个**统一的方法**，然后根据每种传输的相对需求去 tune 传输协议的参数。"

这正是他想用 digital twin 来验证的东西。

### 三、Digital Twin 到底是什么（KK 与同学的深入澄清）

同学问了一个很好的问题，KK 给出了目前最清晰的解释：

**运行链路：** 用户下达实验 workload 命令 → agent → **通过 API 调用我们的 transport protocol** → transport protocol 把数据包送进 digital twin → digital twin 返回结果

**关键类比：** "**把它想象成通过 NS-3 发包**" —— digital twin 会告诉你：

- 包到达对端花了多长时间
- 包是否在某个路由器上丢了（因为路由器在 twin 里被建模了）→ **我们的协议必须从丢包中恢复**
- 最终验证：在 twin 所代表的网络容量下，我们的 transport 能否满足分布式实验的带宽和 deadline 需求

**核心场景设定：** 多个实验并发运行时，**总需求超过网络容量** —— 这才是调度有意义的地方。

**digital twin 的价值：** 提供预测能力 —— 用哪条链路 latency 最好、什么时候需要用多条链路聚合来满足容量需求。

**Digital twin 的范围（KK 承认还不确定）：**

- 可能不止一个：一个给网络、一个给实验、每个国家实验室的数据中心网络各一个
- 还不确定是"多个独立 twin"还是"一个大 twin 内含多个部分"
- **我们只负责网络那部分的 simulator**；实验的 digital twin 由 Kiran 等 ORNL 的人做
- 图里提到的 **EPICS** 和 **IMARIS 3**（转录写作 iMarch 3）是控制真实设备的接口，说明确实有设备产生数据需要传输
- **FSA module** 负责聚合并提供网络分析数据
