## 一句话结论

三人认为，现有 VIT 更像一个能搭出拓扑、容器和简单仪器 workflow 的开发/演示环境，而不是 SciNet 所需的、能刻画多实验并发、网络竞争、deadline、priority、fairness、真实传输协议与联合资源调度的系统。近期不应自己承担“重做 digital twin”的无底洞式开发，而应先把需要的能力与当前缺口写清楚，通过 Mariam 索取正确版本的代码，检查现有实现究竟能支持到哪里。

## 二、首先澄清：哪些是 VIT 已有能力，哪些只是未来工作

KK 看到共享文档后，首先追问其中的描述到底属于哪一种：

1. 是 VIT 现在已经提供的能力；还是
2. 是两位同学认为 SciNet 需要、希望未来具备的能力。

讨论中的具体条目是：

> 用户通过一种 schema 描述 topology，然后由 AI 自动生成 VIT。

同学明确回答：**这是 future work，当前没有实现；对方计划将来实现。**

KK 随后把这一目标重新表述得更完整：这里要描述的不能只是 network topology，而应是**整个科学实验的期望 topology**，包括：

- instruments 在哪里；
- storage 在哪里；
- compute resources 在哪里；
- network 怎样连接这些组件；
- 整个 science experiment ecosystem 的其他必要组成部分。

目标是用一个简单 schema 表达上述系统，再由 AI 生成相应的仿真/模拟环境。同学确认这正是设想中的方向。

这一段开头另有一句被识别成 “BI is a service”，在上下文中无法形成可靠语义，因此这里只保留这一转写事实，不将它解释成任何 VIT 功能或项目结论。

## 三、KK 对系统形态的偏好：模块化互联，而不是一个巨型 VM

即使以后能由 schema 自动生成环境，KK 也不希望结果是一个单体组件。他更倾向于【TD】：

- 把不同功能放在多个彼此连接的组件或 Docker containers 中；
- 组件之间能够高效交换信息；
- 改动或扩展一个组件时，不必重做整个系统；
- schema 最好能表达“这一组东西放入一个容器，另一组放入另一个容器，然后把它们连接起来”。

他不喜欢当前看起来把所有东西放入一台 VM 的做法，但也承认尚不清楚把现有实现改造成模块化结构需要多大“手术”。

这里随即形成一条非常重要的范围约束：

> **团队不应接手创建和长期维护完整 digital twin 的责任。那会变成一个永无止境的开发项目，而且不是本组的核心研究兴趣。**

因此，如果近期 Mininet topology 仍需手写，也可以接受。自动生成 topology 不是眼下必须由本组完成的任务。

## 四、对现有 VIT 网络建模的主要质疑



### 1. 手写 topology 本身不是最大问题

当前 network topology 是手写的。KK 并不把这一点视为最严重的问题；他更担心的是：**VIT 是否真正、正确地使用了 Mininet 的网络行为。**

他提到，对方展示了某种 routing，但尚不清楚：

- 那是否是 Mininet 中由 OSPF、BGP 等协议真实产生的路由行为；
- 还是另外写的一套逻辑；
- 实验是否真的模拟了 TCP、transport protocol、forwarding 和拥塞控制；
- 或者只是把网络当成黑盒，根据观测数据拟合“给定条件下能得到多少 throughput / delay”。

转写把 OSPF 识别成 `USPF`、BGP 识别成 `PGP`，本文按网络上下文校正。

### 2. 当前实验似乎主要只建模 link latency

KK 认为，上一场展示的网络实验“有些站不住脚”：看起来只是给 links 加 latency，没有充分建模网络的其他关键特征，也没有纳入 deadline。

一位同学也表达了相同印象：VIT 似乎不关心网络内部细节，例如：

- queueing；
- priority；
- congestion control；
- transport protocol；
- packet forwarding；
- 在 router 或 switch 中实现 scheduling、routing 或 prioritization 后会发生什么。

在这种做法里，网络只是一个 black box：系统通过 measurement 得到一条 curve，再用曲线估计某种 workload 会经历多少 throughput 和 delay，而不是解释或复现网络机制本身。

### 3. mKN / curve-fitting correction 的边界

讨论提到上一场会议中的 mKN：它似乎不是从底层模拟网络，而是用来学习一个 mapping，把 digital twin 中的 latency / throughput 表现映射到真实网络或 testbed 中的表现。

三人的理解是：

```text
在真实系统与 VIT 中采样
        ↓
学习某个 workload 下的性能映射曲线
        ↓
用这条曲线修正 VIT 对 delay / throughput 的估计
```

KK 对这种方案的批评是：如果 workload 或 network environment 改变，就可能需要重新训练。那相当于：

- workload A 有一条 curve；
- workload B 有另一条 curve；
- 环境变化后还要再拟合；
- 运行时必须先判断该选哪条 curve。

他认为这只是“用 machine learning 拟合结果，却没有理解网络在做什么”。如果因为“TCP 不好模拟”就放弃 TCP，仅用 sockets 和 curve fitting 预测 data transfer，就无法自然表示多个 flow 共同占用网络资源时的 coexistence 与 contention。

一位同学还回忆，论文/报告似乎提到当 bandwidth 超过“10”时结果不再准确，但具体单位与原话在转写中损坏；KK明确说自己不记得 Anees 当时讲过这一点。会议最终仍回到比较确定的事实：对方使用 mKN 学一个 map 来校准 VIT 与真实网络的 latency/throughput 表现。

### 4. `tc` 只能提供粗粒度链路仿真

后半段讨论进一步把能力边界落到 Linux traffic control（`tc`）：

- `tc` 可以让一个 emulated link 表现出某个 delay；
- 也可以施加 bandwidth limit；
- 但只设置这些参数，并不会自动提供 workflow-aware priority；
- 不会自动实现 weighted scheduling；
- 不理解 experiment deadline；
- 也不会自动给出跨多个 workflow 的资源保障。

因此，只有 `tc` 不足以得到 SciNet 需要的系统。即便 Mininet/TC 底层支持更多 queueing 或 QoS primitives，上层仍需要 controller / scheduler 把实验需求翻译成具体策略。

## 五、现有 VIT 没有刻画的核心场景：多实验并发

KK 反复强调，当前展示似乎一次只运行一个 experiment：

- 某个实验占用其组件时，其他人就被挡在外面；
- 没有大量实验并行运行；
- 没有按实验特点确定 priority；
- 没有多个用户同时通过网络访问不同远程仪器的情形；
- 没有多条 transfer 共享网络时的竞争与公平性。

同学补充说，对方确实注意到了资源冲突，但只做了一个很简单的例子：两个用户想用同一台设备，User A 先拿到设备，User B 被拒绝。KK 承认，如果仪器本身一次确实只能运行一个实验，这种 mutual exclusion 可能是正确行为；但它远不足以表示预期系统。

真实目标场景是：

- 数百位 scientists；
- 使用数百台不同的远程 equipment；
- 多个实验同时经过网络；
- 某些实验还会共同使用 compute 和 storage；
- 系统要根据每个实验的性质决定如何调度和传输。

需要考虑的实验属性包括：

- 要发送多少 data；
- deadline 是什么；
- 某条 instrument command 是否有非常严格的 latency requirement；
- 一条 transfer 还剩多少 data；
- 离 deadline 还剩多少 time；
- 多条 transfer 之间是否要求 fairness；
- transfer 1 和 transfer 2 分别何时开始；
- 每条 transfer 到目前为止分别获得了多少 resource；
- 如何在它们之间公平或按优先级分配后续资源。

三人的结论是：这些问题目前都没有被现有展示真正表示。

## 六、deadline 的具体含义：科学家给的是整个实验目标

KK 用一个 parameter sweep 场景解释他所说的 deadline，并非只给单个 packet 或单个 job 一个简单的时间标签。

科学家可能提出：

1. 在多个 dimensions 上做 parameter sweep；
2. 运行一组全因子实验（转写为 `N factorial experiment`，准确术语需结合原始语音核对）；
3. 找到能优化某个 metric 的最佳参数；
4. 在“明天上午 10 点以前”交付整组结果。

这才是 workflow / experiment 层的 deadline。当前 VIT 的 simulation 并没有把这种 end-to-end completion requirement 纳入调度。

## 七、团队真正想研究的系统，而不是重写 simulator

KK 明确说，他原本计划研究的是：

- transport algorithms；
- scheduling；
- deadline-driven resource management；
- agents 如何彼此通信；
- agents 需要从哪些背景信息源取得什么信息；
- 怎样把 experiment requirements 转成资源与网络行为。

他并没有计划重新开发一个完整的 simulator。

在理想系统中，agent 需要理解：

- 当前 science experiment 需要哪些 instruments；
- experiment parameters 是什么；
- 哪些 parameters 重要，哪些不重要；
- 如何借助 background LLM 或其他知识源获得这些信息；
- 如何据此设计 experiment。

KK 随后重建了他心目中的完整执行链：

```text
科学家的实验需求
        ↓
一组 agent 理解目标、参数、仪器和约束，并设计实验
        ↓
agent / agent-functionality twin 执行或模拟 agent 行为
        ↓
network digital twin 承载 agent 之间、agent 与资源之间的通信
        ↓
network twin 把实验请求与输入送给 instrument twin
        ↓
instrument twin 模拟仪器工作并产生结果
        ↓
network twin 把结果送往 storage twin
        ↓
其他组件读取并处理结果
        ↓
agent 将结果呈现给提出实验的 scientist，并可能规划下一步
```

他说，这才是自己原先理解的整体系统，但现有 VIT 与这个模型相差很大。两位同学认同这也是团队最初的目标，并评价当前 digital twin 很简单，更像 toy system，没有复杂 device 或复杂的并发行为。

## 八、近期需要表达的“desirable features”

KK要求两位同学暂时不要设计整个 scheduler，也不必为了写这份说明再读大量论文。当前只需要把已经讨论清楚的**所需能力与缺失能力**列出来。

需要向合作方表达的主要 desiderata 是：

1. **比 latency 更完整的网络 characterization**
  - 不仅能设 link delay / bandwidth；
  - 还要能研究 queueing、priority、QoS、throughput guarantee、routing/forwarding 与 transport behavior。
2. **多实验 concurrency**
  - 多个 experiment 可以同时存在；
  - 可以共享 network；
  - 也可能同时竞争 compute 与 storage。
3. **deadline-aware behavior**
  - 理解 workflow / experiment deadline；
  - 根据 remaining data 和 remaining time 做决策。
4. **contention 与 fairness**
  - 明确哪些 flows / workflows 正在竞争；
  - 记录已经获得的资源；
  - 支持公平性、权重或优先级策略。
5. **dependencies**
  - 同学特别补充，需要表示任务或实验之间的 dependency。
6. **一个面向整体 workflow 的 scheduler**
  - 读取 workflow；
  - 使用下面的 digital twin 评估或执行；
  - 决定什么任务运行；
  - 决定在哪里运行；
  - 决定不同 experiment 怎样使用网络。
7. **更聚焦本组研究的 network-transfer scheduler**
  - 在多个 concurrent transfers 之间调度网络；
  - 面向 deadline、priority、fairness 与 contention 做资源分配。

KK 强调：这里是在说明**为什么需要 scheduler、希望它具备什么输入与能力**，并不是现在就把 scheduler 的算法设计完。

## 九、研究边界：网络是本组职责，agent 可作为长期兴趣

KK承认自己的讨论更偏 network，但他说“那正是我们的工作”。agent 层虽然不一定是本组的直接责任，但可能仍是整体项目中值得参与的一部分，例如：

- 自动创建多个 agent；
- 让不同 agent 分工执行任务；
- 让它们彼此协作并交换必要信息。

不过这些不必全部在 Phase 1 / 六个月内完成；KK 的意思是可以随着项目长期推进、例如后续进入 Phase 2 后再逐步扩展。近期优先级仍是弄清现有代码和 digital twin 到底能支持哪些功能，再选择最小可行的研究切入点。

## 十、怎样向 Mariam 索取代码：先说明目的，不绕过接口人



### 1. 不要只写“请把代码给我们”

KK不希望给 Mariam 的消息只是上一场会议的内容摘要，也不希望显得团队完全没有思考、只是因为“我们是项目成员”就索取代码。

更合适的沟通逻辑是：

1. 先说明基于项目最初 vision，团队认为 digital twin 需要刻画哪些方面；
2. 列出上面已经识别出的 desirable features；
3. 说明希望检查现有代码中哪些已经支持、哪些尚未支持；
4. 因此请求获得代码，以判断 VIT 能否用于这个目标以及需要扩展到什么程度。

这样 Mariam 能看到团队已经认真思考过需求，也更容易理解“为什么需要代码”。

### 2. 代码存在两个版本，但统一通过 Mariam 沟通

两位同学回忆，上一场会议中：

- Mariam 说她手上有一个版本的代码；
- Anees 又提到自己还有另一个版本；
- 因此目前不清楚应该要 Mariam 手里的版本，还是直接向 Anees 要他的版本。

KK 给出了明确的沟通原则：

> **Mariam 是团队与 ORNL 其他人的 interface。在 Mariam 明确让大家直接联系某个人以前，不要绕过她。**

具体做法是：

1. 先请 Mariam 提供她手里的原始版本；
2. 检查是否足够；
3. 如果不够，再请 Mariam 协调 Anees 提供另一个版本；
4. 始终通过 Mariam 这条沟通线推进。

## 十二、对 NRP 跨国部署建议的保留意见

上一场会议中有人建议使用 National Research Platform（NRP）。KK 对本组是否要投入这条路线持明显保留态度。

讨论中提到的设想包括：

- John（或另一位来自 UCSD 的参与者，姓名在转写中不完全确定）可以负责其中一部分；
- 在 containers 中再运行 Docker containers；
- 使用某种 Kubernetes / orchestration 工具进行调度；
- 把组件部署到不同国家或站点，例如日本和美国。

KK 认为需要先问清楚这种部署对研究问题的实际价值：

- 如果只是在 NRP 上做大量 implementation，可能与在 FABRIC 上做大型实验工程类似，会消耗很多时间；
- 除非其真实想法是让 containers 只用 NRP 机器作为承载基础设施，从而较轻量地仿真任务；
- 仅仅展示“系统横跨美国和日本”可能只是一个好看的 demo；
- 跨国本身并不会自动帮助团队开发新的 scheduler 或 transport algorithm；
- 若没有新的共存、竞争或调度机制，那么“美国到日本”与“家里一个房间到另一个房间”在研究贡献上没有本质区别。

KK 用非常直接的话收口：他不在乎为了炫示而跨站点，**真正想展示的是多个 experiment 如何 coexist，这才是主要问题。**

因此，若 John / UCSD 一侧愿意承担 NRP 实现可以继续观察，但本组应尽量避免陷入巨大的实验平台建设工作。

## 附录：近两年与“实验级调度层”相关的顶会论文调研

> 调研范围：2024 年至 2026 年 8 月。以下内容是会后文献调研，不是会议原话。

### 结论

近两年的系统顶会中，已经有若干论文分别覆盖了会议所说调度层的一部分：工作流任务与 I/O 的联合调度、跨地域的数据与 GPU 放置、网络通信阶段避让、GPU 作业的公平性与可预测性、应用优先级向网络 QoS 的映射，以及网络与边缘计算的联合 SLO 调度。

但截至本次调研，没有发现一篇 2024–2026 年系统顶会主会论文完整覆盖会议设想的这一层：以一次科学实验为调度单位，同时处理工作流依赖、仪器、计算、存储、广域网、端到端 deadline，以及多个实验之间的资源竞争。因此，这个方向并不是“完全没人做”，但会议提出的完整组合仍存在清楚的研究缺口。

### 顶会主线论文

#### 1. THman：工作流任务与多层存储联合调度（SC 2024）

- 论文关注 workflow DAG，在线联合调度计算任务和多层存储/I/O，并考虑与传统 HPC batch scheduler 的集成。
- 论文报告最高可将工作流 makespan 降低 30.9%。
- 与会议设想最相关的是：它不是只优化单个 job，而是会看任务依赖，并让计算调度与数据路径协同。
- 尚未覆盖：WAN、仪器，以及多个资源域共同决定的端到端实验 deadline；主要目标仍是 workflow makespan。
- 论文页面：[THman: Online Co-Scheduling of Workflow Tasks and Multi-Tier Storage Resources in HPC Systems](https://sc24.supercomputing.org/proceedings/tech_paper/tech_paper_pages/pap727.html)

#### 2. MAST：跨地域训练的数据与 GPU 联合放置（OSDI 2024）

- MAST 提供一个 geo-global workload queue，在多个 region 之间联合考虑训练数据位置和 GPU 可用性。
- 系统包含 quota、priority、fairness 和 preemption；必要时会复制数据，并可给数据迁移设置 soft deadline 和带宽。
- 在现有工作中，它与会议设想的上层全局控制面最接近：系统先接收 workload，再决定放在哪个地域、是否迁移数据，以及如何协调稀缺计算资源。
- 关键差异是：网络调度仍主要交给独立的数据迁移服务；它没有把动态工作流依赖、仪器资源和网络流联合纳入同一个优化循环。
- 论文页面：[MAST: Global Scheduling of ML Training across Geo-Distributed Datacenters at Hyperscale](https://www.usenix.org/conference/osdi24/presentation/choudhury)

MAST 的控制路径可以概括为：

```text
全局 workload queue
→ priority / quota / fairness
→ region 选择
→ data–GPU co-location
→ 必要时复制数据
→ 为数据迁移设置 soft deadline
→ 由迁移服务分配 bandwidth
```

这说明 MAST 已经走到了“数据、存储位置与 GPU 联合决策”，但网络带宽在其中仍更像约束或下游服务。论文也把存储、网络与 GPU 的更紧密联合优化列为后续方向。

#### 3. CASSINI：按通信阶段规避网络竞争（NSDI 2024）

- CASSINI 观察训练作业的周期性通信模式，通过平移不同作业的通信 phase，减少多个作业同时产生网络拥塞。
- 它允许多个作业共存，并报告平均完成时间最高改善 1.6 倍、尾部完成时间最高改善 2.5 倍，ECN marks 最高减少 33 倍。
- 对会议设想的价值在于：它展示了调度层可以根据应用执行结构来主动安排网络使用，而不只是被动响应拥塞。
- 尚未覆盖：动态 workflow DAG、存储、仪器、WAN 和端到端实验 deadline；其方法依赖 ML 训练通信的周期性。
- 论文页面：[CASSINI: Network-Aware Job Scheduling in Machine Learning Clusters](https://www.usenix.org/conference/nsdi24/presentation/rajasekaran)

#### 4. PCS：兼顾完成时间可预测性、性能和公平性的 GPU 调度（OSDI 2024）

- PCS 将 weighted fair queuing 与 simulation-aided search 结合，在 completion-time predictability、performance 和 fairness 之间做权衡。
- 它主要处理 GPU 作业，不联合调度网络、存储或仪器。
- 对会议讨论尤其重要的一点是：PCS 明确区分预测的 job completion time 与用户声明的 deadline，并指出用户 deadline 可能被策略性夸大。
- 这直接提醒未来实验调度层：不能无条件相信用户提交的 deadline 或最低带宽需求，否则系统容易被“报得越急、拿得越多”的激励扭曲。
- 论文页面：[PCS: Predictability-Aware Cluster Scheduling for Deep Learning](https://www.usenix.org/conference/osdi24/presentation/bin-faisal)

#### 5. 从应用优先级到网络 QoS 的映射（NSDI 2025）

- 这项 Google 的工作把应用侧 priority 映射到 per-RPC DSCP/QoS，使应用语义能够下沉到网络执行层。
- 大规模部署经验显示，QoS class 的使用方式并不总符合直觉；例如，在某些已经过载的 QoS band 中，降级不一定会进一步恶化延迟。
- 这与会议中的“调度层向网络下发优先级”直接相关，可视为执行层机制和运营经验。
- 但它不是动态工作流调度器：映射关系总体是静态的，也不负责根据实验进度、剩余数据量和 deadline 重新计算资源分配。
- 论文页面：[Application Priority to Network Quality of Service: A Large-Scale Case Study](https://www.usenix.org/conference/nsdi25/presentation/buckley)

#### 6. SMEC：联合处理无线网络与边缘计算竞争（NSDI 2026）

- SMEC 面向 RAN 与 edge server 同时竞争的环境，通过解耦操作进行 deadline/SLO-aware 调度。
- 论文报告 SLO satisfaction 达到 90%–96%，对比方案低于 6%；尾延迟最高改善 122 倍。
- 它是“网络与计算联合决定 deadline 能否满足”的很强类比，说明跨资源调度可以显著优于分别调度。
- 但其对象是 5G/edge request，不包含科学工作流 DAG、存储和仪器。
- 论文页面：[SMEC: SLO-Aware Mobile Edge Computing under Radio and Compute Contention](https://www.usenix.org/conference/nsdi26/presentation/zhang-xiao)

### 更贴近科学工作流、但不属于同一档主会的工作

#### WOW（CCGrid 2025）

- WOW 联合决定动态科学工作流的 task placement 和 intermediate-data movement，并使用 speculative copies。
- 原型结合 Nextflow 与 Kubernetes；论文报告在合成模式上最高改善 94.5%，在真实工作流上最高改善 53.2%。
- 它比一般集群调度论文更接近科学工作流语境，但没有同时处理 WAN、仪器和实验 deadline。
- 论文页面：[WOW: Workflow-Aware Online Scheduling of Dynamic Scientific Workflows](https://eprints.gla.ac.uk/350601/)

#### SENSE in Practice（INDIS@SC 2025 Workshop）

- SENSE 把高层 intent 转换为跨域带宽预留，并在 NRP、FABRIC、CMS 等环境中演示网络服务编排。
- 论文报告简单服务平均 provisioning 时间约 183 秒，复杂服务约 290 秒。
- 它适合充当会议设想中的网络 actuator，但不是负责实验依赖和跨资源权衡的上层 scheduler。
- 分钟级 provisioning 时间也意味着，它更适合慢时间尺度的预留与重配置，不适合细粒度的快速闭环。
- 论文页面：[SENSE in Practice: Orchestrating Multi-Domain Network Services for Science](https://sc25.supercomputing.org/proceedings/workshops/workshop_pages/ws_indis117.html)

#### SC 2025 关于计算与仪器协同调度的 BoF

- SC 2025 的相关 BoF 已经明确把 compute、instrument 和端到端 availability 的协同调度描述为新兴需求和开放挑战。
- 这不是完整论文证据，但说明会议讨论的问题已进入 HPC 社区的显性议程，同时仍未形成公认的完整解决方案。
- 页面：[Co-Scheduling Compute and Instruments for Integrated Research Infrastructure](https://sc25.supercomputing.org/proceedings/bof/bof_pages/bof157.html)

### 现有论文与会议设想的根本差别

现有工作的调度单位大致是：

```text
THman     ：workflow task
MAST      ：ML workload / data table
CASSINI   ：周期性 communication phase
PCS       ：GPU job
Google QoS：RPC
SENSE     ：network service request
```

而会议真正需要的调度单位是一次完整的 Experiment：

```text
Experiment
├─ workflow DAG / 动态分支
├─ instrument reservation 或 lease
├─ compute tasks
├─ storage placement
├─ 多条彼此依赖的 network flows
├─ end-to-end deadline
└─ 当前进度、剩余数据量和决策窗口
```

因此，真正缺失的调度层可以定义为：根据实验的实时状态，把端到端 deadline 和任务依赖翻译成仪器、计算、存储的 admission/placement 决策，以及网络的 rate、priority、route 或 reservation，并在多实验竞争和执行偏差下持续重算。

### 不能只把现有系统简单串起来的原因

1. **跨资源可行性。** 仪器、计算和网络必须出现兼容的时间窗口；任一资源单独可用，并不代表实验整体可执行。
2. **依赖感知的资源价值。** 如果上游任务已经错过窗口，单独抢救一条下游流量没有意义；资源价值取决于它位于哪个依赖路径上。
3. **真实性与激励。** 用户可能夸大 deadline、优先级或 `BW_Min_Fail` 以争取资源。PCS 已经展示了类似问题，因此调度策略需要 admission control、历史校准或收费/配额等约束。

### 建议阅读顺序

1. 先读 MAST：它最接近会议所需的上层全局 scheduler 架构。
2. 再读 THman：理解如何把 workflow dependency 与计算、I/O 联合起来。
3. 接着读 CASSINI 和 NSDI 2025 的 QoS 工作：分别理解网络竞争规避和网络执行机制。
4. 最后读 PCS：重点思考 deadline 的可信度、可预测性和公平性，而不只是调度算法本身。

综合来看，最有潜力的论文定位不是再做一个独立的 network scheduler，而是做 **experiment-level orchestration**：上层维护实验状态与依赖，向现有计算、存储、网络控制器发出协同决策，并以端到端实验成功率或 deadline satisfaction 作为核心目标。

## 附录二：六篇候选论文的阅读价值判断

> 调研日期：2026 年 8 月 12 日。以下内容是对会后找到的六篇论文所做的筛选，不是会议原话。

### 总体判断

按“对会议讨论的 experiment-level scheduler 有多直接”排序如下：

| 优先级 | 论文 | 判断 | 与当前问题的关系 |
|---|---|---|---|
| 1 | [ASGE-RR](https://arxiv.org/abs/2608.06033) | **必须立即读** | 最接近核心问题，也是目前最大的 novelty threat |
| 2 | [Murakkab](https://www.usenix.org/conference/osdi26/presentation/chaudhry) | **必须精读** | 最成熟的完整 workflow control plane，且发表于 OSDI 2026 |
| 3 | [Maestro](https://arxiv.org/abs/2606.12950) | **值得精读** | workflow-aware、cross-cluster、SLO-aware scheduler 的直接实现 |
| 4 | [AgentVNE](https://arxiv.org/abs/2601.02021) | **选择性阅读** | 问题形式相关，但实验与方法的说服力较弱 |
| 5 | [OpenHands](https://arxiv.org/abs/2407.16741) | **按需查阅** | 是 workload/runtime，不是 scheduler |
| 6 | [Network Digital Twin](https://arxiv.org/abs/2605.24318) | **可以跳过** | 只做拥塞感知 routing，基本没有 experiment/workflow semantics |

### 1. ASGE-RR：最需要警惕，也最值得先读

这篇几乎正面命中了上一份调研总结出的缺口：

```text
运行时逐渐显露的 workflow DAG
+ 整体 workflow deadline
+ service replica placement
+ request/response network path
+ link 和 service capacity
+ 对未来分支的预测
+ 可修改的软预留
→ 最大化 deadline 前完成的 workflow value
```

它不是给每条流独立选择最短路径，而是回答：当前把稀缺路径分配给这条 call 后，会不会导致未来才出现、但对整体 deadline 更关键的 call 无路可走？

这与前述“依赖感知的资源价值”基本相同。它还把调度单位明确提升到整个 workflow：只有完整 workflow 在 deadline 前完成，才计入 value。[论文全文](https://arxiv.org/pdf/2608.06033)

它与科学实验调度层仍有以下边界：

- 对象是 AI-agent dependency call，而不是 instrument-driven experiment。
- 资源只有 service replica 和 network link，没有仪器 lease、HPC allocation 和存储位置。
- 每个 call 出现后选择 replica/path，尚未联合决定科学任务何时执行。
- 模型中的 service-time bound 忽略 queueing；真实 HPC batch queue 会更难处理。
- 没有处理用户声明的 deadline、value 和资源需求是否真实。

评价规模也不够强：实验只有 20 个 evaluation tasks 和五台 WAN VM。Moderate contention 下，它比 rolling horizon 高 8.75 个百分点；但 saturation 下的置信区间包含 0。20 个任务中，五个改善、十四个持平、一个变差。

**判断：**它不一定已经把问题“做成”，但已经把最核心的算法问题写出来了。后续 proposal 或论文必须明确说明，为什么 scientific experiment scheduling 不是简单换皮的 ASGE。

### 2. Murakkab：最应该学习的系统骨架

Murakkab 是这六篇中发表层级和系统完整度最高的工作，发表于 OSDI 2026。它把 agentic workflow 的模型调用、工具执行和数据依赖暴露成完整计算图，再统一优化：

- workflow topology；
- 每个节点使用什么 model/tool；
- CPU/GPU 类型及并行度；
- 多租户 co-location 和 multiplexing；
- quality、latency、energy、cost SLO；
- 运行时扩缩和 request dispatch。

这正对应会议中“不要让计算、网络、工作流各自看不见对方”的系统架构思路。[论文全文](https://www.usenix.org/system/files/osdi26-chaudhry.pdf)

最值得借鉴的不是某个具体调度公式，而是它把决策拆成了三个时间尺度：

```text
workflow onboarding
→ 确定 DAG 和可用 executor

每个 optimization epoch（论文中为 60 分钟）
→ 选择 model/tool、硬件、并行度和实例数量

每个 request / 秒到分钟
→ dispatch、batching、auto-scaling
```

这可以直接类比成当前方向中的设计：

```text
实验注册
→ 声明 workflow、instrument、数据依赖和 deadline

慢循环
→ 预留仪器、计算、存储和 WAN capacity

快循环
→ 根据实时进度调整流优先级、路径和计算 dispatch
```

但 Murakkab 没有做 WAN bandwidth/path scheduling，也没有仪器、HPC batch queue 和不可暂停的数据源。它更像所需上层 control plane 的云端版本，而不是完整竞争者。

### 3. Maestro：最接近实时 workflow-aware scheduler 的实现参考

Maestro 读取的信息已经很像会议所设想的实时状态：

- agent role 和 workflow position；
- 当前 stage 是否会调用 tool；
- 预测的输出长度与 KV footprint；
- workflow remaining time；
- 各 cluster 的 model readiness；
- cluster 间 latency。

然后分三层调度：

```text
node：模型权重与 KV memory 管理
cluster：综合 latency、model readiness、memory feasibility 做 dispatch
global：按 workflow remaining time 做可抢占 SRTF
```

它有一个包含 32 台双 A100 服务器的原型，并使用 46,769 个 jobs、144,524 个 stages；高竞争下，相比 EDF 的 SLO attainment 提高 23.6 个百分点。[论文全文](https://arxiv.org/pdf/2606.12950)

需要保留的怀疑包括：

- “cross-cluster network”只体现为 latency，没有调度 bandwidth、route 或 reservation。
- 大量 workload 来自固定 workflow template，部分输入是 synthetic。
- deadline 根据 isolated execution distribution 人工设置，不是用户或真实实验 deadline。
- 当前只有 homogeneous A100 和两个 service classes。
- 论文自己承认 external tool execution 尚未纳入联合调度。

因此，它最适合用来回答：已经知道 workflow remaining time 后，如何把它转化为 queue priority、placement 和 memory admission？

### 4. AgentVNE：问题形式相关，但不用精读

AgentVNE 把 multi-agent workflow 表示成 virtual graph，把 cloud/edge infrastructure 表示成 substrate graph，然后联合考虑：

- CPU、memory、disk；
- network topology；
- hardware affinity；
- agent placement；
- virtual-link mapping。

概念上确实相关，但评价几乎完全基于模拟：

- Waxman 生成的 10–600 节点网络；
- workflow 只有 5–7 个节点；
- Poisson arrival 和 exponential lifetime；
- 主要 latency 指标实际是 congestion-weighted hop count；
- baseline 是 Greedy、GA 和较旧的 GAL-VNE；
- 没有真实 workflow deadline，也没有运行时显露的动态依赖。

其中“让 LLM 识别 semantic affinity，再用 GNN/Transformer/PPO placement”更像算法包装，目前没有证明 LLM 是必要的。[论文全文](https://arxiv.org/pdf/2601.02021)

建议只读 system model、constraint 表达和 related work，不用投入时间精读神经网络结构。

### 5. OpenHands：不是 related scheduler

OpenHands 是 AI software agent 平台，核心内容包括：

- agent 与 shell、浏览器、代码环境交互；
- sandbox runtime；
- event stream；
- 多 agent 协作；
- benchmark 和 integration testing。

它值得阅读的条件只有两个：

1. 需要理解 ASGE-RR 的真实 dependency calls 是如何出现的；
2. 需要设计一个能够拦截 tool call、在连接建立前咨询 scheduler 的 runtime hook。

否则，它不帮助回答资源如何调度。可以把它当作 ASGE-RR 使用的 workload generator，而不是 related scheduling work。[论文全文](https://arxiv.org/pdf/2407.16741)

### 6. Network Digital Twin：可以跳过

这篇工作的控制路径是：

```text
GNS3 模拟网络
→ 收集 router/link 指标
→ MPNN 判断边是否拥塞
→ 生成 Policy-Based Routing 配置
→ 将流量移到未拥塞链路
```

它没有 workflow dependency、experiment deadline、计算/存储/仪器资源、多实验价值仲裁或 admission control。

实验主要是图模型生成的拓扑、逐渐增加的文件传输负载，以及 MPNN-PBR 与 MPLS/OSPF 的比较。鉴于已经读过 VIT 和 SciNet，这篇提供的增量很小。[论文 HTML 版](https://arxiv.org/html/2605.24318v1)

### 建议阅读顺序

建议按“先判断 novelty，再学习系统实现”的顺序阅读：

1. **ASGE-RR 全文：**先确定它与核心问题究竟重叠多少。
2. **Murakkab 全文：**学习如何把完整 workflow 暴露给 control plane，以及快慢两层优化。
3. **Maestro 的 §III–IV：**重点阅读 remaining-time priority、cross-cluster dispatch 和 evaluation。
4. **AgentVNE 的 system model 与 related work：**只用于建立 graph embedding 相关工作的边界。
5. OpenHands 与 Network Digital Twin 暂时不读。

### 对上一份调研结论的更新

上一份调研中“没有论文把动态 workflow、deadline 和 network path 放在一起”的说法需要收紧：**ASGE-RR 已经做了这个组合。**

因此，当前方向剩余的研究空间应更明确地落在：

> **instrument-driven scientific experiment + HPC queue/compute + storage + WAN bandwidth/path 的跨资源可行性，以及不可背压数据源和真实实验 deadline。**

这一定位比泛称“workflow-aware network scheduler”更安全，也更准确地说明科学实验场景相对于现有 agentic workflow scheduling 工作新增了什么。
