## Step 2 — DOE computing–instrument ecosystem：现状、目标与为什么需要 VIT

**Anees 这一段的核心不是“网络带宽不够”，而是仪器、存储和计算被隔在不同的物理位置、network/security domain 与运维制度里；现在靠人逐段跨越这些边界，目标则是把它们接成一条自动化的 end-to-end scientific workflow。VIT 是开发这条 workflow 的替身环境，不是 workflow 本身。**

### 1. 第一张背景图：一套科学应用横跨多个 DOE 站点

Anees 开始共享屏幕后，有参会者说画面太小，请他放大；放大后他从 DOE 全景讲起。图中包含的不是一座普通 cluster，而是多类设施组成的 ecosystem：

- 多个地理分散的 national laboratory sites；
- leadership / high-performance computing systems；
- beamlines、microscopes，以及 photon / neutron facilities；
- 连接这些设施的 site networks 和 wide-area network；
- 每个站点内部还存在多个彼此隔离的 network domains。

**[论文对照]** 这张 slide 很可能以 VIT 原文 Fig. 1 为起点，但会议版显然增加了 Anees 后来参与的 DOE 应用。论文 Fig. 1 的抽象只有两类端点——instrument facilities 与 computing facilities——通过各站点 LAN 和跨站 WAN 相连；会议将它具体化成 beamline、microscope、photon/neutron source、leadership computing 等实体。

这里的第一条因果链是：

```text
仪器和算力无法共址
    + 各自属于不同站点/网络域/管理制度
    ↓
实验控制、数据获取、数据分析必须跨设施完成
    ↓
需要的不只是 connectivity，而是一条能跨域执行的 workflow
```



### 2. Anees 用显微镜说明传统工作方式

Anees 随后缩小到 microscope ecosystem。传统流程中有三个彼此分开的对象：

1. **microscope / instrument**：真正采集实验数据；
2. **instrument control computer**：用户远程登录这台机器查看、操控显微镜；
3. **NAS 与 compute facility**：数据先落到独立 NAS，之后再去计算设施做 reconstruction、computation 或 analytics。

他描述的实际操作顺序是：

```text
用户登录 instrument control computer 操作显微镜
    ↓
测量数据写入与控制机分开的 NAS
    ↓
用户再登录 NAS，手工取得/上传/搬运数据
    ↓
用户进入某个 compute facility 做计算与分析
    ↓
如需改变实验，再由人把决定带回仪器侧
```

Anees 说，这种办法已经沿用大约 **20 年**。这里的低效不是某一次 copy 多花了几分钟，而是每个环节的身份、网络和操作上下文都由人手工接起来。

**[论文对照]** 这对应 VIT 原文 Fig. 5 与 §IV-A：instrument control computer 操作仪器，measurements 落到附近 NAS，再手工转移到 HPC 做 processing / AI/ML analytics；论文说这些 manual operations 可能持续 **days or longer**，限制实验操作的 tempo 和 rate。会议只说“这是用了约二十年的方案”，没有在录音中重复“days or longer”这个数字，因此后者只能作为论文补充，不能冒充本次 meeting 的新数据。

### 3. 真正难接的是 security / operational enclaves

Anees 指着图里的 instrument、control computer 和 compute system，强调它们各自处在不同的：

- firewall zone；
- network enclave / subnet；
- physical boundary；
- facility policy 与运维制度。

仪器控制机尤其敏感。按他的描述，很多控制机不会直接接入常规可路由网络，而只通过 private local network 与仪器相连。团队刻意避免让通用的 automated operations——转写举到 update 和 scheduling 一类操作——直接作用到这些控制机，因为它们属于 production facility；错误更新、错误调度或不准确控制可能影响正在运行的实验。

**[我的判断]** 所以“integration 很难”的主语不是 Mininet，也不只是 ESnet。链路即使完全连通，下面四个问题仍然存在：


| 边界   | 需要解决的事                                    |
| ---- | ----------------------------------------- |
| 网络边界 | 哪些地址、端口和路径允许跨域访问                          |
| 身份边界 | 远程用户/程序凭什么操作另一个设施的资源                      |
| 软件边界 | Windows 仪器控制环境与 Linux/HPC analytics 怎样互操作 |
| 运维边界 | 如何保证开发、更新与自动调度不破坏 production instrument   |


VIT 主要让团队在**不碰 production resource**时先解决和测试这些问题；它并不会自动替各设施制定真实的安全与准入政策。

### 4. 目标图：从人工搬运改成 autonomous end-to-end workflow

Anees 把当前方案与他们的目标方案并列：把多个 microscope / instrument facilities 和 computing facilities 对齐成一条 end-to-end workflow，而不是让用户在每个 enclave 之间手工接力。

他具体提到真实部署中要把 control 与 data 分开：

- **control-plane channel**：远程发 instrument commands、查询状态、调整实验；
- **data-plane channel**：把 scan measurements 放进计算侧可直接访问的 storage / filesystem，再交给 GPU/HPC analytics。

转写中出现了一个显微镜实验楼、另一个放置 HPC/GPU 系统的建筑，以及 DGX。建筑或系统名被 ASR 识别成 `I am all` 与 `K200`，VIT 原文无法确认其准确拼写，因此不擅自校正。能够确认的结构是：**仪器与 DGX/compute 不在同一建筑、属于不同网络；instrument 完成 scan 后，数据通过 mounted filesystem 在计算侧出现。**

**[论文对照]** 这张会议 slide 很可能是论文 Fig. 6 所画“cross-facility science instrument ecosystem”的真实部署版：

- data plane 通过跨平台 file mounting（论文举 Samba/CIFS）或 Globus 搬数据；
- control plane 通过专门的软件接口远程 steering instrument；
- 两条 channel 分开，因为控制命令和 measurement data 的大小、权限及可靠性要求不同。

论文还给出一个物理原因：高灵敏度 STEM 怕 mechanical vibration，multi-GPU system 不能和显微镜共址。因此“把 GPU 搬到仪器边上”往往不是可选项，跨楼宇甚至跨站点的 data/control path 是问题本身的一部分。

### 5. VIT 在这张目标图里到底负责什么

Anees 此时第一次给出会议版定义：VIT 是一套 software / infrastructure twin，用软件表示 ecosystem 的 processes 与 components；其中可以放入：

- emulated networks；
- virtual hosts；
- Docker containers；
- computing components；
- microscope 等 instrument simulators。

它解决的是目标系统开发阶段的两个不可用性：

1. **设计阶段，ecosystem 可能尚不存在。** 网络、计算设施或仪器部署还在设计/建设，代码没有地方跑。
2. **开发测试阶段，不能拿 production instrument time 调试。** 真实仪器是稀缺生产设施，不能长期占着做 debugging，更不能让未验证代码直接控制它。

所以会议里这部分的完整关系是：

```text
真实目标：跨域的 autonomous scientific workflow
                     │
                     │ 开发时真实生态不存在或不能占用
                     ▼
VIT：复制它所需的网络、主机、容器和仪器接口
                     │
                     │ 在替身上开发、debug、测试
                     ▼
验证后的软件再迁移到真实 ecosystem
```

**[论文对照]** 这正是原文 §II-A(b) 对 primary purpose 的限定：VIT 首要用于 software development 与 functionality testing，其成立依据是复制近似相同的软件环境。它不要求整个 twin 在物理过程或性能上都与真机等价；网络 throughput 的不等价后来甚至需要 mKN 另行校准。

### 6. 这一段对 SciNet 的直接含义

**[我的判断]** 会议在这里实际上把 SciNet 的实验对象分成了两层：


| 层                        | SciNet 想研究什么                                  | VIT 此时能提供什么                                                    |
| ------------------------ | --------------------------------------------- | -------------------------------------------------------------- |
| science/workflow control | 根据实验状态决定下一步任务与网络需求                            | 可运行 instrument simulator、control client 和 analytics code 的软件环境 |
| network operation        | 根据需求配置 topology、bandwidth、latency、QoS 或 route | 可复制多 network domain，并在虚拟链路上施加部分参数                              |


但此时还**没有**证明 VIT 能模拟 SciNet 最关心的动态 contention、deadline、跨 workflow priority 或闭环 routing stability。Anees 到这里只证明“这些组件能被放在同一个可运行环境里”，不是“环境的性能行为足够可信”。会议后半段对 Mininet TCP dynamics 的讨论正是这个边界。

## Step 3 — VIT 的边界与建模粒度：它包含什么，site / VM / container / Kubernetes 如何对应

**这一轮问答给出了 VIT 最准确的定位：VIT 是一个组合出来的 ecosystem-level twin；instrument simulator 或既有 software digital twin 是它内部的组件。当前实现的基本建模单元是 link、switch/router、vhost 和 Docker container，而不是 Kubernetes cluster。**

### 1. Mariam 的问题：software digital twin 和 VIT 是两套东西吗

Mariam 先指出自己的原理解：

- VIT 似乎主要负责 **network 与 storage**；
- instruments 则由另一个 **software digital twin** 模拟；
- 因而她不确定两者是平行组件，还是 VIT 本身就是 software digital twin 的一种实例。

她实际在问两个层次：

1. **范围边界**：instrument twin 在 VIT 外面还是里面？
2. **概念层级**：VIT 是 digital twin 的一种，还是 digital twin 旁边的 network/storage emulator？

Anees 的口头回答比较绕，但含义可以还原为：**先构建 VIT 这个整体 system，再声明它要包含哪些 physical-ecosystem components 的软件表示**——多少 hosts、哪些 software/processes、哪些 simulators、哪些 hardware-facing components、多少 containers。用于表示 instrument 的 simulator 或既有 digital twin 被装进这个整体，而不是在 VIT 外面另跑一套互不相干的系统。

### 2. 依据原文把 Anees 的回答重新分层

**[论文对照]** VIT 论文把这件事写得比现场回答清楚：VIT 是 digital twin 的一个特例，专门复制 science computing–instrument ecosystem 的 infrastructure 与 software environment。其三层可以这样读：


| VIT 层                                        | 放什么                                                                             | 本次问题中的角色               |
| -------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------- |
| **EI — Ecosystem Infrastructure**            | vhosts、Docker microservices、instrument simulators、site LAN、WAN、vSwitch/vRouter  | 被复制的基础设施与运行载体          |
| **SII — Software and Integration Interface** | Python libraries、instrument control APIs、Nion Swift / EPICS 接口等                 | 让 twin 里的组件以接近真机的方式被调用 |
| **ES — Ecosystem Service**                   | remote steering、measurement collection、performance analytics 等 workflow service | 在底下两层之上完成的跨设施任务        |


因此正确的包含关系是：

```text
Digital twin（上位概念）
└── VIT（面向 computing–instrument ecosystem 的一种 system-level twin）
    ├── emulated network / hosts / storage access
    ├── instrument simulator 或已有 instrument digital twin
    ├── 与真机相似的 control API
    └── steering / analytics / measurement services
```

**不是**：

```text
VIT = network + storage
instrument software twin = 另一套平行系统
```

还有一个原文自身的模糊点：§III 先把 instrument simulators 放进 EI，紧接着又说 SII “may include” Nion Swift、EPICS API 和 instrument simulators。**[我的判断]** 更合理的拆法是：simulator 进程/容器属于 EI，simulator 暴露的 API 与 library 属于 SII；论文把“程序实体”和“它的接口”写混了。Mariam 的困惑不是凭空产生的。

### 3. 第二个问题：复杂站点应该按设备建模，还是按 Kubernetes 等高层对象建模

另一位参会者接着把问题推到 SciNet/NRP 的环境。他说真实系统同时包含：

- 每个 site 自己的 topology 与 ontology；
- 多个组织分别拥有的 networks；
- 跨域 overlays；
- Kubernetes clusters 等高层运行环境。

他问：VIT 是否必须从底向上逐个声明“这里一台 device、那里一条 link”，还是能直接表达 cluster 之类的高层 construct？他还提到 **Containerlab** 作为能较高保真地描述 network topology 的参照，并担心逐设备、逐链路建模会非常 labor-intensive。

这不是在问 VIT“能不能起 Docker”，而是在问它有没有一种**从真实基础设施描述自动生成 twin**的抽象层。这个问题在此处没有被真正解决。

### 4. Anees 的回答：当前实现的原语仍然是网络设备、vhost 和 container

Anees 回答，Mininet / Containernet 能构造：

- switches 与 routers；
- Linux bridge，或带 OpenFlow 能力的 virtual switch；
- virtual hosts；
- 连接到同一 VIT topology 的 individual Docker containers；
- host/link 级的 bandwidth、latency 等 traffic-control 参数。

但对“distributed Kubernetes clusters 能否被直接表示”，他的原话结论是：**没有实际探索过。** 他能确认的是 individual Docker container 可以作为 VIT network 中的节点；这与复制 Kubernetes 不是一回事。

区别如下：


| 当前 VIT 已展示                             | 尚未由这次回答证明                                             |
| -------------------------------------- | ----------------------------------------------------- |
| container 作为 topology 里的 endpoint      | Kubernetes API / control plane                        |
| 给 container 接一块 VIT virtual interface  | pod 调度、重启、伸缩与 service discovery                       |
| 配 site subnet、vRouter 与 WAN link       | CNI overlay、NetworkPolicy、跨 cluster service           |
| 在 container 中跑 application / simulator | cluster-level resource contention 与 failure semantics |


**[我的判断]** 所以把 VIT 部署在 Kubernetes 上，与用 VIT 模拟 Kubernetes，是两个相反方向：前者只是换宿主环境，后者要求把 Kubernetes 的控制行为也变成被测对象。会议此时只具备第一个方向的潜在可行性，第二个没有实现证据。

### 5. 一个 VM 里如何表示多个 site：隔离来自 network domain，不来自多 VM

Anees 特别纠正了一个可能的误解：他的当前实现**不是每个 site 一个 Docker container，也不是每个 site 一个 VM**。一套 VIT 可以整体运行在一个 VM 或一台原生 Linux 主机上；里面的多个 site 靠不同的 network domains/subnets 分开。

**[论文对照]** 原文 Fig. 3/4 的结构是：

```text
VIT 宿主（可为一个 VirtualBox VM）
├── Site A subnet
│   ├── vhosts / containers
│   └── gateway vRouter
├── Site B subnet
│   ├── vhosts / containers
│   └── gateway vRouter
└── emulated WAN
    └── site edge vRouters 之间的 pairwise links
```

会议中 Anees 说自己的模型里能看到约五个 networks：一个表示 ESnet/WAN，其余表示各 facility 的 subnet；转写能辨认出 SNS、OLCF 等名称，但完整清单不可靠。他还说 WAN 侧按各站点之间的 circuit connection 建模。**[论文对照]** 已发表 four-site VIT 使用的是 ANL、BNL、NERSC、ORNL，并把站间连接表示为 ESnet OSCARS dedicated circuits。

关键点是：**“一个 VM”只描述 VIT 软件在哪里运行；“多个 network domain”才描述它假装有哪些站点。** **这使单机功能测试很方便，但也意味着这些“远隔千里”的站点实际上争用同一宿主 CPU、内核和文件系统【TD-01】**

### 6. QoS 参数能配置，不代表端到端性能被忠实复现

Anees 接着说，他不只是给每个 site 放两三个节点；还会对 main links 做 traffic engineering / QoS 设置，复制 bandwidth 和 latency。`ping` 可以看到相应 RTT——如果配置的是单向 delay，round-trip measurement 会表现为约两倍。

转写随后有一句大意是“已经做到/验证到 1 Gb/s，与 ESnet 上某个实际 end-to-end 情况一致”，但语法与对象都被 ASR 破坏，无法判断指配置上限、某次验证，还是实际 production path，因此不把它当作可靠数字。

更重要的是，Anees 在这里说的“almost identical network parameters”必须拆成两类：


| 可直接设置并核对                       | 不能因此推定准确                        |
| ------------------------------ | ------------------------------- |
| topology、IP/subnet、route       | TCP congestion-control dynamics |
| 人为施加的 link delay、bandwidth cap | 多流竞争后的 achieved throughput      |
| `ping` 看到的 RTT                 | 高带宽长距离传输曲线                      |


**[论文对照]** VIT 原文明确展示反例：同样 RTT 下，laptop/desktop VIT 的 throughput 数值和曲线形状都不同于 10GigE hardware-emulator testbed；VIT 甚至得到 convex profile，而 testbed 是 concave profile。也正因此作者后来加入 mKN mapping。故此处不能把“latency / cap 配得出来”扩张成“网络性能几乎完全一致”。

### 7. instrument 怎样接入 VIT

Anees 最后回到 Mariam 的问题，给出了 instrument 接入条件：

- instrument 有 simulator，且 simulator 能表示 control API；或
- instrument 已有某种 digital twin，可以作为组件接入。

满足其中之一，就能把它与 emulated network、compute hosts 和 containers 组合成针对某个 purpose 的 ecosystem。**[我的判断]** 真正不可替代的前提仍然是 interface fidelity：VIT 能把 simulator 接上网络，不代表 simulator 的行为和真仪器一致。论文在 limitation 中也承认，准确的 instrument-emulation module 是 VIT 可行性的必要条件。

### 8. 这轮问答留下的三个明确缺口

1. **没有 topology/ontology → VIT 的自动翻译层。** 仍需人写 topology【TD-02】，第二位提问者担心的 bottom-up labor 没被消除。
2. **没有 Kubernetes fidelity。** individual Docker integration 不能替代 cluster、CNI 和 scheduler semantics。【TD-03】
3. **没有 performance fidelity 保证。** 可设置 QoS 参数，但高带宽 TCP、竞争与 workload-level timing 仍可能失真。【TD-04】

这三个缺口恰好预示 Anees 最后列的 “VIT as a service”：让用户用 schema 描述 topology，再由 engine/AI 生成 VIT。那是 future work，不是当前系统已有能力。【TD-05】

### 本步收口

```text
VIT 是 system-level twin
→ instrument simulator / digital twin 是内部组件
→ 当前用 link、router/switch、vhost、Docker 逐层拼出多个逻辑 site
→ 整套东西可以跑在一个 VM 中
→ 但 Kubernetes、高层 ontology 自动映射和端到端性能保真尚未解决
```

**下一步进入 Anees 的第一个完整 use case：four-site DOE VIT 如何组合 ESnet circuits、EPICS 与 iMars3D，让 BNL 用户远程控制 ANL beamline 并运行 tomography analysis；随后团队追问，这种单用户 connectivity demo 与 SciNet 所需的“大量用户、竞争 workflow、deadline/QoS 差异”之间还差什么。**

## Step 4 — 已完成的 two use cases，以及它们离 SciNet 多工作流调度还有多远

**Anees 展示的两个案例证明了“同一套未修改应用能跨 VIT 网络访问模拟仪器，并能迁移到真实设施”；但团队马上把标准提高到“大量用户、相互竞争、deadline 与 QoS 不同”。Anees 明确承认，当前只有一个非常有限的 two-user demonstration。**

### 1. Four-site DOE VIT 的组成

Anees 先回到上一轮提到的 multi-network topology：他们建立了一个 **four-site DOE VIT**，各站点通过模拟的 ESnet circuit connections 相连，并把 instrument control 与 tomography analysis 应用放进同一个可运行环境。

**[论文对照]** 缺失的 slide 几乎可以确定对应 VIT 原文 Fig. 11。四个逻辑站点是：


| Site      | VIT 中的代表组件                                              |
| --------- | ------------------------------------------------------- |
| **ANL**   | APS beamline / EPICS simulator、计算节点与 iMars3D            |
| **BNL**   | 发起远程 workflow 的 `bnlcomp` vhost                         |
| **NERSC** | 发起另一条远程 workflow 的 `nersccomp` vhost                    |
| **ORNL**  | CNMS/Nion microscope、SNS/EPICS、CADES/FSA；原文还在这里放 FSA-AC |


站点 LAN 通过 gateway / edge vRouters 接到 emulated WAN；站间 link 被抽象成 ESnet OSCARS circuits。原文 Table 1 的 latency 是根据地理距离选取的 **notional values**，并非会议现场从 ESnet 实时抓取的遥测。

这套 VIT 里混用了两种 endpoint：

- **vhost：表示通用 compute / control node；**
  - `COMP` 电脑图标表示 **Mininet vhost（虚拟主机）**，不是一台独立 VM。它可以扮演：
    - 用户接入端：`bnlcomp`、`nersccomp`
    - 计算节点
    - 软件、数据或服务所在节点
- **Docker container：封装 EPICS、iMars3D 等有专门依赖的应用。**
  - 蓝色蜂巢图标表示 VIT 中的 **Docker container / containerized service**：
    - EPICS：仪器模拟器容器
    - iMars3D：重建分析容器
    - FSA / FSA-AC：图中按容器化节点表示；FSA 实际也可原生运行
- 所以，蜂巢是封装好的应用服务；电脑是运行客户端、计算代码等普通 Linux 进程的 vhost。

运行中的 container 可以通过 `dcontainerbridge` 再接一块 virtual interface，加入 VIT subnet，而不必停掉并重建整套 topology。

### 2. Use case A：BNL 用户远程访问 ANL beamline，再运行 tomography analysis

Anees 的口头描述是：把 EPICS 和 ORNL 开发的 iMars3D tomography application 放进 four-site VIT，演示 BNL 用户经模拟 ESnet 网络访问 beamline instrument、采集/控制 measurement，再调用 iMars3D 做分析。

由于转写把站点和动作挤在一个长句中，下面按 VIT 原文 Fig. 14–16 重建 slide 上最可能的完整路径：

```text
BNL science user / bnlcomp
    │
    │ ssh + EPICS Channel Access commands
    ▼
ANL / APS 的 EPICS-sim container
    │  caget: 读取 areaDetector 的 Noise PV
    │  caput: 修改 Noise PV / instrument setting
    ▼
生成 tomography measurements
    │
    ▼
ANL / APS 的 iMars3D container
    │  Jupyter notebook 做 reconstruction
    ▼
用户从 BNL 浏览器查看和操作分析
```

**[论文对照]** 原文给出的实现细节包括：

- BNL vhost：`172.19.0.4/24`；
- APS EPICS container：`172.18.1.3`；
- 模拟的是 areaDetector IOC 中 `13SIM1:cam1` 的 `Noise` Process Variable；
- 用户可用 `caget` 读取、`caput` 修改；

这里容易误解的一点是：**BNL 用户是远程操作者；论文示例中的 measurement 与 iMars3D container 都在 ANL/APS 一侧。** 它证明跨站点控制和远程使用计算服务，并没有展示大体量 tomography data 被从 ANL 搬到 BNL。【TD-06】

这一案例真正验证的只有三件事：

1. EPICS container 能作为 simulated beamline endpoint 加入 VIT；
2. 远端用户的真实命令和浏览器可以穿过 emulated multi-site network；
3. 后加的 analysis container 可以在 topology 已启动后接入并被访问。

它没有验证 deadline、资源竞争或网络调度。【TD-07】

### 3. 团队立刻追问：如果不是一个 user，而是大量 competing workflows 呢

一位参会者打断 use case，指出 SciNet 面对的不是“一个用户能否连通”，而是：

- large user base；
- 多条 workflows 同时竞争 instrument、compute 和 network；
- workflow 内不同 elements 有不同 requirements；
- 有的重 throughput，有的有 hard deadline；
- 不同 flow 需要不同 QoS。

这个问题把成功判据从：

```text
远端命令能不能到达？
```

换成：

```text
当总需求超过资源时，谁先跑、谁让路、谁必须按 deadline 完成？
```

Anees 的回答很明确：他有一个 **limited demonstration of multiple users**，随后会展示；没有声称已经实现大规模、多 QoS workflow scheduling。

### 4. Use case B：先在 Nion simulator 上开发，再把同一控制方案搬到真显微镜

Anees 说他们为 microscope workflow 建过两种 VIT：一个 ORNL-only，一个 multi-site。动机仍是无法长期占用真实 microscope 做 control software 的开发测试。

他的做法是：

1. 找到 Nion 提供给客户培训使用的 **Nion Swift simulator**；
2. 把 simulator 集成进 VIT；
3. 在 VIT 上开发 remote-control server/client；
4. 测通后，把同一方案的 server 部署到真实 microscope/control side，把 client 部署到 user side；
5. 在真实 ORNL ecosystem 运行。

他说明这项工作属于 **INTERSECT project**。

**[论文对照]** 这就是论文把“twin 中的软件环境近似等价于 production”落成代码的地方：VIT 里的 server 调 Nion Swift simulator API，真机 server 调 physical Nion Swift API；远端 client 的调用方式不变。可迁移性来自 simulator 与真机的 API compatibility，不是网络 emulation 自动提供的。

### 5. Mariam 追问：能否把 deadline / priority 变成 Mininet QoS

Mariam 把 large-workflow 问题具体化：既然 Mininet 能设置 bandwidth，是否也能设置 prioritization / weights，用来做 scheduling？即使 Mininet 本身不理解 workflow deadline，表示 microscope/user endpoint 的 containers 能否把 deadline 转成 network priority？

Anees 区分了“Mininet 可能具备什么”和“他当前实际用了什么”：

- 当前只通过 **TCLink / Linux traffic control** 设置 link capacity、delay 等参数；
- 没有在这套 VIT 中实现 deadline-aware scheduling；
- 也没有声称已使用 Mininet 的完整 QoS feature set；
- 其他功能如 vhost 与 storage/file-system mounting 可以组合，但不是 deadline semantics。

随后参会者复述确认：如果 Mininet 支持所需 QoS primitives，项目可以在现有 VIT 上扩展**【TD-08】**。Anees 同意，并建议涉及 Docker applications 时采用 **Containernet**。另有参会者指出 Puneet 团队对 Mininet 很熟悉，因此 network-emulation 部分可能有现成经验可用。

这里形成的接口实际上是：

```text
workflow deadline / science priority
        │  尚缺：翻译与调度逻辑
        ▼
network class / queue weight / rate limit
        │  Mininet/TC 可能执行其中一部分
        ▼
emulated link behavior
```

**[我的判断]** 中间那层才是 SciNet 的核心，Mininet 只是执行器。把 deadline 写进 container 并不会自动改变 network queue；必须有 controller 读取 workflow state、解决冲突、生成具体 queue/rate/path configuration。

### 6. “Multi-user demonstration”具体做了什么

Anees 随后展示 two-user microscope workflow。根据转写与原文 Fig. 12/13，可以还原为：

- NERSC 用户从 `nersccomp` 发起 `scan_channel.py`，远程控制 ORNL/CNMS 的 Nion microscope；
- BNL 用户从 `bnlcomp` 运行 `check_scan.py`，查询同一 microscope 的 scan status；
- status 为 **True** 时，表示 microscope 正被占用，第二位用户不能提交自己的 job；
- status 变为 **False** 时，表示 instrument vacant，第二位用户才可提交。

原文还补充：Nion microscope 有可动态加载多个 samples 的 magazine，因此两条用户 workflow 可以围绕同一设备运行；但演示中的并发仍只是“一人扫描，另一人轮询状态”。

这是一种非常薄的 admission control：

```text
if scan_status == occupied:
    reject / wait
else:
    submit
```

它没有：

- waiting queue；
- 用户或 workflow priority；
- deadline；
- reservation / lease；
- 公平性或抢占；
- network bandwidth competition；
- 多用户同时修改 instrument state 时的互斥协议。【TD-09】

Anees 自己也把它称为 **simple multi-user workflow**，没有把它包装成完整 scheduler。

### 7. 当前 VIT demo 与 SciNet 要求的差距【TD-10】


| 维度             | Anees 已展示                | SciNet 团队追问的目标                         |
| -------------- | ------------------------ | -------------------------------------- |
| 用户规模           | 两个远程用户                   | large user base                        |
| instrument 冲突  | Boolean busy/vacant      | queue、reservation、priority、fairness    |
| workflow 语义    | 单个 scan/status operation | 多阶段依赖、剩余数据量、hard deadline              |
| network policy | 静态 bandwidth/delay       | 根据 science state 动态改变 QoS/path         |
| 竞争             | 基本没有同时传大流                | 多 workflow 争用同一 WAN/compute/instrument |
| 成功判据           | 能访问、能迁移代码                | 在资源不足时仍优先保住重要 experiment               |


**[我的判断]** 这不是说 VIT 对 SciNet 没用，而是确定了分工：VIT 已经提供可运行的 instrument/network/application substrate；SciNet 要补的是状态模型、决策器和 contention workload。没有后面三样，实验只能再次证明“可以 ping 通、可以调 API”。

```text
four-site VIT 证明远端 EPICS + iMars3D 能连起来
→ Nion use case 证明 twin 上开发的控制代码能迁移到真机
→ two-user demo 只用 busy/vacant 阻止冲突

```

## Step 5 — APS–ALCF、resiliency testing，以及 Mininet 吞吐失真的补救

**这一步出现了 VIT 的两种不同价值：它既能在不破坏生产设施的情况下做 failure injection，也能生成可运行的网络实验；但它给出的高带宽 TCP 性能数字不可信。作者没有继续把 Mininet 调到“像真网”，而是用 physical measurements 学一个映射，把 VIT profile 校正成接近 testbed 的 profile。**

### 1. Argonne 的 tomography mini-app：复制真实 APS–ALCF 路径

Anees 先介绍一个仍在合作中的 Argonne use case。实际 workflow 是：

```text
APS imaging / detector 侧采集数据
        ↓ distributed data component
ALCF / Polaris 侧处理 tomography workload
```

团队已经把 workload 缩成一个 **mini-app**：各组件放在 containers 中，通过 Docker Compose 启动。Anees 的团队询问能否用它测试 network resiliency；对方同意后，向他们提供了实际 network architecture。VIT 因而不是凭空画一条 APS→Polaris link，而是复制：

- APS 数据采集侧的 components；
- ALCF / Polaris 处理侧的 components；
- 两侧之间的 physical topology；
- mini-app 的 data distribution / processing components。

转写中 APS 数据管理系统的具体名称被严重破坏，VIT 原文也没有这项新工作，无法可靠恢复，因此不补造名称。

| iMars3D demo  | APS–ALCF mini-app                   |
| ------------- | ----------------------------------- |
| 主要证明远程访问与应用接入 | 目的是复制一条真实 distributed workload path |
| VIT 论文已经发表    | meeting 中描述的后续合作                    |
| 没有主动制造故障      | 明确要用于 resiliency testing            |




### 2. Nagi 的早期 multi-VM / SDN 方案

Anees 随后展示一项 Nagi 在他加入前完成的早期工作：同样复制多个 DOE sites，但实现方式更重。

- 大约使用五个 VMs；
- 每个 VM 内运行不同的 Mininet network topology；
- 有 SDN controller 跨这些网络进行控制；
- 配有 Web interface，用来控制/展示跨设施网络设备；
- Anees 记得它也曾用于 beamline control，但口头表述带有 “I believe”，因此不是完全确定的归属。

**[论文对照]** 这与 VIT 原文对 precursor **VNSE** 的描述一致：早期方案为不同 sites/services 分配 dedicated VMs，部署较重；2023 VIT 的改进之一就是把整体打包为一个 integrated VM，并用内部 network domains 表示 sites。

这组 slides 很可能是在说明 VIT 的演化：

```text
多个 VM 各自模拟一段网络 + 外部 SDN control
        ↓ 部署过重
一个 VIT runtime 内构造多个逻辑 site/network domain
```



### 3. 为什么 resiliency 必须在 twin 上测

Anees 说另一项 ongoing work 是 VIT-based resiliency testing。原因不是 DOE 网络“不 resilient”，恰恰相反：生产网络已经承担真实业务，团队不能为了验证恢复机制而随意：

- 断开物理 link；
- 关闭真实 host / process；
- 破坏 APS–ALCF 正在运行的路径；
- 给真实 instrument workflow 注入错误。

因此他们在 VIT 中复制 network、host、process 与 workflow，再安全地制造失败。转写显示这项工作由 Nagi 与 Anees 协作：一侧负责 APS–ALCF VIT，另一侧负责 ALCF workflow/resiliency 部分；具体任务边界被 ASR 破坏，不再细分。

**[我的判断]** 对 SciNet 而言，resiliency experiment 至少要同时包含三种 fault，否则只测到一半：


| Fault                      | 观察目标                                 |
| -------------------------- | ------------------------------------ |
| link/path failure          | reroute、QoS 是否重新配置                   |
| endpoint/process failure   | workflow 是否重试、迁移或降级                  |
| instrument/service failure | 后续 flow 是否还值得保留，还是整个 task branch 应取消 |


会议只确认 VIT 能安全承载这类测试，没有给 fault model、恢复时间指标或已完成结果。

### 4. Anees 主动承认：Mininet 复现不了 10 Gb/s TCP dynamics【TD-11】

接着进入 performance fidelity。Anees 说 Mininet 不能很好地复制 TCP dynamics、congestion control 与 protocol behavior，特别是把 link 配成约 **10 Gb/s** 时：

- VIT profile 可能呈现错误的 convex shape；
- 或曲线不平滑、波动异常；
- 真实 / hardware-emulated testbed 则呈较平滑的 concave profile。

他尝试调整 congestion-control algorithm 与 congestion window，结果有所改善，但仍不稳定。这说明问题不是把 `tc bandwidth=10G` 写进去就结束；achieved throughput 同时受 host CPU、shared kernel、socket buffers、TCP tuning 和 competing processes 影响。

**[论文对照]** 原文 Fig. 17 给出具体证据：


| 环境                      | 配置/结果                                                     |
| ----------------------- | --------------------------------------------------------- |
| VIT on HP laptop        | 16 GB RAM，4-core i7-8565U 1.80 GHz；profile 明显失真           |
| VIT on Dell workstation | 16 GB RAM，10-core Xeon E5-2630 2.20 GHz；与 laptop 结果也明显不同  |
| physical testbed        | 两台 32-core Supermicro、RHEL7、10GigE Ixia hardware emulator |


在 BNL–NERSC 对应的 **91 ms** latency 下，testbed throughput 仍约 **8.3 Gb/s**；VIT 数值更低、形状也相反。相同 topology 和相同 Mininet 参数换一台宿主机就变，证明 measurement 在很大程度上量到了 VIT host，而不是所宣称的远端 ecosystem。

### 5. 作者现有方案：mKN + physical testbed 学一个 correction map

Anees 说他们不再要求 Mininet 从底层忠实重现所有 TCP 行为，而是：

1. 在 VIT host 上运行一个可调 RTT 的 micro-Kernel Network（mKN），收集 baseline throughput；
2. 在 physical / hardware-emulated testbed 上，对相同 RTT 收集 target throughput；
3. 用两组数据学习 inter-model mapping `f̂`；
4. 后续同一宿主机上的 VIT measurement 先经过 `f̂`，输出接近 physical testbed 的估计值。

```text
VIT/raw profile ──f̂──► estimated physical profile
```

**[论文对照]** 原文训练使用的 RTT 为 `{1, 22, 75, 93, 105, 150, 182} ms`，试了两类 regression：

- GPR（Gaussian Process Regression）：smooth model；
- EOT（Ensemble of Trees）：non-smooth model。

Fig. 19 显示两者都能把 laptop VIT 的错误 convex profile 变成更接近 testbed 的 smooth concave profile。

但它有清晰边界【TD-12】：

- `f̂` 是针对某台 VIT host 学的；换宿主机可能要 retrain；
- 宿主 load 明显变化时也可能要 retrain；
- 它校正的是 aggregate throughput profile，不会恢复真实 packet/queue dynamics；
- 需要先有 physical/testbed measurements，不能凭空预测从未测过的体系。



### 6. 参会者的关键评论：不要重新实现 TCP，直接 measure and represent

一位参会者指出，真实 throughput 不只由 CUBIC 等 congestion-control mechanism 决定；生产系统往往还有数页 kernel、buffer、NIC 与系统 tuning。试图在 Mininet 中从头复制几十年的 TCP/network optimization，代价大且仍难预测最终行为。

他倾向于两种模型：

1. **phenomenological model**：不解释每个底层原因，直接拟合观测到的 flow behavior；
2. **更理想的 real-time surrogate model**：持续读取真实 telemetry，动态更新对 flow 的表示。

他用上一次 Supercomputing 结束时的 “data tsunami” 举例：许多 flows 实际相当平滑，可以用简单 time-dependent functions 表示；少数 aggressive protocol 才会制造复杂干扰，应作为专门研究对象，而不是让所有模型都为最坏情况付出复杂度。

Anees 同意并把方案总结成：**VIT 先生成 synthetic profile，再用 ML 根据 physical measurements 修正。**

### 7. 不要把会上建议的 real-time model 和论文 mKN 混在一起


|          | VIT 论文中的 mKN                 | 会上提出的更进一步方向              |
| -------- | ---------------------------- | ------------------------ |
| 数据       | 预先采集的 VIT + testbed baseline | 持续的 production telemetry |
| 更新方式     | 通常先训练一次，host/load 变化再训练      | online / periodic update |
| 输出       | RTT→throughput profile 的映射   | flow 随时间变化的 surrogate    |
| 能否反映突发竞争 | 很有限                          | 目标上可以，但尚未实现              |


因此“他们已经有 real-time digital twin calibration”是不准确的。当前发表的方法是离线 cross-inference；实时 surrogate 是会议中的建议。【TD-13】

### 8. 对 SciNet 的意义：校正平均性能，不等于校正闭环行为

**[我的判断]** mKN 可以回答近似问题：

> 在给定 RTT 的单/少量 transfer 下，这台 VIT 测到的吞吐应映射成真网的多少？

但 SciNet 更关心：

> 多条带 deadline 的 flows 同时竞争，controller 改 route/QoS 后，queue、TCP 与下一轮 controller decision 会怎样共同演化？

后一个问题包含**反馈与因果动态**。静态 `f̂` 即使把平均 throughput 数字校准正确，也可能把 routing oscillation、短时 queue buildup、flow synchronization 等关键现象抹掉。会议开头对 congestion-aware routing stability 的怀疑，正好在这里重新出现。

所以比较稳妥的实验分工是：【TD-14】

```text
VIT：功能、接口、拓扑与故障注入
mKN/telemetry model：吞吐量级校准
真实 NRP/ESnet testbed：闭环稳定性与跨流竞争的最终验证
```



### 本步收口

```text
APS–ALCF mini-app 提供真实 workflow/topology
→ VIT 可以安全注入 network/host failure
→ 但 Mininet 的 10 Gb/s TCP profile 失真且依赖宿主机
→ 当前用 physical measurements 学 f̂ 做离线校准
→ 实时 surrogate 与闭环稳定性仍是 SciNet 要补的部分
```

**下一步进入 Anees 对 VIT deployment mode 的升级：把 VIT 原生部署到 ORNL DGX，形成 continuous design/development/debugging/deployment platform；workflow 测通后只改 instrument IP，就从 simulator 切到 physical microscope。随后还会讲 chemistry/Globus 场景和“VIT as a service”这项与 SciNet 最直接重合的 future work。**

## Step 6 — Native DGX、hybrid mode、chemistry/Globus 与 VIT as a service

**Anees 在这里把 VIT 从“外部 VM 中的替身环境”推进到“真实 ecosystem 内的开发入口”：VIT 原生运行在 DGX 上，与真实 mounted data 和 GPU 共址；控制 workflow 在 simulator 上测通后，只替换 instrument IP，就能切到 physical microscope。随后提出的 VIT as a service 则与 SciNet 直接重合——输入 topology/process schema，自动生成 twin，再由 agentic AI 管理和优化其中相互作用的 processes。（目前只是构想【TD-15】）**

### 1. 从 external VM 转向 ecosystem 内的 native VIT

Anees 先总结：此前展示的多数案例都把完整 VIT 装在一个 VM 中。那种模式适合外部开发，但完成后仍要把代码、配置与依赖转移到 production ecosystem。

他们后来在 ORNL ecosystem 的 **DGX system** 上原生部署 VIT modules，称为：

> continuous **design, development, debugging and deployment** platform

四个阶段共用同一运行位置：

```text
design → development → debugging → deployment
              同一台 ecosystem-side DGX
```

这样做仍然是为了避免占用 microscope booking time，但与 external VM 相比多了两项关键条件：

- DGX 能访问真实的 mounted filesystem / experimental data；
- workflow 能直接使用 DGX GPUs 做 computation、training 或 inference。

因此开发环境不再只有假的 hosts 和假数据，而是可以组合：

```text
simulated instrument control
+ production-adjacent data mount
+ real GPU compute
```

**[论文对照]** 2023 VIT 原文只把“在 ecosystem computing system 上原生执行 VIT，使代码可直接用于 in-situ production”列为 future work。会议表明这项方向后来至少已有 DGX deployment，不再只是论文中的设想。

### 2. Emulated mode 怎样切换到 physical mode

Anees 描述的开发流程是：

1. 在 DGX 上启动 VIT 与 microscope simulator；
2. workflow 通过 simulator 的 control environment 测试实际 commands；
3. 同时读取 mounted filesystem 中的数据，并使用 GPU compute；
4. 确认 workflow 正确后，把 client 指向 simulator 的 virtual/private IP 改成 physical microscope/control server 的 IP；
5. 其余 control logic 不变，切入真实设备。

```text
同一个 control client / workflow
          │
          ├── simulator IP → emulated mode
          └── physical IP  → physical mode
```

Anees 还把“部分真实、部分模拟”称为 **hybrid mode**。例如：

- instrument control 走 simulator；
- data mount 和 GPU 是真实资源；
  - **真实 data mount**：workflow 用生产环境相同的文件路径、权限和数据格式读取数据，能验证数据发现、I/O、文件处理是否真正可运行。
  - **真实 GPU**：直接运行实际的 tomography reconstruction、ML training/inference，验证依赖、显存需求和执行时间。
  - 之前不是“全仿真”：应用代码一直是真程序，但运行资源是 VM 宿主，不是目标生产资源。Hybrid mode 的意思是：**只把危险、稀缺的 instrument 留作模拟，storage 和 compute 直接用真**
- 或在验证后只把 instrument endpoint 切到真机。

这个切换能成立的必要条件不是“IP 可以改”，而是两端必须暴露兼容的 API、command 和 response semantics。Nion simulator 正好提供与 physical installation 相似的 Swift control environment，因此 IP 才是主要切换点。

**[我的判断]** “只改 IP”不应理解成所有 instrument 都能零修改迁移。至少还隐含：

- authentication / authorization 方式相容；
- simulator 与真机 method signatures 相同；
- state initialization 与错误码相容；
- physical firewall 允许访问；
- command timing 与副作用没有超出 simulator 覆盖范围。

VIT 原文的 limitation 也承认：如果 production software environment 差异较大，代码仍需 refactoring。

### 3. 两套 microscope deployment

Anees 说他们保留了两种 topology：

- four-site DOE VIT；
- ORNL-only VIT。

DGX 上的 VIT 一侧连接 mounted data，另一侧提供可通过浏览器/IP 使用的 UI 或服务入口；用户可以执行 control commands、运行 workflow、访问数据。切换到 physical instrument 时，主要改变 endpoint address，而不是重写整条 workflow。

这里的价值不在“少写一行配置”，而在于开发与部署不再是两个完全分离的环境：同一 DGX 上已经有真实数据路径、GPU 和 production network proximity，减少了从 laptop/VM 搬入 ecosystem 时的 environment drift。

### 4. Chemistry workflow：把 lab、instrument、orchestrator 与全球 compute 都放进 topology

Anees 随后介绍另一个尚未完成的 chemistry use case。转写中的项目与仪器专名损坏严重，只能确认其结构：

```text
chemistry instrument / lab
        ↓ control unit 获取 measurement 并控制 experiment
workflow orchestrator
        ↓
远端 compute facility 做 training / inference
```

由于无法在 physical system 上安全测试 resiliency，他构建了一个 virtual topology，复制：

- instrument lab；
- instrument/control unit；
- workflow orchestrator / controller；
- local 或远端 compute systems；
- 跨地域 network conditions。

他还把 VIT 直接与 **Globus** 连接，使 workflow 能访问真实 Globus transfer/compute-facing services；同时用 emulated latency 表示 compute 位于本地、其他美国设施，甚至 Japan、Australia 等远端位置。

这项实验仍是 **work in progress**，会议没有提供结果。它的目标是测试“全球分布的 compute endpoint + laboratory control workflow”在不同 location/network condition 下如何运行，而不是声称已经忠实复制所有国家的真实网络。

### 5. Anees 对 VIT 已用场景的总结

按会议中的总结，VIT 已经或正在被用于：

- beamline control；
- microscope control；
- chemistry / laboratory workflow；
- control-plane software development；
- Globus access；
- Docker applications 接入 VIT network，而不是只留在 Docker bridge；
- resiliency testing；
- network/computing measurement 与 ML correction。

转写还出现一句类似 `red five streaming` 的专名，但无法从 VIT 原文或上下文可靠恢复，故只记录其存在，不推断为 RTSP、Red5 或其他具体技术。

### 6. Anees 列出的 future work【TD-16】

Anees 的 future-work slide 大致包含六组：

1. 复制更复杂的 computing–instrument ecosystems；
2. 探索其他 network simulator/emulator 与 digital-twin components；
3. 进一步把 VIT 与 HPC systems 原生集成；
4. 处理 heterogeneous networks 与 heterogeneous applications；
5. 用 ML 修正或表示 VIT computing/network measurements；
6. 把 **VIT 做成 service**。

最后一项的目标是：用户不再手写全部 Mininet/Containernet topology code，而是用 method/schema 描述需要的 topology；一个 engine 接收描述，结合 AI/agent components，生成所需的 complex DOE network/ecosystem model。

```text
用户给 schema / requirements
          ↓
VIT service engine
          ↓
生成 network domains、links、hosts、containers、instrument components
          ↓
启动可运行的 VIT experiment
```

这正面回应了 Step 3 中“逐 device、逐 link 建模太 labor-intensive”的问题。但 Anees 的措辞是“正在做 / future work”，不是已经完成的能力。

### 7. 参会者指出：最后一项就是 SciNet 项目要做的

一位参会者立即回应：**“Your last bullet point is what we are trying to do in this project.”** 随后的解释把 SciNet 与 VIT 的连接说得比论文更清楚。

他的观点是：真实系统的 microscopic physical details 可能被 ensemble-level / macroscopic behavior 隐藏或覆盖；对项目更重要的抽象是：

- ecosystem 由一组相互作用的 **processes** 构成；
- network 与 end systems 是持续变化的 real-time systems；
- 每个 process 会提出 demands；
- 不同 process 有不同 requirements 与 metrics of success；
- 当 requirements 很多时，需要把它们抽象成可优化的 success metric；
- 然后用 agentic AI architecture 管理这些 processes，并按尚待定义的目标优化 operation。

因此 SciNet 想做的不是简单的：

```text
自然语言 → 生成一张静态 Mininet topology
```

而是：

```text
表示 processes、interaction、demand 与 success metric
        ↓
agent 观察当前 state
        ↓
选择 network / compute / workflow action（这应该是我们lab重点负责的一层）【TD-17】
        ↓
VIT 或真实环境执行
        ↓
measurement 返回，进入下一轮
```



### 8. “生成 VIT”与“用 agent 优化 VIT”是两个不同问题

**[我的判断]** 会议把两者连着说，但实现时必须拆开：


| 阶段                 | 输入                                       | 输出                                        | 当前状态                                 |
| ------------------ | ---------------------------------------- | ----------------------------------------- | ------------------------------------ |
| **Twin synthesis** | topology/component schema                | 可启动的 VIT                                  | Anees 的 VIT-as-a-service future work |
| **Twin operation** | workflow state、telemetry、success metrics | QoS/path/schedule/failure-recovery action | SciNet/agentic AI 要补的核心【TD-18】       |


只完成第一行，得到的是“自动生成 testbed”；只完成第二行而没有可信 testbed，agent 的策略又无处安全验证。两者连接处需要一个共同的 state/action schema。

一个最小 schema 至少要表达：

- sites、network domains、links 与 endpoints；
- instrument / compute / storage components；
- workflow processes 及依赖；
- flow demand、deadline、remaining volume；
- success/failure metrics；
- 允许 agent 执行的 actions 与 fault injection。

这份 schema 会议没有定义；“如何表示 processes and interactions”正是参会者留下的研究问题。【TD-19】

### 本步收口

```text
VIT 原生部署到 DGX
→ simulator、真实 data mount 与 GPU 可以混合使用
→ API 相容时，替换 instrument IP 即可切到 physical mode
→ chemistry/Globus 把模式扩展到全球 compute，但仍未完成
→ VIT as a service 自动生成 twin
→ SciNet 再用 agent 根据 process demand 与 success metric 操作这个 twin
```

**下一步是团队把抽象落到部署细节：一个 Argonne→ORNL workflow 到底需要一个 VM 还是两个 VM？ESnet 是否应当单独建模？随后他们提出“YAML/XML workflow → intelligent job submitter → VIT results”的 SciNet pipeline，Anees 解释 Mininet network namespace、Docker integration 与 scheduler 应该放在哪里。**

## Step 7 — 一台 VM 如何模拟多站点，以及 SciNet scheduler 应放在哪里

**当前 VIT 的默认结构是“一台 VM 承载整个 topology”，ANL、ORNL 与 ESnet 的分离由 network namespaces、subnets、vRouters 和 virtual links 实现，不需要每个站点一台 VM。SciNet 提出的 YAML/XML job submitter 并不在现有 VIT 中；它应当是 VIT 上方新增的决策层。**

### 1. 团队先提出了一个错误的部署模型

一位参会者用最简单的 two-point workflow 询问：

```text
Argonne detector 产生数据
        ↓ network
ORNL 接收、处理，scientist 在那里看结果
```

他的猜测是：打开一个外层 VM，再在里面创建两个 VMs，分别代表 Argonne 和 ORNL，然后配置中间网络参数并运行 simulation。

Anees 立即否定：**当前做法不是 nested two-site VMs，而是一台 VM 中运行一份 topology。** 站点分离来自不同的 network address space，例如给 ANL 一个 subnet、ORNL 另一个 subnet，再用 emulated WAN links 连接。

```text
一个 VIT VM
├── ANL network namespace/subnet
├── ORNL network namespace/subnet
└── emulated ESnet links/vRouters
```

因此：

- VM 是整套 VIT 的 packaging/runtime boundary；
- site 是 VIT 内的 logical network boundary；
- vhost/container 是 site 内的 endpoint；
- virtual link/router 表示站点之间的 network path。



### 2. 多 VM 是早期/可选方案，不是当前必要条件

Anees 承认 Nagi 的早期方案确实采用“每 site 一个 VM”或多个 VMs。Anees 自己过去也用过 **GNS3** 做 VM/network separation，甚至在 PhD work 中将它接到外部 ISP/network environment。

但他现在倾向一台 VM，理由是：

- topology 可以写在一个文件中并一次启动；
- 部署更快；
- 不需要启动、连接和管理许多 guest OS；
- QoS 仍可施加在每条 virtual link 上；
- 对软件开发与功能测试，network-level separation 已经够用。

会议中有人把理由复述为减少大量 I/O/overhead，Anees表示同意。**[我的判断]** 更准确地说，省掉的是 VM boot、虚拟 NIC、跨 VM forwarding 和多 OS 管理成本；不是科学 workflow 的数据量因此消失。

如果实验需要更强隔离或真实 router image，Anees 仍认为 GNS3 或多个 VirtualBox VMs 可用，只是属于 heavier-weight design。

### 3. ESnet 是否需要单独一台 VM

参会者继续问：若 ANL 与 ORNL 各有实体，是否应把中间的真实 ESnet 也建成独立实体，才能记录：

- 数据何时离开 ANL；
- 何时进入 emulated ESnet；
- 何时到达 ORNL；
- 中间 latency / throughput 如何变化。

Anees 回答：**即使所有东西都在一台 VM 中，仍可监控每条 virtual link。** ESnet 在当前 VIT 中不是一台“ESnet VM”，而是一组 edge routers 与 links；在 link ingress/egress 采集 timestamp、counter 或 traffic measurement，就能观察虚拟 WAN。

```text
ANL vRouter ──[可监控 virtual link]── ESnet topology ──[可监控 virtual link]── ORNL vRouter
```

如果研究目标要求 ESnet 自己拥有独立 OS/process/router image，才需要 GNS3 或多 VM；当前 VIT 的抽象只把它表示为 topology + configured link behavior。

**[我的判断]** 这两种方案回答不同问题：


| 表示方式                       | 能回答什么                                  | 不能忠实回答什么                                          |
| -------------------------- | -------------------------------------- | ------------------------------------------------- |
| 单 VM 中的 virtual links      | workflow 是否连通、配置是否生效、基本 timing/counter | 独立 router CPU、真实 queue/NIC contention、跨设备 failure |
| 多 VM / GNS3 / real testbed | 更强的设备与 failure isolation               | 部署重、实验成本高                                         |




### 4. 团队提出 SciNet 的完整 pipeline

接着团队把需求画成了一条明确的数据流。假设同时提交两条 workflows：

- workflow A：Argonne→ORNL，执行任务 A；
- workflow B：同样 Argonne→ORNL，但执行另一种任务，可能有不同 deadline/resource requirement。

每条 workflow 用简单的 XML 或 YAML 描述，然后：

```text
Workflow YAML/XML × N
        ↓
intelligent job submitter / scheduler
        ↓ 决定何时运行、放在哪个 facility、给什么 network treatment
VIT
        ↓
执行与 measurement results
```

提问者判断 Anees 当前系统缺少最上面的 initial layer。这个判断是对的：现有 VIT 能运行 topology 和 components，但不解析 workflow intent，也不替多条 workflow 做智能 scheduling。【TD-20】

### 5. Anees 的回答：这个 scheduler 可以加，但不是现成功能

Anees 同意可以在 VIT 上构建 scheduler，因为 VIT 底层仍是 Linux/Mininet：scheduler 可以作为普通 process，在某个 vhost 或 container 中运行，调用其他 virtual hosts、workflow simulators、HPC components 与 network-control utilities。【TD-21】

但他的回答是“you can build it”，不是“已经有”。现有能力与待开发层应分开：


| 现有 VIT                            | SciNet 需要新增【TD-22】               |
| --------------------------------- | -------------------------------- |
| topology、IP、route、link parameters | YAML/XML schema 与 parser         |
| vhost/container execution         | multi-workflow queue/state store |
| instrument/application simulator  | deadline/priority/resource model |
| traffic control hooks             | scheduling/optimization policy   |
| measurement hooks                 | 结果评价与下一轮 decision                |




### 6. 为什么所有 vhost 都能调用宿主软件

Anees 用 Linux namespace 解释当前实现。Mininet vhost 本质上是宿主机上的 process，主要隔离的是 **network namespace**：每个 vhost 有自己的 virtual interface、IP 与 routing table。【TD-23】

但它默认不具备 Docker 那种完整隔离。Anees 说 Linux 有多类 namespaces，而 Mininet 主要只分开 network domain；因此宿主机安装的 utilities/software 可以从不同 vhosts 调用。这是他故意利用的特性：不必给每个 emulated compute node 重装同一套 Python 和工具。

代价是【TD-24】：

- vhosts 共享 host filesystem；
- 共享 CPU/kernel；
- 软件依赖无法真正分开；
- resource/performance isolation 很弱。



### 7. 什么时候改用 Docker container

若 workflow simulator/application 已经以 Docker image 交付，或需要独立依赖环境，Anees 就把它作为 Containernet node 导入 VIT【TD-25】：

1. container 原本接 Docker bridge；
2. 将应用流量从默认 bridge 移到/接入 VIT network；
3. 给它分配对应 site subnet 的 interface/IP；
4. 让 scheduler 或其他 vhost 通过 VIT path 调用它。

因此 vhost 与 container 的选择标准是【TD-26】：


| 需求                                              | 选择                       |
| ----------------------------------------------- | ------------------------ |
| 只需独立网络身份，共用宿主软件即可                               | Mininet vhost            |
| 需要自己的 filesystem/dependencies/process isolation | Docker/Containernet node |




### 8. Scheduler 放在哪里不重要，掌握什么信息才重要

Anees 说 **scheduler 可以从任一 vhost 启动**；物理位置不是难点。**[我的判断]** 真正缺的是 scheduler 的输入与控制权限【TD-27】：

- 是否知道 workflow deadline、remaining data、task dependency；
- 是否知道 instrument/compute 当前状态；
- 是否能修改 rate、queue、route 或 resource allocation；
- 是否能把 measurement 与 success metric 对应起来。

没有这些，scheduler 即使成功跑在一个 vhost 上，也只是另一个脚本，不是 science-aware controller。

### 本步收口

```text

→ site/ESnet 靠 network namespace、subnet、router、link 区分
→ 多 VM/GNS3 只在需要更强设备隔离时使用
→ 当前 VIT 没有 YAML/XML job submitter
→ SciNet 应在 VIT 之上补 parser、state、scheduler、policy 和 feedback loop
```

### 4. Anees 的两个部署顾虑

**第二，nested container networking。** 如果把整个 VIT 放进一个 Kubernetes/Docker container，那么 VIT 内部还要创建：

- Mininet vhosts/network namespaces；
- virtual interfaces/bridges；
- Containernet Docker containers。

**[我的判断]** 这里的主要障碍不是“Docker 语法”，而是权限和网络：创建 network namespace、veth、bridge、traffic control 通常需要 privileged mode 或 `CAP_NET_ADMIN`；这些在多租户 Kubernetes 上未必默认允许。

## TD 汇总

共 28 个标记；以下 `TD-01`—`TD-28` 与原文出现顺序一一对应。

### 1. 一些重点

1. **单 VM 的隔离只是逻辑隔离（TD-01）。** 多个 site 由 network domain/subnet 区分，但仍共享宿主 CPU、kernel 和 filesystem，因此适合功能测试，不代表真实多站点资源隔离。
2. **Docker endpoint 不等于 Kubernetes twin（TD-03）。** VIT 能接入 individual container，但没有复制 Kubernetes control plane、CNI、scheduler 和 cluster semantics。
3. **能配置 QoS 参数不等于 performance fidelity（TD-04）。** bandwidth/delay 可设置，但高带宽 TCP、竞争和 workload timing 可能失真。
4. **EPICS+iMars3D demo 没有展示大数据跨站传输（TD-06）。** BNL 是远程操作者；measurement 和 iMars3D 都位于 ANL/APS。
5. **现有 demos 的验证边界很窄（TD-07、TD-10）。** 已验证远程访问、代码迁移和两个用户的 busy/vacant 检查；未验证 large user base、deadline、priority、资源/带宽竞争、动态 QoS、network scheduling 和资源不足时的实验保障。
6. **Mininet 无法忠实复现 10 Gb/s TCP dynamics（TD-11）。** profile 的数值和形状受宿主机、shared kernel、socket/TCP tuning 影响。
7. **mKN 有明确边界（TD-12）。** `f̂` 绑定训练宿主；host/load 变化可能要 retrain；只校正 aggregate throughput，不恢复 packet/queue dynamics；且依赖 physical/testbed measurements。
8. **当前不是 real-time calibration（TD-13）。** 已发表方法是离线 cross-inference；实时 telemetry surrogate 只是会上建议。
9. **DGX hybrid mode 已做，VIT-as-a-Service 未做（TD-15）。** VIT 可在 DGX 上使用真实 data mount/GPU，并在 simulator 与真 instrument 间切换；schema→自动生成 twin 仍是构想。



### 2. 需要做的事

1. **构建 topology/ontology → VIT 的自动翻译层（TD-02、TD-05）。** 当前仍由人手写 Mininet/Containernet topology；目标是 schema→engine/AI→VIT。
2. **扩展 QoS 实验能力（TD-08）。** 确认 Mininet/TC 支持的 queue、weight、rate primitives；需要 Docker endpoint 时使用 Containernet。
3. **补 instrument concurrency control（TD-09）。** 不能只做 busy/vacant；需要 lock/lease、queue、reservation、priority 与冲突处理。
4. **按三层验证系统（TD-14）。** VIT 测功能/接口/拓扑/故障；mKN或 telemetry model 校准吞吐量级；真实 NRP/ESnet testbed 验证闭环稳定性和跨流竞争。
5. **推进 Anees 列出的 future work（TD-16）。** 更复杂 ecosystem；其他 simulator/emulator/digital-twin components；VIT-HPC 原生集成；heterogeneous network/application；ML measurement correction；VIT as a service。
6. **定义共同 schema（TD-19）。** 至少表示 topology/components、process interaction、workflow dependency、demand、deadline、remaining volume、success metric、可执行 action 与 fault injection。



### 3. 我们 lab 需要 focus on 的事

1. **Twin operation / agent decision layer（TD-17、TD-18）。** 输入 workflow state、telemetry、requirements 和 success metrics；输出 network/compute/workflow action，即 QoS、path、schedule 和 failure recovery。
2. **补 VIT 上方的 initial layer（TD-20、TD-21）。** 解析 YAML/XML workflow intent，维护多 workflow 状态，并把调度结果送入 VIT；scheduler 可作为 VIT 中的 process 运行，但目前不存在。
3. **实现 SciNet 相对 VIT 的五项增量（TD-22）。** schema/parser、multi-workflow queue/state store、deadline/priority/resource model、scheduling/optimization policy、result evaluation/feedback loop。
4. **先定义 scheduler 能看见和能控制什么（TD-27）。** 必须拿到 deadline、remaining data、task dependency、instrument/compute state；并能修改 rate、queue、route、resource allocation，再用 measurement 对照 success metric。



### 4. 无法归类

1. **Mininet vhost 的实现事实（TD-23）。** vhost 是宿主 process，主要隔离 network namespace，拥有独立 interface、IP 和 route。
2. **vhost 的代价（TD-24）。** 共享 filesystem、CPU 和 kernel；依赖无法真正隔离；resource/performance isolation 弱。
3. **何时使用 Docker（TD-25、TD-26）。** 只需独立网络身份时用 vhost；需要独立 filesystem/dependencies/process isolation 时用 Docker/Containernet，并把 container interface 接入 VIT subnet。
4. **NRP 是可选验证路线（TD-28）。** 把 endpoints 放到真实地理节点，用真实 WAN latency/path 与单机 VIT 对比；它不是构建或运行当前 VIT 的必要条件。
