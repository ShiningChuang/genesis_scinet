### 3. SciNet 与其他 Phase 1 工作的区分

有人询问 Kiran，Phase 1 是否还资助了其他 networking proposals。讨论中提到：

- 一个相关项目更偏向 Globus automated data movement，使用的是 “data movement” 而不是 “networking” 的表述；

因此，与会者建议本项目更明确地聚焦 networking infrastructure：一端是 Network Agent 与其他 agents 的接口，另一端是 Network Agent 与 SENSE 及实际网络基础设施的接口。会上把本项目所补的空白描述为：SENSE 不负责产生所有高层决策，本组需要研究由哪些更高层决定来驱动或填充所谓 Data Movement Manager 的行为。

### 4. 项目提供机制，不替科学实验作政策决定

讨论再次限定项目边界：本组要提供一个 framework，使实验的数据管理、软件和基础设施系统可以交互并作出调整；本组不替实验决定 policy、priority 或整体 success metric。

本组最终仍聚焦 Network Agent 和 networking components，但不能把网络孤立设计。必须理解其他资源 agents 在哪里、workflow-aware 到什么程度，以及网络决策需要看到多少 workflow 结构；这个程度尚待确定。

### 1. 为每个组件补充职责描述

一位与会者首先肯定整体逻辑 “very good”，随后要求为图中的每个 box 写清楚 description。目的不是增加图面文字本身，而是明确：

### 2. 站点不会保证公开全部信息

Harvey 指出，站点没有义务向外部 agent 提供图中设想的全部 queue、resource 或 timing 信息【K】。有些站点会提供较多信息，有些只提供最低限度的信息；Scheduling Agent 必须能根据站点实际返回的内容，对 workflow task schedule 作 best-effort 安排。

讨论据此区分了两类环境：

- **NRP 原型环境**：资源面向社区、较为 opportunistic，系统可以主动查询当前可用资源并选择；
- **真实大型实验环境**：实验已有自己的 site-selection 工具和政策【K】。本系统通常不能替实验选择处理站点，只能接受“数据从 A 到 B、任务在某站点处理”等约束，再确认该站点是否有足够资源、何时可开始及预计何时完成。

因此，Compute Agent 或 Scheduling Agent 中的 “site selection” 不能默认对所有 use cases 成立。更一般的表述应是：上游给出候选站点或固定站点，本系统在仍有选择空间时比较 offers；若没有选择空间，则用返回的可用性和 timing 安排 workflow 其余任务。

### 3. 网络可选择的范围也有限

讨论指出，系统可以选择 source 和 destination，但未必能指定完整物理路径。SENSE Orchestrator 与 OSCARS 会根据已有 circuits、拥塞情况或预先定义的 express paths 决定路径；“某处存在硬件”也不表示该硬件当前可供本 workflow 使用。

一位与会者建议把 Compute Agent 更接近地解释为：先询问“这个 workflow 的 candidate sites 是哪些”，然后在允许的候选集合中工作。若实验已声明站点可用，动态选择的重点可能转向网络条件：哪里有足够容量、哪里能得到带 bandwidth guarantee 的 virtual circuit。执行开始后，还必须由 instrument / site 状态确认进度；若站点没有达到先前给出的能力，系统要能与 Site-RM 或其他站点接口重新协商。

### 4. 必须明确 workflow 的时间尺度

与会者追问当前考虑的是必须立即运行的 just-in-time workflows，还是允许一个月完成的长期 workflows。汇报方解释，目前假定 workflow 有明确 deadline，目标是在多个 workflows 之间安排资源，使 deadline 前完成的 workflows 尽可能多，并没有把时间跨度固定为“立即”或“一个月”。

讨论补充，大规模 production 可能需要数周。此时系统不能只看最终 deadline，还需要 milestones 和合理 progress rate，以便在偏离时调整 priorities 或资源安排。汇报方同意，这正是设计必须支持修改的原因：真实实验的传输和计算不会只持续几毫秒。

### 5. 这套图适合作为职责协商的起点

讨论方认可，这些仍是初始 assumptions，未来 Compute / Instrument agents 很可能由其他人或其他团队实现。但当前草图至少提供了一个具体基础，可以开始讨论和协商“哪些 functions 属于谁”，而不是停留在抽象框架。

### 6. Local recovery 只能在可能时进行

对于 Site Agent 的 recovery 描述，与会者特别强调 **when possible**。如果本站能在不改变 global commitment 的情况下恢复，就应在本地处理；不能默认所有故障都能在站点透明解决。

有人用 SENSE 作类比：其较稳定的 Layer-2 overlay 与 Layer-3 flow management 可以在不同时间尺度变化，必要时也可能调整 Layer-2 topology。这只是会上用于说明“局部恢复与较大范围重配置可以分层”的类比，没有进一步落实为本项目的具体机制。

### 7. “Capacity publish” 要拆成静态能力与动态可用性

与会者指出，capacity 并非静态属性，真正影响调度的是随时间变化、且可能受 policy 和既有 allocation 影响的 availability。讨论提出两类信息：

- 类似 NetBox 的 inventory：有什么硬件、架构和接口；
- 实时或准实时 availability：当前哪些资源可用、可用到何时、能否预约。

因此，`capacity publish` 可能应改成 `capacity and availability`、`available resources` 或 “notification of availability”【K】。具体名称没有定稿。

John 分享了 NRP 的 resources 与 reservations 页面，并说明 NRP 资源视图可以给出 architecture、available cores、RAM、CUDA version 等信息，也包括 local-area network capacity；端点之间的 wide-area path 则应由 SENSE Orchestrator 提供。他称资源视图约每 10 分钟更新一次；该刷新频率是会上说法，本文未对实际接口作实测。

## 四、Sourabha 的 hierarchical telemetry 设计与讨论



### 1. Local detail 与 global summary 分层

Sourabha 将 telemetry 分成两个可见层次：

- Site Agent 可直接使用的本地细粒度状态；
- 供中央 Compute、Instrument、Network 等 agents 使用的 global / normalized state。

本地信息可以包括具体 node ID、GPU utilization、NIC port rate、instrument state，以及 Slurm、HTCondor 等本地 scheduler 的原生 job IDs。每个站点可以保留自己的 scheduler 和数据格式；设计不要求所有站点为了加入系统而改用同一套本地格式。

Site Telemetry Service 或等价的数据处理层负责从这些格式中抽取跨站可比较的 summaries。精细数据首先帮助 Site Agent 做局部恢复；中央层只接收完成调度决策所需的信息。

### 2. Workflow/task 与本地 job 的双向映射

Sourabha 提出维护如下映射：

```text
global workflow ID / task ID
        ↕
site scheduler job ID / node ID / resource state
```

这样既能从全局 task 找到具体 Slurm / HTCondor job，也能从本地故障或高利用率反查它影响哪个 workflow task。会上把这称为 resource-to-task 与 task-to-resource 的双向 mapping。

该 mapping 主要服务两个目的：

- Site Agent 能判断某个 job 延迟或网络故障是否可在本站修复；
- global agent 在摘要不足时，可以沿 reverse mapping drill down，取得更细的本站状态。

与会者认可“摘要不等于永久丢失信息”：global agents 平时在高层状态上工作，但必要时必须能够回查细节。

### 3. Local telemetry 示例需要补清设备语义

有人追问图中 `detector = busy` 的含义。汇报方解释，它只是一个 instrument detector 的状态例子，可能有 `busy` / `idle` 等属性；实际设施可以通过 EPICS process variables 暴露更丰富的字段。

对于 `free GPUs = 4`，讨论指出该值只有在知道设备配置时才有意义。Telemetry schema 以后必须说明设备类型和配置，例如 GPU type、server composition 与 NIC 关系，不能只给一个脱离上下文的总数。

图中的 `X1` 被解释为 transfer ID。系统可以将它对应到文件传输系统中的一次具体 transfer，并保留 start time、end time、完成百分比等细节。

### 4. Site Telemetry Service 的处理职责

Sourabha把该服务描述为 data-processing layer，候选职责包括：

- 将本地细粒度、自定义格式归一化为 global format；
- 按 GPU type 汇总数量，并提供 availability 的 start/end time；
- 对链路提供某个时间窗口内的可用带宽摘要；
- 维护 site job ID 与 workflow/task/transfer ID 的映射；
- 按规则发现 job delay 或 transfer 超时，并先通知 Site Agent；
- 若 Site Agent 无法处理，再把问题升级到 global resource agent。

这里的 alerting 被描述为 rule-based 机制；会议没有决定具体规则引擎、阈值或数据 schema。

### 5. Global summary 要围绕 decision relevance

“Decision-relevant summary” 指只向中央 agents 提供足以进行 scheduling / replanning 的有限指标，而不是复制所有 node- 和 port-level time series。会上以 aggregate GPU counts、aggregate rates、availability interval 为例。

讨论还尝试把 predicted finish 与实际 progress 的偏差、历史 completion-percentage time series、均值或标准差联系起来，用于估计 slack 或发现偏离。转写中的公式表述不完整，因此本文只记录目标：系统需要表达预计完成时间、实际进度及两者偏差，具体统计量尚未定稿。

### 6. 不能只设计 operation 之前的 telemetry

一位与会者指出，当前例子偏重 initial scheduling；同样重要的是运行期间持续回答：

- 当前是否仍按时推进；
- progress toward completion 是否足够；
- progress variation 是否正常；
- 超出本站 control band 时如何恢复或升级；
- 某个 site / device 最近的表现是否正常。

后一项既有 tactical 用途，也有 strategic 用途：近期表现不佳的资源可能暂时不应被选择；长期反复异常的 site element 则应被报告和修复。

Telemetry 还要支持来自 science side 的主动修改。例如实验可能要求“比原计划更早完成”，这会触发重新评估，而不仅是被动响应资源故障。汇报方承认目前对运行中修改的关注还不够。

## 五、Attribution 与现有工具的衔接

## 七、从 NRP 原型走向大设施的资源模式

John 提到在 Oak Ridge 等设施的 allocated node 上部署相同工具后，讨论转向一个更战略的问题：Genesis 若要实现动态 agentic orchestration，就不能完全依赖传统的“提交 proposal、数月后得到 allocation、再开始运行”的模式。

与会者认为，大型设施需要提供某种：

- opportunistic resource pool；或
- 能在短时间内申请和确认的 reserved resource pool。

会上举了“设施为项目长期保留一部分资源，例如 50%”的说明性例子，用来表达系统必须能预期某个资源池存在。这个数字没有获得设施承诺，也不是项目决策。

有人把该机制理解为 broker agent：接收 workflow，发现当前可用或可快速预约的 compute resources，从而减少每次运行前都单独申请长期 allocation 的需要。讨论强调，Genesis 本身隐含了更快速的资源获得机制；否则年度评审和数月 turnaround 无法支持运行时 orchestration。【K】

NRP、FABRIC、CloudLab 一类环境被用来与高度依赖人工委员会的传统设施流程作对比。与会者认为 Genesis 可能提供机会，让至少一部分资源突破原有模式。

## 八、Network alert 的逐层处理示例

Sourabha最后用 network port offline / down 说明 alert 如何从 local site 传播到 global scheduling。该流程是设计示例，不是已运行的 demo。

1. **记录事件**：Site Agent 或 telemetry layer 记录端口何时 down，以及相关状态。
2. **关联影响对象**：通过 attribution 找到对应 task ID、transfer ID 和 workflow。
3. **本地修复**：Site Agent 检查是否有连接到同一 switch 的冗余端口，且替代后仍满足 transfer requirement。
4. **更新 ETA**：若本地切换后仍能在原 finish time 前完成，则继续 transfer，并向 global Network Agent 发出 `repaired` notification，供全局追踪。
5. **升级为 at-risk / failure**：若本站无法满足 ETA，则通知 global Network Agent。
6. **全局网络重规划**：Network Agent 尝试选择 alternate path，并与 SENSE 协商；成功后建立新路径，通知 Site Agent 继续 transfer。
7. **升级到 workflow 层**：若 Network Agent 也无法解决，则交给 Scheduling Agent，由其决定调整 time slot、改变更高层 schedule，或在多个 transfers / workflows 之间重新安排优先级。

一位与会者评价这是一套适合继续讨论的 framework，很多 logical concepts 是正确的，但最终 implementation 可能不同。他举例指出，资源不足时不一定是“把其他 tasks 降低优先级”，也可能是提高受影响任务的优先级；只有在整体条件都很差时才需要更复杂的取舍。这被归为后续 implementation detail，会议没有定稿 priority policy。
