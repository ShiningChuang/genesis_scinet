## 读代码时注意三点

1. **所有消息共用一个基类** `Msg`（[schemas.py:20-21](../../src/lib/network_agent/schemas.py#L20-L21)）。它规定两件事：消息不可修改（frozen），未知字段一律拒绝。agent 之间走 JSON，坏消息在入口就被拦下，不会流进账本。
2. **校验只管"格式和自洽"，不管"能不能满足"。** 例如时间窗颠倒、没写时区、p95 早于 p50 都会被拒；但"50 TB 一分钟传完"能通过，因为它格式合法。容量够不够，是第 4 步 `find_placements` 的事。
3. `TransferQuote` **的自洽规则**（[schemas.py:137-150](../../src/lib/network_agent/schemas.py#L137-L150)）：feasible 必须带 offers 且不带原因；不可行时必须带原因且不带 offers。这样下游拿到结果就不用再猜。

## 为什么要把消息单独定义成 `Msg`

1. **消息的另一端不在我们的图里。** scheduling agent 可能是 Mariam 那边的框架、另一个进程，甚至另一个站点。双方约定的是 JSON 格式，不能依赖我们用不用 LangGraph。哪天换掉 LangGraph，或者对方根本不用它，消息格式都不用变。
2. **state 会经常改，消息格式要稳定。** 图里加个节点、加个中间字段（比如 `ledger_txn`），只改 state；对外的消息格式不受影响，对方不用跟着改。
3. **入口需要运行时校验。** LangGraph 常用的 `TypedDict` state 只是类型标注，运行时不检查，时间窗颠倒也照样流进节点。pydantic 在构造对象时就会报错，正好用来把守 agent 的入口。
4. **同一套消息要被多处复用。** 图 A、图 B（runtime 修复要调用 reserve/commit 这些指令），以及不经过图的测试和 demo 都会用到。放在 `schemas.py` 里，三处共用。

另外，LangGraph 也支持直接用 pydantic 模型当 state，但我们的 `Msg` 设成了不可变，而 state 本来就要在节点之间一步步合并更新，语义正好相反。所以我的安排是：state 用 `TypedDict`，负责"可变的工作记录"；`Msg` 负责"不可变的对外契约"。

> @model_validator(mode="after")     def *distinct*ends(self):         if self.src == self.dst:             raise ValueError("src and dst must differ")         return self 这段代码啥意思

这是 `TransferRequest` 的一条自定义校验规则：**源站点和目的站点不能是同一个。**

逐行看：


| 代码                               | 意思                                                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `@model_validator(mode="after")` | 告诉 pydantic，这个函数是一条校验规则。`mode="after"` 表示先按字段类型逐个检查、转换完，再调用这个函数，所以函数里拿到的 `self.src`、`self.dst` 已经是确定的字符串 |
| `def _distinct_ends(self):`      | 函数名可以随便取。前缀 `_` 是 Python 的习惯写法，表示内部使用，不需要外部调用                                                            |
| `if self.src == self.dst:`       | 检查两端是否相同                                                                                                 |
| `raise ValueError(...)`          | 不合法就抛错。pydantic 会把它包装成 `ValidationError`，对象创建失败                                                          |
| `return self`                    | 合法就把对象原样交回，创建成功。`after` 模式要求必须返回 `self`                                                                  |


为什么要单独写一个函数：字段的类型标注（如 `src: str`）只能检查**单个字段**自己，"两个字段之间的关系"只能靠这种函数检查。同一个文件里的其他 `model_validator` 也是这个道理，比如时间窗要求 `earliest_start < latest_finish`，offer 要求 `p50 ≤ p95`。

效果：

```python
TransferRequest(src="anl-dtn01", dst="ornl-esgf", ...)   # 创建成功
TransferRequest(src="anl-dtn01", dst="anl-dtn01", ...)   # ValidationError: src and dst must differ

```

为什么要拦这种请求：同一端点到自己不需要走网络，也就不该向 network agent 请求带宽，出现这种请求说明上游拆分有错。测试里对应 [test_step1_schemas.py](../../src/lib/network_agent/tests/test_step1_schemas.py) 中注释为 `# src == dst` 的那一行。

> 1. AwareDatetime是啥
> 2. @property     def start(self) -> datetime:         return self.rate_profile[0].start property是啥？

**1.** `AwareDatetime` **是什么**

`AwareDatetime` 是 pydantic 提供的类型，要求时间值**必须带时区**。

Python 的 `datetime` 分两种：

```python
datetime(2026, 10, 20, 9, 0)                       # naive：没有时区，"9 点"，但不知道是哪里的 9 点
datetime(2026, 10, 20, 9, 0, tzinfo=timezone.utc)  # aware：明确是 UTC 9 点

```

为什么非要时区：ANL 在芝加哥（UTC−5），ORNL 在田纳西（UTC−4），UCR 在加州（UTC−7）。一个跨站点请求如果只写"09:00"，三个站点会理解成三个不同的时刻，账本就会把容量记错时段。

所以 schema 里所有时间字段都用 `AwareDatetime`。没带时区的时间直接报错，测试里注释为 `# 无时区` 的那一行验证的就是这个。我们内部约定统一用 UTC。

**2.** `@property` **是什么**

`@property` 是 Python 内置的装饰器，**把一个方法伪装成属性**：调用时不用加括号，像读字段一样读它，但值是现算出来的。

```python
offer = a2()
offer.start      # 用了 @property：像字段一样读
offer.start()    # 如果不加 @property，就得这样调用

```

这里的逻辑是：offer 的开始时间，就是 `rate_profile` 第一段的开始时间。

为什么不直接把 `start` 存成一个字段：存了就会有两份数据，可能对不上。比如 `start=09:00`，而 `rate_profile` 第一段却从 12:00 开始，那该信哪个？用 `@property` 每次从 `rate_profile` 现算，就只有一个事实来源，不可能自相矛盾。

另一个附带效果：pydantic 只把字段序列化进 JSON，property 不会出现在消息里。对方收到 JSON 后，自己从 `rate_profile` 就能推出开始时间，消息里不需要重复。`QuoteResponse.admissible` 也是同样的写法。

> infeasible | unreachable有何区别？ all(ok)是啥意思 return all(ok) if self.mode == "all_or_nothing" else any(ok)啥意思

**1.** `infeasible` **和** `unreachable` **的区别**


| status        | 意思                             | 对应的 cause                                              |
| ------------- | ------------------------------ | ------------------------------------------------------ |
| `unreachable` | **到不了**：拓扑里 src 和 dst 之间根本没有路径 | `no_path`                                              |
| `infeasible`  | **路是通的，但满足不了要求**               | `no_capacity`、`beyond_horizon`、`below_min_useful_rate` |


区分它们是因为 scheduling agent 的应对完全不同。`unreachable` 时，等多久、放宽多少都没用，只能换数据源或换站点；`infeasible` 时，改窗口、降速率或者晚点再问，都可能变成可行。

顺带说一个不足：目前 schema 没有强制这个对应关系，`status="unreachable"` 配 `cause="no_capacity"` 也能通过校验。要不要在 `TransferQuote` 的校验里加上这条约束？加了更严格，代价是多几行代码。

**2.** `all(ok)` **是什么意思**

`all` 和 `any` 是 Python 内置函数，作用于一串 True/False：

```python
all([True, True, False])   # False：全部为 True 才返回 True
any([True, True, False])   # True：只要有一个 True 就返回 True

```

上一行先算出 `ok`：

```python
ok = [r.status == "feasible" for r in self.results]
# 比如三条传输的结果是 feasible、feasible、infeasible
# → ok = [True, True, False]

```

**3.** `return all(ok) if self.mode == "all_or_nothing" else any(ok)` **是什么意思**

这是 Python 的条件表达式，`A if 条件 else B` 的意思是"条件成立取 A，否则取 B"。等价于：

```python
if self.mode == "all_or_nothing":
    return all(ok)   # 整组接受：每条都可行才算可接纳
else:                # best_subset
    return any(ok)   # 挑子集：至少有一条可行就算可接纳

```

用上面的例子 `ok = [True, True, False]`：

- `all_or_nothing` → `False`：有一条不行，整个 workflow 不接纳。对应 slide 17 的 "if one transfer cannot fit, W is not admitted"。
- `best_subset` → `True`：先接纳能做的两条。

> 1. 为什么network agent需要class EndpointBinding(Msg):这个message？ 2. class Commitment(Msg):，为什么一个commitment只对应一个transfer id，不应该是transfer list吗？

**1. 为什么需要** `EndpointBinding`

**因为预留路径的是 network agent，真正搬数据的是 WMS。WMS 必须知道该从哪里发、往哪里发，数据才会走上预留好的那条路径。**

slide 5 原话："The agent reserves the path; the WMS still moves the bytes."

SENSE 建好的 circuit 是一条专用的二层通道，只服务特定的 VLAN 和接口。如果 WMS 照常用默认地址发数据：

```
预留了：anl-dtn01 ──[VLAN 3001, eth1, 100 Gbps 专线]──► ornl-esgf
WMS 照常发：anl-dtn01 ──[普通路由，共享带宽]──► ornl-esgf      ← 预留白做了

```

带宽是预留了，但数据没走上去。slide 19 说的 "without the binding the bytes take the default route" 就是这个意思。

所以 commit 成功后，network agent 要把"用哪对端点、哪个 VLAN、哪个接口"交回去：

```
EndpointBinding(transfer_id="T1", src_uri=..., dst_uri=..., vlan=3001, interface="eth1")
   → scheduling agent 放进 ExecutionPlan.endpointBindings[]（slide 5）
   → WMS 用它配置传输工具

```

**2. 为什么一个** `Commitment` **只对应一个 transfer**

因为后面所有环节都按单条传输来判断和处理，一个 commitment 对应一个 transfer，粒度正好对得上：


| 环节             | 为什么要按单条传输                                                                  |
| -------------- | -------------------------------------------------------------------------- |
| Runtime 判断能否赶上 | 每条传输有自己的 `latest_finish`。slide 20 的 R2 要求逐个 commitment 重算 p95，再和各自的截止时间比   |
| 上报 `at_risk`   | 一条传输受影响，只报这一条。如果一个 commitment 装着一组传输，一条出问题就得整组上报，scheduling agent 也分不清该改哪条 |
| 修改与释放          | T1 传完就释放 T1 的容量，不必等同组的 T2、T3                                               |
| Learning 关联    | slide 20 的 L1 用 `commitmentRef` 做关联键，一条传输记录对一个承诺，才能算出"实际速率 / 预留速率"         |


**"一组"在别的层次表达，不需要塞进 commitment：**

```
ReserveRequest(offer_ids=[a2, b1, c3])    一次预留一组（整个 bundle 原子地预留）
        ↓
CommitAck.commitments = [c_T1, c_T2, c_T3]    一次确认返回一组 ← 你说的 list 在这里
        ↓
Circuit C1 上承载 c_T1、c_T3，Circuit C2 上承载 c_T2    多个 commitment 共用一个 circuit（slide 24）
        ↓
每个 commitment 都带 workflow_id    按 workflow 归组

```

反过来还有一种情况：第 8 步做多路径增容时，一条可拆分的传输可能分到两条路径上，变成**一个 transfer 对应多个 commitment**，每条路径一个。所以真正固定的规则是"一个 commitment = 一条传输落在一个 circuit 上的一个承诺"，而不是"一个 commitment = 一组传输"。
