## 读代码时注意四点

**1. 链路拆成两个方向**（[topology.py:62-66](../../src/lib/network_agent/topology.py#L62-L66)）

链路是全双工的，A→B 占满不影响 B→A。所以每条物理链路拆成两条有向链路，id 形如 `L2:esnet-chi>esnet-atl`。一条路径就是这些 id 组成的元组。

**2. 账本按链路记，不按站点对记**

[test_shared_link_couples_paths](../../src/lib/network_agent/tests/test_step2_topology_ledger.py) 演示了原因。主路径和绕行路径共用第一跳 L1。在主路径上预订 80 Gbps 后，绕行路径只剩 20，而且账本能指出瓶颈是 L1。按站点对记账就看不出这一点。

**3. "容量在哪里扣减"**（[ledger.py:122-138](../../src/lib/network_agent/ledger.py#L122-L138)）

这正是 KK 追问的地方，答案是 `pending()`：

```
pending()  ──成功──► confirm()  ──用完──► release()
   │
   └─(如 SENSE 失败)──► rollback()

```

- **检查与写入是原子的**：先查完路径上每条链路、每个时间槽，全都够了才写入，任何一处不够就什么都不写。测试 `test_insufficient_is_atomic` 验证了这一点。外面还套了一把锁，防止两个请求同时抢同一份容量。
- **不够时会说清原因**：抛出的 `InsufficientCapacity` 带着"哪一跳、哪个时段、缺多少、被谁挡住"。被谁挡住分两种：被我们自己的预订挡住（`own_commitment`），还是被外部流量挡住（`foreign_traffic`）。第 4 步的 offer 和第 7 步定位拥塞都会用到这些信息。

**4. 时间槽有量化误差**

13:00–13:07 只用了 7 分钟，也会占满 13:00 这一整个 15 分钟槽。这就是 slide 23 说的槽越大浪费越多。测试 `test_slide23_table` 原样复现了 slide 23 的整张表：observed 100,100,100,40,40,40，own 40,40,0,0,25,25，available 60,60,100,40,15,15。

## 1. `LinkSpec`、`TopologySpec`：外部给的拓扑描述（第 15–41 行）

对应 [helpers.py](../../src/lib/network_agent/tests/helpers.py) 里 `TOPO` 那种写法：

```python
{"id": "L2", "a": "esnet-chi", "b": "esnet-atl", "capacity_gbps": 100}

```

- `LinkSpec` 描述**一条物理链路**，只写两端 `a`、`b`，不分方向。写拓扑的人只需要描述"哪两个点之间有一根线"。
- `TopologySpec` 是整张图：节点列表加链路列表。
- 第 30–41 行的校验管的是**字段之间的关系**，和你之前问的 `_distinct_ends` 是同一种写法：
  - 第 32、34 行：节点 id 和链路 id 不能重复。第 32 行的写法是：转成 `set` 会去重，长度变了就说明有重复。
  - 第 37 行：链路两端不能是同一个点（自环）。
  - 第 39 行：链路两端都必须是已声明的节点。`<=` 用在集合上表示"是子集"，即 {a, b} 都在 nodes 里。

用 pydantic 是因为这部分数据**来自外部**（yaml 配置），需要在入口检查。

## 2. `DirectedLink`：一个方向的链路（第 44–50 行）

```python
DirectedLink(id="L2:esnet-chi>esnet-atl", link_id="L2", src="esnet-chi", dst="esnet-atl", capacity_gbps=100)

```

这里用普通 `dataclass` 而不是 pydantic，因为它是第 63 行由我们自己的代码生成的，数据已经可信，不需要再校验。`frozen=True` 表示创建后不能修改。

第 53 行 `Path = tuple[str, ...]` 是**类型别名**，只是给"有向链路 id 组成的元组"起个名字，让后面的代码更好读。`...` 表示长度不定。

## 3. `Topology.__init__`：拆方向、建邻接表（第 57–65 行）

它准备好两张表：


| 属性           | 内容                       | 用途            |
| ------------ | ------------------------ | ------------- |
| `self.links` | 有向链路 id → `DirectedLink` | 账本按 id 查容量    |
| `self._out`  | 节点 → 从这个节点**出发**的有向链路    | 找路径时查"从这里能去哪" |


关键是第 62 行：每条物理链路循环两次，正反方向各生成一条有向链路。拿 L2 来说：

```
L2(esnet-chi, esnet-atl)
  → L2:esnet-chi>esnet-atl   放进 _out["esnet-chi"]
  → L2:esnet-atl>esnet-chi   放进 _out["esnet-atl"]

```

两个方向各有一份完整的 100 Gbps，对应全双工。

第 67–69 行的 `from_dict` 是便捷入口：先用 `TopologySpec` 校验 dict，再构造。`@classmethod` 表示它通过类本身调用（`Topology.from_dict(...)`），不需要先有一个对象。

## 4. `paths`：找候选路径（第 71–90 行）

用的是**深度优先搜索**：从 src 出发，一条路走到底，到了 dst 就记下来，然后回头试别的岔路。

- 第 76–78 行：未知节点直接报错。
- 第 81 行的 `walk` 定义在 `paths` 内部，所以能直接用外层的 `dst` 和 `found`。它带三个参数：
  - `node`：当前走到哪；
  - `visited`：已经经过的节点，用来防止绕圈；
  - `path`：已经走过的有向链路。

用 demo 拓扑跑一遍 `paths("anl-dtn01", "ornl-esgf", k=3)`：

```
anl-dtn01 ─L1→ esnet-chi ─┬─L2→ esnet-atl ─L3→ ornl-esgf   ✓ 记下（3 跳）
                          ├─L4→ esnet-nash ─L5→ esnet-atl ─L3→ ornl-esgf   ✓ 记下（4 跳）
                          └─L1→ anl-dtn01   ✗ 已访问过，跳过（第 86 行）

```

- 第 87 行 `visited | {d.dst}`、`path + [d.id]` 每次都生成**新的**集合和列表，而不是在原来的上面修改。这样一条岔路走完回头时，不需要手动把加进去的东西删掉，代码更不容易出错。
- 第 90 行：按 `(跳数, 链路 id)` 排序后取前 k 个。跳数少的排前面；跳数相同时按 id 排，保证每次结果顺序都一样，测试才可重复。

**局限（文档字符串第 74 行写明了）：** 这种做法会把所有无环路径都找出来，路径数随拓扑规模指数增长。demo 只有 6 个节点没问题，拓扑变大要换 Yen 算法，它能直接只找最短的 k 条。

> [ledger.py](../../src/lib/network_agent/ledger.py) 可以分四块读：**存了什么 → 时间怎么切成槽 → 怎么读 → 怎么写**。下面用一个贯穿的例子：`slot_seconds=900`（15 分钟），`horizon_seconds=86400`（24 小时），构造时传入 `origin=09:05`。



## 1. 存了什么（第 27–70 行）

**两个异常类**


| 类                                 | 什么时候抛                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------- |
| `OutOfHorizon`（第 27 行）            | 时间落在账本覆盖范围之外。它继承自 `ValueError`，所以调用方可以把它当成"参数不合法"来统一处理                            |
| `InsufficientCapacity`（第 31–38 行） | 容量不够。它不只是一句报错文字，还把"哪条链路、哪个时段、要多少、有多少、被谁挡住"作为属性带出去，后面的代码可以直接读，比如 `e.value.link_id` |


**两个小数据结构**

- `Observation`（第 41–45 行）：一个观测值，带来源和采样时间，比如 `(100, "topology", 09:00)`。这就是 slide 12 说的每个数都带出处，日后可以追问"这个 40 Gbps 是谁、什么时候说的"。
- `Booking`（第 48–53 行）：一笔我们自己的预订。`slot_gbps` 是"槽号 → 占用速率"，比如 `{12: 100, 13: 100, ..., 16: 100}`；`state` 是 pending 或 confirmed。

**账本本体** `CapacityLedger`**（第 56–63 行）**

前三个字段由调用方传入，后三个带 `field(init=False)`，表示不由构造函数传入、由内部自己建：


| 字段          | 内容                                   |
| ----------- | ------------------------------------ |
| `_observed` | 每条有向链路一个列表，长度为槽数，存每个槽的 `Observation` |
| `_bookings` | 预订 id → `Booking`                    |
| `_lock`     | 一把线程锁，写操作时用                          |


注意**账本没有存 own 和 available**，只存 observed 和预订本身。own 每次都从预订现算，available 再由 observed − own 算出。这和你之前问的 `@property start` 是同一个思路：只保留一个事实来源，就不会出现两份数据对不上。代价是每次查询都要遍历所有预订，demo 规模下无所谓。

`__post_init__`**（第 65–70 行）**

dataclass 自动生成的构造函数执行完之后，会调用这个方法做两件事：

1. **对齐 origin（第 67–68 行）。** 把 09:05 往回拨到最近的槽边界 09:00。`epoch % slot` 是"距上一个 15 分钟整点过了多少秒"，减掉它就对齐了。对齐是为了让所有槽都落在整 15 分钟上，便于阅读和对表。
2. **用拓扑容量填满 observed（第 69–70 行）。** 每条链路的 96 个槽都填 `Observation(100, "topology", 09:00)`。`[x] * n` 是把同一个对象重复 n 次，因为 `Observation` 不可变，共用同一个对象没有问题。



## 2. 时间槽（第 74–92 行）

```
槽号:    0      1      2     ...    95
       09:00  09:15  09:30  ...  次日 08:45  │ horizon_end = 次日 09:00

```

- `n_slots` 是 86400 // 900 = 96；`slot_start(i)` 是第 i 槽的开始时间；`horizon_end` 是第 96 槽的开始，即账本的尽头。
- `slots_covering(start, end)`（第 85–92 行）把一段时间换算成它碰到的槽号，这是最关键的换算。以 a2 的 12:00–13:07 为例：

```
first = (12:00 − 09:00) / 900 秒 = 10800 / 900 = 12        向下取整
last  = (13:07 − 09:00) / 900 秒 = 14820 / 900 = 16.47 → 17  向上取整
→ range(12, 17) = 槽 12, 13, 14, 15, 16

```

13:07 只用到槽 16（13:00–13:15）的前 7 分钟，但整个槽都会被占用，这就是量化误差。

第 91 行的 `-(-x // slot)` 是 Python 里向上取整的常用写法：对负数做向下取整，再取反，结果就是向上取整。超出账本范围的时间在第 87 行就会抛出 `OutOfHorizon`。

## 3. 读（第 96–110 行）

三个函数逐层往上算：

```
observed(link, i)   直接查表                       → 100
own(link, i)        把经过这条链路的预订在第 i 槽的占用加起来 → 40
available(link, i)  max(0, observed − own)           → 60

```

- 第 100 行 `own` 的条件 `if link_id in b.path` 很关键：一笔预订占用的是它**路径上的每一条链路**，所以只要这条链路在路径里，就要算上。
- 第 103 行的 `max(0, ...)` 处理观测值变小的情况。比如我们已经预订了 40，后来观测降到 30，30 − 40 是负数，可用容量记为 0，不会出现负数。
- 第 107 行的 `path_available` 返回路径在某个槽的可用容量，等于沿途各链路的最小值，即木桶效应。写法上是对 `(容量, 链路 id)` 这样的二元组取 `min`：先比容量，所以顺带就拿到了瓶颈是哪一跳。



## 4. 写（第 114–161 行）

`set_observed`（第 114–119 行）把一段时间内的观测值替换成新的采样，第 3 步接 telemetry 后开始使用。

`pending` **是整个文件的核心**（第 121–137 行），分三段：

**第一段（第 123–126 行）：把速率曲线换算成"槽号 → 速率"。** 这一段在加锁之前做，因为它只是计算，不读写共享数据。第 126 行处理一种边界情况：同一笔预订的两段相邻 segment 落在同一个槽里，比如 12:00–12:40 是 50、12:40–13:00 是 80，它们都碰到槽 14。这时取较大的 80，而不是相加成 130，因为这两段是先后发生的，同一时刻不会同时占用。

**第二段（第 130–136 行）：先全部检查，不写任何东西。** 逐条链路、逐个槽检查容量够不够，只要一处不够就抛异常退出。第 135 行判断是被谁挡住的：

```
observed ≥ need → 如果没有我们自己的预订，本来是够的 → own_commitment
observed < need → 就算我们一笔预订都没有，也不够     → foreign_traffic

```

这个区分以后会交给 scheduling agent：`own_commitment` 意味着可以和我们自己别的预订协调，`foreign_traffic` 则说明是外部流量占用了容量。

**第三段（第 137 行）：全部检查通过，才写入一行。** "全查完再写"就是原子性：不会出现前两跳已经扣了容量、第三跳失败、前面又忘了退回的情况。

**整个检查和写入都放在** `with self._lock:` **里（第 127 行）。** 如果两个请求同时进来，没有锁就可能都查到"还剩 60"，然后各扣 50，结果超额预订。加锁后，同一时刻只有一个请求在检查和写入。

**状态转换（第 139–161 行）：**

```
          pending() 写入
              ↓
          [pending] ──confirm()──► [confirmed] ──release()──► 删除
              │
              └──rollback()──► 删除

```

每个操作都先调用 `_require` 检查"这笔预订存在，并且处于正确的状态"。这样可以挡住不合法的操作，比如对已经 confirmed 的预订做 rollback，或者 confirm 一个不存在的 id。

`confirm` 只是改了状态，available 不会变化，因为 pending 时容量已经扣过了。在第 4 步的 quote 看来，pending 和 confirmed 占用容量的效果完全一样，区别只在于 pending 还可以 rollback。

> ledger的origin是啥

`origin` **是账本时间轴的起点，也就是第 0 个时间槽开始的时刻。** 所有槽号都从它算起：

```
origin = 09:00
槽号:     0       1       2     ...     95
        09:00   09:15   09:30   ...  次日 08:45
         ↑
       origin                          horizon_end = origin + 24h = 次日 09:00

```

第 i 槽的开始时间就是 `origin + i × slot_seconds`，见 `slot_start()`，第 82–83 行。

## 它从哪来

创建账本时由调用方传入，通常就是"现在"。传进来后会向下对齐到最近的槽边界（第 67–68 行）：

```python
CapacityLedger(topo, cfg, origin=09:05)   # 传入 09:05
ledger.origin                             # → 09:00

```

对齐的原因是让每个槽都落在整 15 分钟上（09:00、09:15……），和 slide 23 表头的时间一致，查表时也不会出现 09:05–09:20 这种零碎的格子。

## 它决定了账本能回答什么

账本只覆盖 `[origin, horizon_end)` 这一段：

- **早于 origin 的时间**不在表里，因为已经过去了，不需要预订。
- **晚于 horizon_end 的时间**也不在表里，这时会抛出 `OutOfHorizon`，对外就是你之前问的 `beyond_horizon`。

## 目前的局限

origin 现在是**固定的**：账本建好后，origin 就停在 09:00 不动。实际运行时时间一直在走，到了下午，上午的槽已经没用了，而次日上午之后的时段又不在表里。

第 4 步要给账本加一个推进操作，对应 slide 23 的 "advance the frontier"：

```
到 12:00 时推进：origin 09:00 → 12:00
   丢掉 09:00–12:00 的 12 个过期槽
   在末尾补上次日 09:00–12:00 的 12 个新槽

```

推进后，原来的"第 12 槽"会变成"第 0 槽"。所以预订里存的槽号也要跟着平移，这一点第 4 步实现时要注意。

>  解释这行代码，包括每个标识符：return sum(b.slot_gbps.get(i, 0.0) for b in self._bookings.values() if link_id in b.path)

这行代码算的是：**第 i 槽里，所有经过** `link_id` **这条链路的预订一共占用了多少 Gbps。**

## 逐个标识符


| 标识符                    | 是什么                   | 这里的含义                                                           |
| ---------------------- | --------------------- | --------------------------------------------------------------- |
| `return`               | Python 关键字            | 把后面算出的值作为函数 `own()` 的结果返回                                       |
| `sum(...)`             | 内置函数                  | 把括号里产生的一串数加起来；如果一个数都没有，结果是 0                                    |
| `self`                 | 方法的第一个参数              | 当前这个账本对象                                                        |
| `self._bookings`       | 账本的字段，一个 dict         | 预订 id → `Booking`，例如 `{"b1": Booking(...), "b2": Booking(...)}` |
| `.values()`            | dict 的方法              | 只取 dict 的值（各个 `Booking` 对象），不要 key                              |
| `for b in ...`         | 循环                    | 依次取出每笔预订，命名为 `b`                                                |
| `if link_id in b.path` | 过滤条件                  | 只保留路径经过这条链路的预订                                                  |
| `link_id`              | `own()` 的参数           | 要查询的有向链路，比如 `"L2:esnet-chi>esnet-atl"`                          |
| `in`                   | 成员运算符                 | 判断 `link_id` 是否在 `b.path` 这个元组里                                 |
| `b.path`               | `Booking` 的字段         | 这笔预订走的路径，即有向链路 id 的元组                                           |
| `b.slot_gbps`          | `Booking` 的字段，一个 dict | 槽号 → 该槽的占用速率，例如 `{0: 40, 1: 40}`                                |
| `.get(i, 0.0)`         | dict 的方法              | 取槽号 i 对应的值；**这笔预订如果没占用槽 i，就返回默认值 0.0**，不会报错                     |
| `i`                    | `own()` 的参数           | 要查询的槽号                                                          |


## 结构：生成器表达式

`sum(` 和最后的 `)` 中间这一段叫**生成器表达式**，格式是：

```
(  要产出的值  for 变量 in 可迭代对象  if 条件  )

```

它等价于下面这个普通写法：

```python
total = 0
for b in self._bookings.values():   # 遍历每笔预订
    if link_id in b.path:           # 只看经过这条链路的
        total += b.slot_gbps.get(i, 0.0)   # 加上它在槽 i 的占用，没占用就加 0
return total

```

一行写法更紧凑，每算出一个值就交给 `sum` 累加，不会先把所有值存进一个列表。

## 例子

账本里有三笔预订，查询 `own("L2:esnet-chi>esnet-atl", 0)`，即 L2 在 09:00 槽的占用：


| 预订  | path 是否经过 L2   | slot_gbps        | `.get(0, 0.0)` | 计入         |
| --- | -------------- | ---------------- | -------------- | ---------- |
| b1  | ✓（主路径）         | `{0: 40, 1: 40}` | 40             | 40         |
| b2  | ✓（主路径）         | `{4: 25, 5: 25}` | 0.0（不占槽 0）     | 0          |
| b3  | ✗（绕行路径，不经过 L2） | `{0: 30}`        | —              | 被 `if` 过滤掉 |


结果：40 + 0 = **40**。

b3 虽然在槽 0 占用了 30，但它不走 L2，所以不算进 L2 的占用。这正是按链路记账的意义：每条链路只算真正经过它的流量。
