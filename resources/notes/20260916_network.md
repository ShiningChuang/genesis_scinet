## 1. Overview

### 1.1 一句话定位

**Network agent 把 scheduling agent 的需求（多少字节、在什么时间窗里送到）变成一个可兑现的承诺（几点能到、有多大把握），并在执行中维持住它。它是全系统唯一碰 SENSE 的模块。**

它讲*网络语言*：容量、时隙、电路、带宽、路径。它不知道 DAG，也不知道 deadline 背后的科学含义，只知道 scheduling agent 给它的时间窗 `[earliest_start, latest_finish]`。

分工的依据是：**谁看得见容量曲线，谁就决定带宽 × 时长的形状**。scheduling agent 发需求，不发方案；可行性由 network agent 负责，取舍归 scheduling agent。

### 1.2 主线：从 SENSE 的数到可兑现的承诺，中间隔着两层

Network agent 做的所有事，都围绕"SENSE 给的数"和"能对上层承诺的数"之间的差距展开。

```
SENSE 说：这条路还能预约 100              reservable     （observed 层）
  − 我们自己已经占掉的                     allocated      （own 层）
  = 还能分给新承诺的                        available      ← 第一层：账本减法
  × 端系统实际能跑到的比例                                  ← 第二层：achievability 折算
  = 承诺给上层的完成时间所依据的速率          achievable     → predicted_finish{p50, p95}
```

- **规划期**：用这两层把需求变成 offer。减法保证不超卖，折算保证不空头承诺。
- **运行期**：遥测不断检验这两层还成不成立。observed 下降，说明减法的被减数变了；实测吞吐偏低，说明折算系数变了。任何一个变化让 `predicted_finish` 越过 `latest_finish`，就要修或上报。
- **跨 run**：把历次"预约多少 vs 实际跑到多少"配对，让折算系数越来越准。系数越准，预留的安全余量越少，锁死的容量也越少。

`reservable ≠ available ≠ achievable`：三者混用是这个领域最常见的错误来源。所以账本里每个数字都要带语义标注（§2.4）。

### 1.3 三个阶段、十个任务

字母取自各阶段：**Q**uote（规划期）、**M**onitor（运行期）、**L**earning（跨 run，与 slides 一致）。L1–L3 与 scheduling agent 的 L1 同名，口头或跨页引用时加上 agent 名。

**底座**（三个阶段共用）

| ------ | --------------------------------------------------------------------------------------- | --- |

## 2. 底座：容量账本（对应已有第 11 页）



### 2.1 为什么必须有状态

"每次 quote 现问 SENSE"行不通：

1. **SENSE 只有点查询**：给一个时间窗，返回一个数。没有曲线，也没有批量接口。
2. **问"最早什么时候能开始"要在时间轴上二分搜索**，一次 quote 要打几十个 SENSE 请求。
3. **延迟预算**：0908 的 gate 要求 agent 协调 p50 < 200 ms。
4. **最致命的一条**：同一个 bundle 里的几个 transfer 会互相占用同一段容量。放完第一条之后，SENSE 并不知道你刚安排了它，第二条的查询结果就是错的。你只能在本地扣掉再算——那一刻你已经在建账本了，只是建在临时变量里、用完就扔。



### 2.2 两层，信任等级不同

```
observed 层  ← SENSE / twin：这条路"外界"还剩多少
             语义 = reservable，含非 SciNet 流量的影响
             会过期、有误差、要主动刷新

own 层       ← 我们自己 hold / commit 出去的每一笔
             语义 = allocated
             精确、即时、无需查询

available(t) = observed(t) − Σ own(t)
```

**这条减法必须在本地做。** 刚 commit 的预约，SENSE 的可用量视图可能还没反映出来；依赖它反映，就会把同一段容量卖两次。KK 点名要求的"并发调度总需求不超过 capacity"，靠的是这条减法，不是 SENSE。

【已定，暂定】按 (src, dst) 建账，时间切成离散时隙：

```
  ANL→ORNL            09:00  09:15  09:30  09:45  10:00  10:15   (Gbps)
  observed              100    100    100     40     40     40
  own (hold+commit)      40     40      0      0     25     25
  ──────────────────────────────────────────────────────────
  available              60     60    100     40     15     15
```

quote 就是在这张表上找放置。"最早什么时候能开始"是查表，不是调 SENSE。

### 2.3 observed 层怎么建：用有限次点查询拼出曲线

SENSE 的查询是"给一个时间窗 → 返回**整段都能保证**的容量"，也就是这段时间里的瓶颈值：

```
查 [09:00, 10:30] → 40        ← 整段取最小，看不到 09:00–09:45 其实有 100
查 [09:00, 09:45] → 100
```

一次查询把曲线压成一个数，所以只能**把窗口切开反复问**。6 小时按 15 分钟粒度就是 24 次。

**一次查询实际怎么发**（0911 p10 的核验）：

```
GET  /instance                                   → 领一个新的 siUUID
POST /instance/{siUUID}?sync=true&proceed=false  → 提交带 queries[] 的 ServiceIntent
读   $.queries[*].results[*].bandwidth           → bit/s，÷1e6 得 Mbps
```

```jsonc
{ "ask": "total-block-maximum-bandwidth",
  "options": [ { "name": "Connection 1", "start": "now", "end-before": "+1h" } ] }
```

- `proceed=false` 是关键：只计算、只回答，不下发配置。
- 查询**顺带算了一条可行路径**，所以它同时回答了"有没有路"，这就是 quote 里 `status: unreachable` 的判据来源。
- **代价比想象的高一档**：查一次 = 领一个 siUUID + POST 一个 intent，不是一次轻量 GET。这让"近期密、远期疏"从优化变成必需，也可能逼我们把时隙放粗。

**进账本的格式**：

```jsonc
// CapacitySample
{ "src": "anl-lcrc", "dst": "ornl-olcf",
  "window": ["…09:00Z", "…09:15Z"],
  "maxReservableGbps": 100,          // 整段窗口的瓶颈值
  "queriedAt": "…08:55Z",
  "validUntil": "…09:05Z",           // SENSE 不给，由我们的刷新策略定
  "source": "sense-query" }          // sense-query | twin
```

**三个参数进 config**：


| 参数      | 含义           | 权衡                                   |
| ------- | ------------ | ------------------------------------ |
| horizon | 账本往未来看多远     | 跟 workflow deadline 的典型跨度挂钩          |
| slot 粒度 | 一个时隙多长       | 量化误差 vs 装箱复杂度；"粒度 vs 调度质量"本身是个现成的小实验 |
| 刷新策略    | 何时、在哪些时隙重新采样 | 查询代价 vs 数据新鲜度                        |


**刷新策略的三个动作**（【倾向】v1 规则）：


| 动作      | 做什么                         | 频率                    |
| ------- | --------------------------- | --------------------- |
| 推进前沿    | 在 horizon 边缘加新时隙，丢掉已过期的     | 随时钟滑动                 |
| 重采样已有时隙 | 重新查表里已有的时隙，因为别人也在占容量        | 近期密、远期疏（如 5 min 刷新近期） |
| 事件触发    | commit 前核对一次；`at_risk` 之后重查 | 按需                    |




### 2.4 每个数都带 provenance

```
Fact { value,
       semantics: physical | reservable | allocated | measured | predicted,
       source:    sense-query | twin | manifest | probe | history | assumption,
       timestamp, valid_until, confidence }
```

理由：`reservable ≠ available ≠ achievable`。标注之后，"哪些是 SENSE 给的、哪些是我们假设的"可以直接枚举出来，这正是 KK 要的那张缺口表。

**两个语义陷阱**（0904 核验）：

- `ServiceState: STABLE` **只说明配置稳定，不说明性能达标**。把它当性能证据，账本会把一条烂路当好路。
- discovery 里的 `capacity` 字段没有单位、时间戳和语义分类，**不能直接当 reservable 用**。



### 2.5 commitment 与 circuit：账本的第二个维度

**一个 transfer 不等于一条电路**（详见 §3.3）。所以账本要记两套时间轴：


| 层            | 记什么                  | 对谁负责             |
| ------------ | -------------------- | ---------------- |
| commitment 层 | 谁承诺了什么、什么时候、多少带宽     | scheduling agent |
| circuit 层    | 哪些电路开着、各自剩多少余量、什么时候拆 | SENSE            |




### 2.6 必须诚实承认的信息边界

**SENSE 不暴露内部 node-link graph，也读不回完整有序的 route**（0904 §5.2.1–5.2.2）。所以账本只能按 (src, dst) 建，不能按 link 建。

后果：A→B 和 C→D 可能共用一条看不见的瓶颈链路。账本上两笔都算得开，实际会撞车。

这不是能修的 bug，是信息边界。三道兜底：

1. observed 层打 **safety margin**（初期保守常数，之后由历史校准）
2. commit 前做一次 **SENSE 核对**（`propagate` 天然是这个核对点）
3. 撞了就靠运行时 `at_risk` 兜底

**这个盲区可以做成实验变量**：digital twin 里我们知道真实拓扑，可以量化"按 (src, dst) 建账导致多少次误判"。

## 3. 规划期

三步对应 SENSE 的两阶段接口：quote 只问不占，hold 占住不下发，commit 真正下发。

### 3.1 Q1 quote：在账本上找放置



#### 收到什么

```
QuoteRequest:
  bundle: [TransferRequest]
  mode:   all_or_nothing | best_subset

TransferRequest:
  id, workflow_id, priority, src, dst,
  bytes (+is_estimate), window: [earliest_start, latest_finish],
  divisible, min_useful_rate
```

各字段对 network agent 的意义：


| 字段                      | network agent 怎么用                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| `bytes` + `is_estimate` | 估计值 → `predicted_finish` 多留余量、区间放宽；之后 `refine` 换成真值时增量重算                                   |
| `window`                | 放置必须落在里面；p95 越过 `latest_finish` 的放置不给                                                      |
| `divisible`             | 可分 → 可以在时间轴上见缝插针；不可分 → 只能整块找位置                                                             |
| `min_useful_rate`       | 速率下界，避免给出"技术可行但没意义"的 offer（占 5 Gbps 传三天）                                                   |
| `mode`                  | `all_or_nothing`：一条排不下整批 infeasible，用于 workflow admission；`best_subset`：尽量排、告诉我哪些不行，用于探索瓶颈 |




#### 怎么找放置（纯确定性，不用 LLM）

- **单条、恒定速率**：对每个候选起始时隙，速率上界 = 该跨度内 `min(available(t))`；而跨度又取决于速率。所以在 (start, rate) 上做一维扫描 + 二分，O(时隙数 × log)。
- **bundle 内多条**：【已定】v1 贪心，按窗口余量从紧到松逐条放，放一条就在本地扣掉一条。
- **速率形状**：【已定】v1 常数速率（一个 transfer 一个带宽值，直接对应 SENSE primitive），但协议字段 `rate_profile` 留成 list，以后能升级到分段时变。代价要清楚：常数速率就是 KK 批评 DMM 的"每个 flow 一次性固定分配"，统计复用的入口留在电路层（§3.3）。



#### 承诺按 achievable 算，不按 reservable 算

放置用的是 **reservable 速率**（账本上占多少），但 `predicted_finish` 必须用 **achievable 速率**（实际能跑多少）来算。两者之间就是 achievability model（§5.2）。

**例子**：沿用 §2.2 的账本，一个 9 TB（72,000 Gb）的传输，窗口 [09:00, 10:30]。这对站点历史上 achievable / reserved 的 p50 = 0.6、p95 = 0.45。


| 放置         | 预约速率 | 按 reservable 算 | 按 p50 achievable 算  | 按 p95 achievable 算  | 预约跨度内每个时隙够不够                         |
| ---------- | ---- | -------------- | ------------------- | ------------------- | ------------------------------------ |
| o1：09:00 起 | 60   | 09:20          | 36 Gbps → **09:34** | 27 Gbps → **09:44** | 09:00、09:15、09:30 都 ≥ 60 ✓           |
| o2：09:00 起 | 40   | 09:30          | 24 Gbps → **09:50** | 18 Gbps → **10:07** | 预约要覆盖到 p95 的 10:07，而 10:00 时隙只剩 15 ✗ |


读法：

- **按 reservable 承诺 o1 会说 09:20 到**，实际大概 09:34，最坏 09:44。下游 task 按 09:20 排，就会空等。
- **o2 看起来更省容量**，但【倾向】预约必须覆盖到 p95 完成时刻，一覆盖就撞上 10:00 那个只剩 15 的时隙，所以不能给出。**不确定性区间越宽，要锁的容量越多**，这就是 §5.2 校准的价值。
- 10:00 以后只剩 15 的原因是 own 层占了 25，所以这一段的 `blocked_by = own_commitment`；09:45 起 observed 只有 40，是外部流量，`blocked_by = foreign_traffic`。



#### 回答什么

```
QuoteResponse (per transfer):
  status:  feasible | infeasible | unreachable
  offers:  [ { start, rate_profile, predicted_finish{p50, p95}, qos_class } ]
  binding: { when, blocked_by: own_commitment | foreign_traffic }
```


| 字段                           | 设计要点                                                                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `offers[]` 是复数               | 返回这个 transfer 的**可行前沿**（最早到 / 最省容量 / 推后到），scheduling agent 在本地做组合搜索，不必反复往返。network agent **不替它选**，因为选哪个取决于别的 workflow 要什么                    |
| `infeasible` 也给 offers       | 就是 counter-offer："最早能到 t'"或"接受 X' 速率就赶得上"                                                                                                    |
| `unreachable`                | 结构性不可能：端点不可达、拓扑上没路、VLAN / MTU 不兼容。这不是调度问题，是配置问题，只能报给人                                                                                        |
| `predicted_finish{p50, p95}` | 不用离散的 confidence 档位。scheduler 要决定的是"留多少 slack"，一个 0.8 没法算 slack；p95 可以直接算。给人看时再按 provenance 标 `high / medium / low`（有充分历史 / 条件不同的历史 / 冷启动常数） |
| `binding.when`               | 时间轴上哪几个时隙卡住了；是 counter-offer 的依据，也是向人解释"为什么被推后两小时"的原始素材                                                                                      |
| `binding.blocked_by`         | 只要两个值。`own_commitment`：被我们自己的承诺占着，scheduler 可以去抢占或让路；`foreign_traffic`：不归我们管，只能换时段或换路径。这一条把优先级仲裁从盲目试错变成有向搜索                                  |




### 3.2 Q2 hold：试探性预留

```
hold(chosen offers, ttl) → hold_id      ← 整组一个 hold_id
```

- **对应 SENSE** `propagate`：把 intent 算完，把资源预留下来，但不真正下发网络配置。
- **和 quote 背后的查询要分清**：quote 用 `proceed=false`，只算不留；hold 用 `propagate`，真的占资源。
- **hold 立刻写 own 层**。之后别的 quote 看到的 available 已经扣掉这一笔。
- **TTL 到期自动释放**，所以 scheduler 可以把 hold 当成搜索原语：先 hold A 的方案，再 quote B，组合更优就 release A 重放，失败的试探不会留下垃圾预留。
- **它是 commit 前的核对点**：`propagate` 失败，说明账本和 SENSE 真实状态不一致（可能就是 §2.6 的隐藏瓶颈），此时触发一次事件型刷新。

**为什么 hold 是整个协议里最重要的动词**：没有它，scheduler 在 quote 和 commit 之间世界已经变了。有了它，一个 workflow 的所有 transfer 可以先 quote 一圈、全部 hold 住、确认都可行再原子 commit——这就是 workflow admission 的正确实现，而 SENSE 的两阶段接口白送了这个能力。

> 【未设计】hold 过期、propagate 部分失败时的错误路径。



### 3.3 Q3 commit：落到电路上



#### commitment 不等于 circuit

SENSE 建 L2 overlay 要几分钟，所以 overlay 通常长期保留，快速恢复发生在 L3（flow redirection）。30 秒恢复目标直接排除了"故障后重建电路"。

```
commitment（逻辑承诺，对 scheduling agent 说的话）
        ↓  多对一
circuit（物理电路，对 SENSE 说的话）
```

**commitment 是一趟班次，circuit 是一条包下来的专用车道。** 开车道要几分钟，排班次是瞬间的事。

```
circuit C1：ANL→ORNL，100 Gbps，09:00 建立，18:00 拆除      ← 只 provision 一次

  09:00        10:30        12:00                           18:00
  │─cmt A─────│──空闲──────│─cmt B─────────│─cmt C──────────│
    WF-1                      WF-2             WF-1
```

commit 时，network agent 要决定这笔 commitment 放到哪条电路上：

1. 同一 (src, dst) 上有保温中、余量够的电路 → **直接复用**，只写账本，毫秒级
2. 没有 → **懒创建**新电路（下面的编译步骤）
3. 电路空闲超过阈值 → **拆除**（§4.5）

**这一层换来三件事**：30 秒恢复变得可信（在已有电路里改速率或改路径）；电路建立延迟被摊薄，quote → commit 才可能落进 p50 < 200 ms；故障时不碰 L2。

**代价**：图中 10:30–12:00 空闲，但电路预约的容量仍然锁着，别人用不了。这正是 KK 批评 DMM 的那件事。**统计复用的入口就在这一层**：让保温电路的闲置容量能被别的 commitment 借用。v1 不做，架构上留位置。

> 【新增，待定】**电路池会让 §2.2 的减法重复计算。** 电路一旦建好，SENSE 的 observed 视图里已经扣掉了整条电路的 100；而 own 层如果再按 commitment 扣一遍，同一段容量就被减了两次。需要明确 own 层记的是什么：
>
> - 对**已有电路**：可用 = 电路容量 − 同一时隙内这条电路上的 commitment 之和
> - 对**新建电路**：可用 = observed − 我们已建但 SENSE 视图尚未反映的电路
>
> 笔记里没有处理这一点，建议在定账本数据结构时一并定。



#### 编译成 ServiceIntent

```jsonc
{ "service": "dnc",
  "alias": "scinet-cmt-7f3a91",
  "terminals": [                                  // 由 bindings 经 GET /discover/lookup/{name} 解析
    { "uri": "urn:ogf:network:anl.gov:2013:…", "vlan_tag": "any" },
    { "uri": "urn:ogf:network:ornl.gov:2013:…", "vlan_tag": "any" } ],
  "bandwidth": { "capacity": "40000",             // Mbps 字符串
                 "qos_class": "guaranteedCapped" },// guaranteedCapped | softCapped | anyAvailable | bestEffort
  "schedule": { "start": "…09:00:00Z", "end": "…10:07:00Z" },
  "path_tprofile": { "exclusion_list": [ … ] } }  // 只表达偏好
```

三条纪律：

- `capacity` **是 cap，不是吞吐保证**。填进去的数来自账本；承诺给上层的完成时间必须经 achievability 折算，两者不是一个量。
- `schedule.end` **要覆盖到 p95 完成时刻**，否则慢一点就掉出预约。
- **路径只作偏好**。`path_tprofile` 的 inclusion / exclusion 可以用，但绝不指定完整链路序列：0908 要求"保持 source 与 destination 固定，让中间网络图可变"，而且 SENSE 也读不回完整有序 route。



#### 我们的动词 → SENSE 调用


| 我们的动词     | SENSE 调用                                              | 说明                      |
| --------- | ----------------------------------------------------- | ----------------------- |
| （账本刷新）    | `POST /instance/{siUUID}?proceed=false` + `queries[]` | 只算不留                    |
| （端点解析）    | `GET /discover/lookup/{name}`                         | bindings → terminal URI |
| `quote`   | 不调 SENSE                                              | 查本地账本                   |
| `hold`    | `PUT /instance/{siUUID}/propagate`                    | 算好并预留，不下发               |
| `commit`  | `PUT /instance/{siUUID}/commit`                       | 真正下发；失败走 `rollback`     |
| `modify`  | `POST /instance/{siUUID}/modify`                      | 在线改带宽或时间                |
| `release` | `cancel` / `release`                                  | 拆除或释放                   |
| （状态确认）    | `GET /instance/{uuid}`                                | 读回 ServiceState         |


复用已有电路时，`hold` / `commit` 可能只动账本、不调 SENSE。

#### commit 返回什么

**不能只返回** `commitment_id`**。** 还必须返回端点绑定：

```
{ commitment_id, circuit_id, src_uri, dst_uri, vlan, interface }
```

scheduling agent 把它装进执行计划的 `endpointBindings[]` 交给 WMS。SENSE provision 出来的路径带着特定的 VLAN / IP / 接入点，**传输必须在这些端点之间发起才会落到电路上**，否则数据照走默认路由，预约白做。这正是 Rucio–SENSE 论文里 DMM 做的事。

commit 之后读 `ServiceState`，确认到了 `provisioned: true`，才算真正生效。

## 4. 运行期

4.1 是 M1–M4 共用的底座：network agent 能看到什么、看不到什么。4.2–4.5 是四个具体任务。

### 4.1 遥测怎么进到 network agent（M1–M4 共用）



#### 能拿到的三类，走两个 API 面


|                  | API 面                            | 状态         | 能说明什么                   | 不能说明什么     |
| ---------------- | -------------------------------- | ---------- | ----------------------- | ---------- |
| `CapacitySample` | SENSE-O Intent API               | 已确认        | 某时间窗还能预约多少（模型量）         | 实际流量、实时利用率 |
| `ServiceState`   | SENSE-O Intent API               | 已确认        | 电路配置是否完成、是否 STABLE、是否过期 | **性能是否达标** |
| `ProbeResult`    | **SiteRM Debug API**（不是 SENSE-O） | **可得性未确认** | 这一刻的吞吐、RTT、丢包、路径        | 持续的时间序列    |


```jsonc
// ServiceState
{ "serviceInstanceUuid": "…", "circuitId": "C1",
  "state": "STABLE",                 // CREATE-COMMITTED | STABLE | CANCEL-COMMITTING | …
  "provisioned": true, "changedAt": "…08:58Z" }

// ProbeResult —— rapid-ping / traceroute / iperf-client，有代价
{ "src": "anl-lcrc", "dst": "ornl-olcf",
  "kind": "iperf",                   // iperf | rapid-ping | traceroute
  "measuredAt": "…08:50Z",
  "throughputGbps": 62.4,
  "rttMs": { "p50": 12.2, "p95": 18.0, "p99": 35.1 },
  "lossPct": 0.02, "path": ["L1", "L2", "L3"],
  "cost": { "bandwidthUsedGbps": 10, "seconds": 30 } }
```


|                  | 去哪                                                           | 注意              |
| ---------------- | ------------------------------------------------------------ | --------------- |
| `CapacitySample` | observed 层的时隙                                                | 账本唯一的外部真相来源     |
| `ServiceState`   | circuit 层的生命周期                                               | 只作配置状态用，绝不作性能证据 |
| `ProbeResult`    | RTT 进 achievability 输入；`lossPct` 进归因；`path[]` 补 SENSE 读不回的路径 | 冷启动时是唯一的先验来源    |




#### SiteRM 这一路的四个后果

1. **可得性未确认**（0904）：是否允许直接访问、各站点支持哪些 action、跨站点可访问性都没实测。probe planner 的第一条规则应该是"先探这个站点对支不支持探测"。
2. **授权边界不同**：SENSE-O 一个 token；SiteRM 可能每个站点单独授权。
3. **单次探测不是持续遥测**：`iperf` 给的是那一刻、那一条合成流的数字。所以**实际传输记录才是 achievability 的主数据源**，探测只作补充与冷启动先验。
4. **twin 要模拟两套接口**。如果 twin 只实现了 SENSE-O 那一半，Phase 1 就没有 probe，冷启动只能靠常数。【待核对】值得提前问清楚。



#### 谁都拿不到的

- **实时链路利用率、RTT、丢包、抖动**：SENSE-O Northbound 没有（0904 §5.2.4–5.2.5）
- **端系统事实**：DTN 的 NIC、PCIe、存储读写、TCP 参数。只能从实际传输结果**反推**出"这对站点跑不满"，推不出成因。
- **传输进度**：归 WMS 的搬运工具（Globus / Rucio / FTS），不在 network agent 手里。

> 【新增，待核对】最后一条直接影响 M1：运行中"吞吐退化"要靠传输进度才能看出来，而进度不在我们手里。需要 WMS 经 Telemetry Service 上报运行中传输的进度（已传字节数 + 时间戳），否则只能等传输结束才知道慢了。



#### digital twin 的遥测给多少

> 【未定】【倾向】twin 默认按真实 SENSE 的能力边界提供观测量，把"额外遥测"做成可开关的实验变量。
>
> - 给全：检测又快又准，但那是给自己开了后门，结论迁移不到真实系统。
> - 按真实能力裁剪：结果诚实，而且"逐项拿掉遥测、看性能退化多少"这个实验立刻变得可做。



### 4.2 M1 偏差检测


| 信号                      | 来源                        | 性质            | 能多快发现        |
| ----------------------- | ------------------------- | ------------- | ------------ |
| 电路掉出 `STABLE` / 链路 down | `ServiceState`、link state | **事件**，有明确信号  | 秒级，5 秒可承诺    |
| observed 容量下降           | `CapacitySample` 重采样      | 事件，但受刷新周期限制   | 取决于刷新频率      |
| 吞吐低于预期                  | 传输进度（见上条缺口）、probe         | **统计量**，要观测窗口 | 5 秒内分不清退化和抖动 |
| 丢包 / RTT 升高             | probe                     | 统计量，且有代价      | 按需           |


**0908 的 "5 秒检测" 要诚实拆开**：链路失效这类**事件**可以 5 秒；吞吐退化 30% 这类**统计量**不行。后者的检测延迟由采样率和判定阈值决定，**"检测延迟 vs 误报率"本身是一条可测曲线**，比含糊承诺"5 秒检测一切"体面得多。

### 4.3 M2 故障扫描：先扫描，再逐条判断

故障后第一步不是"修这一条"，而是**找出这条路径上所有受影响的 commitment**，包括正在跑的和还没开始的。

```
故障 → (src, dst) / circuit
     → 账本上这条路径在受影响时段内的所有 own 记录
     → 每条按新的 available 和 achievable 重算 predicted_finish{p50, p95}
```

- **扫描未开始的**：observed 下降时，把受影响时段的所有 own 记录一次性重算，不必等它们逐条开始跑、逐条变慢才发现。
- **扫描范围受信息边界限制**：按 (src, dst) 建账，共用隐藏瓶颈的其他路径扫不到（§2.6），会漏报；反过来也可能误报。缓解手段：`ProbeResult.path`、`WfPlatform.routes`。



### 4.4 M3 自修或上报



#### 判据：slack

```
每条受影响的 commitment
   ├─ 新 predicted_finish.p95 ≤ latest_finish  → 快回路：自己修，发 repaired
   └─ 赶不上了                                → 慢回路：发 at_risk，scheduling agent 重新仲裁
```

判据现成：scheduler 给的窗口是 `[earliest_start, latest_finish]`，network agent 承诺的是更早的 `predicted_finish`，**两者之差就是本地自修预算**。协议不用加字段。

快回路必须存在，否则每次抖动都惊动 scheduler，30 秒预算全花在协商上。

#### 自修手段，按代价从低到高

**共同点：全部只动这一条 commitment 自己。**


| 手段             | 碰 SENSE 吗     | 适用                    |
| -------------- | ------------- | --------------------- |
| 往后挪，吃自己的 slack | 否，只是账本操作      | 当前时段拥塞，但 deadline 还宽裕 |
| 提速补量           | `modify` 改带宽  | 账本上后续时隙还有余量，把落后的量赶回来  |
| 换电路            | 否，用电路池里现成的    | 同一目的地有另一条保温电路         |
| 重新 provision   | 是，慢，可能超过 30 s | 前面都不行才用               |


> 0909 曾把"加并行流 / 调传输参数"列为第一手段。0914 更正：这是数据面参数，由 WMS 的搬运工具控制，**network agent 改不了**。只能在上报里给出建议，由 scheduling agent 写进更新后的执行计划，交给 WMS 执行。



#### 上报格式

**成批上报**：一次故障通常同时产生几条 `repaired` 和几条 `at_risk`，一起发，让 scheduler 一次看到全貌再重排，而不是一条条被动反应。

```
repaired | at_risk:
  commitmentRef
  predicted_finish { p50, p95 }                 ← 修后 / 预计的新完成时间
  cause: end_host | network | foreign_traffic | unknown
  affected_window
  suggestion?                                   ← 可选，如 "increase parallel streams"
```

- `repaired` **也要带新的** `predicted_finish`：虽然还在窗口内，但 slack 被吃掉了，scheduler 得知道这条已经没有余量。
- `repaired` **和** `at_risk` **必须分开**：前者是通报（承诺仍成立，无需决策），后者是升级（保不住了，等你决定）。混成一个，scheduler 分不清要不要动。
- **上报结论，不上报原始指标**：利用率 80% 对某条 commitment 意味着什么，只有结合账本和 achievability model 才知道，而这两样都在 network agent 里。
- `cause` **怎么定**：来自 §5.3 的归因；拿不准时填 `unknown`，不要猜。



#### network agent 看不到的

它只知道每条 commitment 的窗口，看不到窗口背后的 DAG。所以它**不知道**：下游健康路径上的传输也要挪；哪几条 `at_risk` 属于同一个 workflow；自修吃掉的 slack 是否本来是留给下游计算排队的。这三件事由 scheduling agent 在 Runtime DAG 上传播时发现（见 scheduling §4.3）。

### 4.5 M4 执行重排、维护电路池



#### scheduling agent 的决定如何落到 network agent

走同一套协议，不加新动词：


| scheduling agent 的决定 | network agent 这边发生什么                                   |
| -------------------- | ------------------------------------------------------ |
| 接受更晚完成               | 对原 commitment quote 新窗口 → `modify`（SENSE modify 改时间）   |
| 提速补时间                | quote 更高速率 → `modify`（SENSE modify 改带宽）                |
| 抢占低优先级               | 为高优先级 `hold` 新放置 → 被抢者 `modify` / `release` → `commit` |
| 重排下游                 | 下游 transfer 按平移后的窗口重新 quote → `modify`；前面空出的时段回到账本     |
| 换副本源                 | 新 transfer 走 `quote → hold → commit`，成功后 `release` 旧的  |
| 放弃                   | `release`                                              |


**先占新，再放旧**（make-before-break）：新方案 `hold` 成功 → release 旧的 → `commit`。先 release 的话，释放那一刻容量可能被别人拿走，最后两头落空。

`at_risk` **需要响应期限**：scheduler 迟迟不决定，network agent 不能无限等。【未定】默认行为，例如超时后按 best-effort 继续传，并把该承诺标记为违约。

#### 电路池维护


| 事件                    | 动作                                                 |
| --------------------- | -------------------------------------------------- |
| 电路上最后一笔 commitment 结束 | 进入保温，开始计空闲时间                                       |
| 空闲超过阈值                | 拆除（`cancel` / `release`），circuit 层删除，容量还给 observed |
| 新 commitment 到来且有保温电路 | 直接复用                                               |
| 电路长期利用率偏低             | 考虑缩容（`modify` 降带宽）【倾向】v1 不做                        |


空闲阈值怎么定、要不要按历史到达规律预测，是一个 policy 点，v1 用固定值。

## 5. 跨 run



### 5.1 L1 配对 reserved vs achieved

achievability model 要学的是一对数，而这两个数来自不同的源，**必须在 network agent 里配对**：

```
reserved   预约了多少   ← network agent 自己的账本（own 层）
achieved   实际跑到多少 ← 转发来的传输记录：bytesTransferred / durationSeconds
ratio    = achieved / reserved
```

**转发来的记录**（`transfer_outcome`）：

```jsonc
{ "commitmentRef": "cmt-7f3a91",       // 配对的键，这一跳存在的全部理由
  "fileId": "input.txt",
  "source": "aps-beamline-8id", "destination": "anl-n01",
  "startedAt": "…08:31:12Z",
  "durationSeconds": 1720.0, "bytesTransferred": 5.0e11,
  "path": ["APS-LCRC"],
  "rttMs": { "p50": 3.1, "p95": 4.4, "p99": 9.8 },
  "parallelStreams": 8, "protocol": "globus-gridftp",
  "concurrentTransfers": 2,              // 这条链路上所有并发，含非本 workflow 的
  "status": "completed" }                // completed | failed | partial
```

**network agent 手上已有、不必传的另一半**：`reservedRateGbps`、当时给出的 `predicted_finish{p50, p95}`、`circuit_id`、账本上占的时隙。

两个字段是必须的：

- `commitmentRef`：没有它只能靠 `(fileId, source, destination, startedAt)` 就近匹配。重传时同一对端点会有多条记录，配错就把别人的 achieved 算到这条头上，等于污染训练集。
- `status`：只记成功的传输会造成**幸存者偏差**，模型系统性乐观，而失败的恰恰最该学。`partial` 时 `bytesTransferred` 记实际传成的量。



### 5.2 L2 achievability model



#### 它是什么

一个学习型映射，不是一张历史数值表：

```
achievable_rate = f(reservable, 路径, 两端主机, 协议, 并行流数, RTT, 文件大小, 并发数)
                  + 不确定性区间
```

- **冷启动**：用保守常数（如 0.6×）
- **积累后**：按站点对、按时段收紧



#### 为什么需要它：差距多数不是网络过载

SENSE 说这条路能预约 100 Gbps，实测可能只有 60。SENSE 确实在路径每条链路上把 100 留住了，跑不满是因为瓶颈在**网络之外**：NIC、PCIe、磁盘读写、单条 TCP 流在高 RTT 长肥管道上跑不满、MTU、主机 CPU。

**所以学它是为了改承诺，不是改申请。** 申请 150 换 100 是绝对不能做的事：端系统是 60，网络给再多也是 60，只是多锁死 50。

#### 四个作用


| 作用             | 说明                                                                       |
| -------------- | ------------------------------------------------------------------------ |
| **算出可兑现的完成时间** | 按 reservable 算会系统性承诺过早，下游 task 排错位置，整个 DAG 顺延（§3.1 的例子：说 09:20，实际 09:34） |
| **让预约贴合实际**    | 稳定只能跑 60，申请 100 就是锁死 40。**校准的结果往往是申请更少，减轻网络压力**（落地见 §5.4）                |
| **给出不确定性区间**   | 残差分布决定 p50 / p95 的宽度，进而决定 safety margin 留多少                              |
| **归因诊断**       | 同样是"约 100 跑到 60"，成因不同修法完全不同（§5.3）                                        |




#### 残差、区间与 safety margin

**残差** = 实际完成时间 − 预测完成时间，每次传输完得到一个。

- 残差小而集中 → 区间窄：`p50: 11:20, p95: 11:35`
- 残差大而分散 → 区间宽：`p50: 11:20, p95: 12:40`

**safety margin** = 做承诺时额外留的余量：按 p95 而不是 p50 承诺、预约跨度覆盖到 p95。区间越宽，余量越大，锁死的容量越多。**模型越准，余量越小，浪费越少**——这就是"收紧"的意思。

长回路里还要对照 **p95 承诺 vs 实际**，检验模型是不是系统性乐观。

### 5.3 L2 归因：端系统还是网络

看 `ratio = achieved / reserved` **跟着什么变**：


| 现象        | 例子                       | 瓶颈在              | 修法                                                 | `cause`                       |
| --------- | ------------------------ | ---------------- | -------------------------------------------------- | ----------------------------- |
| 稳定，且与路径无关 | 这对主机不管走哪条路、白天夜里，总是 ≈ 0.6 | **端系统**：瓶颈跟着主机走  | 建议加并行流 / 换 DTN（经 scheduling agent 给 WMS）；预约按实际能力下调 | `end_host`                    |
| 波动，且与时段相关 | 白天 0.4、夜里 0.9；或换条路就好了    | **网络侧**：拥塞、别人的流量 | 换路径、换时段、发 `at_risk`、标记该路径不可靠                       | `network` / `foreign_traffic` |


**probe 的** `lossPct` **用来定案**：端系统瓶颈通常丢包低；网络拥塞通常伴随丢包升高。

没有归因，快回路就不知道该调参数还是该换路径。

### 5.4 L3 Apply：把学到的东西落回规划和电路池

L1、L2 只产出一个模型和一个归因。**不落回去，它们就只是一份报表。** L3 把它们用到下一次 quote、下一次自修和电路池上。

#### 输入


| 输入                  | 来自                       | 内容                                               |
| ------------------- | ------------------------ | ------------------------------------------------ |
| achievability model | L2                       | 每个站点对的折算系数与 p50 / p95 区间                         |
| `cause`             | L2                       | 差距来自 `end_host` 还是 `network` / `foreign_traffic` |
| 电路利用率               | 账本 circuit 层（本地，不来自传输记录） | 见下                                               |


**电路利用率有两个，含义不同**：

```
预约利用率(C) = Σ commitment 的 (预约速率 × 时长) / (电路容量 × 电路在线时长)   ← 电路有多少时间在空转
实际利用率(k) = achieved / reserved                                        ← 每笔 commitment 跑满没有（L1 给）
```

前者低，说明电路本身开得太久或太大；后者低，说明 commitment 预约得太多。两者修法不同。

#### 输出：改变了什么


| 作用到                     | 改变什么                                         | 条件 / 例子                                                                                               |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **预约速率**（Q1）            | 预约贴合端系统实际能力，**多出来的还给账本**                     | 这对主机稳定只能跑 60 → 下次预约约 65 而不是 100，35 回到 available。**只在** `cause = end_host` **时下调**；若是网络侧，下调没用，应换路径或换时段 |
| **预约跨度**（Q1、Q3）         | 区间收窄 → `schedule.end` 覆盖到的 p95 更早 → 锁的时隙更少   | §3.1 的 o2 因为 p95 太晚撞上 10:00 时隙而给不出；区间收窄后可能重新可行                                                        |
| **承诺的完成时间**（Q1）         | `predicted_finish{p50,p95}` 用校准后的系数          | 上游 scheduling agent 据此算的 slack 才是真的                                                                   |
| **自修手段**（M3）            | 按 `cause` 选修法                                | `end_host` → 建议加并行流 / 换 DTN；`network` → 换电路、换时段、发 `at_risk`                                           |
| **路径偏好**（Q3）            | 网络侧反复出问题的路径写进 `path_tprofile.exclusion_list` | 只作偏好，不指定完整路径                                                                                          |
| **电路池**（M4）             | 预约利用率低 → 缩短空闲阈值、拆除；复用频繁的站点对 → 保温更久           | 缩容（`modify` 降带宽）【倾向】v1 不做，但数据从这里来；也是将来统计复用的输入                                                         |
| **probe planner**（§5.5） | 历史充分、区间已窄的站点对不再探；偏差变大的加探                     | 把探测预算花在不确定性最大的地方                                                                                      |


**一条原则**：**校准的结果通常是预约更少，而不是更多。** 它减轻网络压力，而不是加剧。

**作用时机**：【倾向】v1 只影响**之后**的 quote 和电路池决策，不回改已经 commit 的承诺，避免计划抖动。

### 5.5 probe planner：什么时候花代价去测

探的是账本里**查不到**的东西：SENSE 只给 reservable（模型量），给不了 measured（实测量）。


| 探什么           | 工具                 | 用来干什么                                  |
| ------------- | ------------------ | -------------------------------------- |
| 实际吞吐          | `iperf`            | 冷启动时给 achievability 一个先验               |
| RTT / 丢包 / 抖动 | `rapid-ping`、owamp | 归因（网络侧还是端系统）；RTT 本身是 achievability 的输入 |
| 实际路径          | `traceroute`       | 补 SENSE 读不回的有序路径；缓解 §2.6 的盲区           |


**为什么是决策而不是常开**：`iperf` 会真的打流占带宽，可能干扰正在跑的传输；跨站点要授权；结果不是立刻返回。"花一次探测消除多少不确定性值不值"本身是个判断题。

【倾向】v1 规则：只在两种情况探测，外加每小时次数上限。

1. **冷启动**：该站点对没有历史，模型只能用 0.6×，探一次能立刻收紧
2. **偏差超阈**：上次实测偏离预测太多，需要判断是一次性抖动还是系统性变化

做成可替换的 policy 接口，之后再量化比较换成更聪明的策略是否更好。
