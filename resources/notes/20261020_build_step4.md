## 读代码时注意四点

**1. state 和 context 分开**

- **state（`QuoteState`）**是这一次报价的工作记录。每个字段都注明了由哪个节点写入，读代码时可以按节点顺序跟着 state 走。
- **context（`AgentContext`）**放账本、拓扑、telemetry 这些长期存在、所有请求共用的对象。每次调用时传入：`graph.invoke({"raw": ..., "now": ...}, context=ctx)`。节点通过 `runtime.context` 读取。

这就是 10/14 设计里的"账本不进 state"。

**2. 节点只做编排**

每个节点基本上都是：从 state 取输入 → 调用前几步写好的模块 → 把结果写回 state。比如 `refresh_if_stale` 就是把第 2、3a 步的 `paths`、`is_stale`、`link_samples`、`apply` 串起来。

**3. 放置搜索的三条规则，复现了 slide 7**


| 规则               | 含义                     | 复现结果                                                   |
| ---------------- | ---------------------- | ------------------------------------------------------ |
| `earliest_start` | 最早能开始的时刻，用从那时起能维持的最大速率 | a1：09:00 @ 40 → 11:46:40（`blocked_by=foreign_traffic`） |
| `max_rate`       | 整个窗口内能达到的最高速率          | a2：12:00 @ 100 → 13:06:40                              |
| `min_rate`       | 从最早时刻起，刚好赶在截止前的最低速率    | a3：09:00 @ 20 → 14:33:20                               |


slide 7 的 a3 是 20 Gbps，正好对应"按 10 Gbps 步长取整"。理论最低速率是 18.5，向上取整得到 20。这也是新增 `rate_step_gbps` 的原因。

**4. 报价是只读的**

quote 不预扣容量（测试 `test_quote_is_read_only`），也不调用 SENSE。它唯一的写操作是把过期的观测刷新进账本：那是观测值，不是预订。

报出的每个 offer 都记进 `offer_book`（offer_id → 方案，含路径）。因为 offer 消息里不带路径，第 5a 步 reserve 时要靠 offer_id 把路径找回来。

> 解释一下quoteState的设计思路，为什么是那9个属性

**设计原则只有一条：state 里的每个字段，都是某个节点交给后续节点（或交给调用方）的东西。** 读法就是"谁写、谁读"。9 个字段按流程分成三组：

```
输入（调用方给）     raw, now
中间产物（节点之间传递）  request → paths, refreshed → placements, rejections → offers
输出（交回调用方）    response

```



## 逐个字段：谁写、谁读、为什么需要


| 字段           | 谁写                                | 谁读                                   | 为什么需要                       |
| ------------ | --------------------------------- | ------------------------------------ | --------------------------- |
| `raw`        | 调用方                               | `validate_bundle`                    | 原始请求，见下面第 1 点               |
| `now`        | 调用方                               | `refresh_if_stale`、`find_placements` | 判断观测是否过期，以及报价不能早于现在         |
| `request`    | `validate_bundle`                 | 后面所有节点                               | 校验通过、类型确定的请求，后面节点不用再担心格式问题  |
| `paths`      | `refresh_if_stale`                | `find_placements`                    | 候选路径。刷新时已经算过一遍，直接传下去，避免重复计算 |
| `refreshed`  | `refresh_if_stale`                | **没有节点读**                            | 见下面第 3 点                    |
| `placements` | `find_placements`                 | `estimate_finish`、`respond`          | 可行方案，**带路径**                |
| `rejections` | `find_placements`                 | `respond`                            | 不可行传输的原因                    |
| `offers`     | `estimate_finish`                 | `respond`                            | 对外的 offer 消息，**不带路径**       |
| `response`   | `validate_bundle`（失败时）或 `respond` | 调用方                                  | 最终回复                        |




## 几个值得说明的选择

**1. 为什么输入是** `raw: dict`**，而不是直接收** `QuoteRequest`

如果调用方先自己构造 `QuoteRequest`，不合法的请求在进图之前就已经报错，`validate_bundle` 这个节点和"校验失败 → 直接回复"这条分支就都没有意义了。

收原始 dict，校验就成为图里的一步，失败时也能按协议回一个 `ErrorResponse` 给对方，而不是让整个调用抛异常。这正是 10/15 修订里补上的"validate 失败要有出口"。

**2. 为什么** `now` **也放进 state**

`now` 是这一次请求的输入，每次调用的值都不同，所以放在 state 里；context 放的是跨请求共用的东西。由调用方传入还有两个好处：测试可以固定时间，第 6 步的 demo 可以用模拟时钟快进。

**3. 为什么留着一个没有节点读的** `refreshed`

它是给人和测试看的：这一次报价刷新了哪些链路。测试 `test_fresh_values_are_not_refetched` 就靠它验证"新鲜的值不会重复拉取"。

LangGraph 执行结束后会返回完整的 state，所以中间产物天然就是一份执行记录。以后接入 LangSmith 这类追踪工具，也能看到每一步产生了什么。

**4. 为什么可行和不可行分成两个字段**

每条传输的结果只有两种：有方案，或者有原因，互斥。分成 `placements` 和 `rejections` 两个 dict，`respond` 只要看传输 id 落在哪个 dict 里，就知道该回 feasible 还是 infeasible/unreachable，不用在同一个结构里再加状态标记。

**5.** `placements` **和** `offers` **看着重复，为什么两个都要**

两者一一对应，但给的对象不同：


|              | 给谁                                           | 有路径吗         | 有 p50/p95 吗 |
| ------------ | -------------------------------------------- | ------------ | ----------- |
| `placements` | 我们内部：存进 `offer_book`，第 5a 步 reserve 时要靠它找回路径 | 有            | 没有          |
| `offers`     | scheduling agent：放进回复                        | 没有，对方不需要知道路由 | 有           |


`respond` 节点会把两者按顺序配对：offer 放进回复，placement 按 offer_id 存进 `offer_book`。

## 哪些东西故意不放进 state

账本、拓扑、telemetry、rate model、`offer_book` 都在 context 里，因为它们是**跨请求**的：

- 账本必须被所有请求共享，下一次报价才能看到上一次的预扣；
- `offer_book` 要在 quote 结束之后还留着，等下一次 reserve 调用时取用。

state 只活在这一次图执行里，放进去的东西执行完就不再被别的请求看到。这就是一开始设计时说的"state 是这一次执行的工作记录"。

## 第一行的 `total=False`

`TypedDict` 默认要求所有字段都存在。`total=False` 表示字段可以缺失：执行开始时只有 `raw` 和 `now`，其余字段由节点一步步补上。

`respond` 里用 `"response" in state` 来判断 validate 是否已经失败，靠的也是字段可以缺失这一点。

---

> AgentContext是啥，怎么用的，怎么设计出这几个属性？

`AgentContext` **是三张图共用的"运行环境"：一个 dataclass，装着所有请求都要用、而且要活得比一次图执行更久的对象。** 在 LangGraph 里，这叫 runtime context。

## 它是什么

```python
@dataclass
class AgentContext:
    cfg: NetAgentConfig
    topology: Topology
    ledger: CapacityLedger
    telemetry: TelemetrySource
    rate_model: RateModel
    offer_book: dict[str, Placement] = field(default_factory=dict)
```

它和 state 的分工，可以对照着看：


|                  | state（`QuoteState`）               | context（`AgentContext`） |
| ---------------- | --------------------------------- | ----------------------- |
| 寿命               | 一次图执行，执行完就结束                      | 由调用方创建，跨越多次执行           |
| 范围               | 只属于这一次请求                          | 所有请求共用                  |
| 谁来改              | 节点**返回** dict，LangGraph 合并进 state | 节点**直接调用**对象的方法，原地修改    |
| LangGraph 是否记录变化 | 记录，执行完能看到每一步写了什么                  | 不记录，只是把同一个对象传给每个节点      |




## 怎么用：三处代码

**1. 建图时声明类型**（[protocol.py](../../src/lib/network_agent/graphs/protocol.py) 的 `build_quote_graph`）：

```python
g = StateGraph(QuoteState, context_schema=AgentContext)
```

告诉 LangGraph：这张图运行时会带一个 `AgentContext`。

**2. 调用方创建一次，每次调用时传入**（测试里的 fixture `ctx`）：

```python
ctx = AgentContext(cfg=cfg, topology=topo, ledger=CapacityLedger(...),
                   telemetry=MockTelemetry(...), rate_model=IdealRateModel())

graph.invoke({"raw": 请求1, "now": t(9)},    context=ctx)
graph.invoke({"raw": 请求2, "now": t(9, 1)}, context=ctx)   # 同一个 ctx：第二次能看到第一次的结果
```

**3. 节点通过** `runtime` **参数读取**：

```python
def refresh_if_stale(state: QuoteState, runtime: Runtime[AgentContext]) -> dict:
    ctx = runtime.context
    ctx.ledger.is_stale(...)
    ctx.telemetry.link_samples(...)
```

节点的参数里写了 `runtime`，LangGraph 就会把它传进来；不需要 context 的节点（如 `validate_bundle`）不写这个参数即可。

## 这 6 个属性是怎么选出来的

挑选标准：**节点需要用，而且满足下面至少一条**：

- **(a) 跨请求共享**：多个请求必须看到同一份；
- **(b) 活得比一次执行长**：这次写下，下次调用还要读；
- **(c) 实现可替换**：mock 和真实系统要能互换，不该写死在节点里。


| 属性           | 哪个节点用                                                               | 满足哪条   | 说明                                           |
| ------------ | ------------------------------------------------------------------- | ------ | -------------------------------------------- |
| `cfg`        | `refresh_if_stale`（`max_paths`）、`find_placements`（`rate_step_gbps`） | (a)    | 参数来自 config 文件，所有请求一致                        |
| `topology`   | `refresh_if_stale` 找候选路径                                            | (a)    | 网络结构，所有请求共用                                  |
| `ledger`     | `refresh_if_stale`、`find_placements`                                | (a)(b) | **最关键的一个**：下一次报价必须看到这一次之后的预扣，否则会超额预订         |
| `telemetry`  | `refresh_if_stale`                                                  | (c)    | `TelemetrySource` 接口：mock 和真实数据源可互换          |
| `rate_model` | `estimate_finish`                                                   | (c)    | `RateModel` 接口：现在是理想模型，第 9 步换成校准模型           |
| `offer_book` | `respond` 写入                                                        | (b)    | quote 结束后还要保留，等下一次 reserve 调用按 offer_id 取回路径 |


反过来看，`now`、`raw` 这类**每次请求都不同**的值放在 state 里，不放进 context。

## 为什么不用全局变量

账本如果写成模块级全局变量，也能"跨请求共享"。但那样：

- 测试之间会互相污染，每个测试都想要一本干净的账本；
- 没法在同一个进程里跑两个 network agent，比如以后 demo 里有两个站点各自一个 agent。

用 context 显式传入，每个测试都新建一个 `ctx`，互不干扰。

## 还会继续加属性

第 5a 步会加入 `sense`（`SenseAdapter`）和存放 reserve/commitment 记录的存储；图 B、图 C 也会用同一个 context。

## 一个要注意的地方

LangGraph 只管理 state，不管理 context。context 里的对象目前都在内存里，**进程一重启，账本和** `offer_book` **就都没了**。真正部署时，账本和 commitment 记录要放进数据库；这不影响图的写法，只需要把 context 里的对象换成有持久化的实现。

---

> 所以context本质就是一个数据库对吗

**不完全是。context 更像一个"工具箱"：它本身不存数据，只是把节点要用的几样东西打包好，一次性递给每个节点。** 这些东西里，有的确实在存数据，像数据库；有的根本不是数据，而是一种能力或者一个接口。

把 6 个属性分开看：


| 属性           | 是数据吗            | 更像什么                        |
| ------------ | --------------- | --------------------------- |
| `ledger`     | 是：容量观测、预订记录     | **像数据库**，而且带业务规则（原子预扣、状态转换） |
| `offer_book` | 是：offer_id → 方案 | **像数据库里的一张表**               |
| `topology`   | 是，但只读           | 一份只读的参考资料                   |
| `cfg`        | 是，但只读           | 一组参数                        |
| `telemetry`  | **不是**          | 一个外部接口：调用它会去问别的系统           |
| `rate_model` | **不是**          | 一段计算逻辑：给定方案，算出完成时间          |


所以更准确的说法是：

- **context 是"依赖注入"的容器。** 节点需要什么，不自己去创建或查找，而是由调用方准备好、从外面传进来。节点只认 `runtime.context.ledger` 这个名字，不关心它背后是什么。
- **数据库是 context 里某些东西"背后可能的实现"。** 现在 `ledger`、`offer_book` 都存在内存里；真正部署时，可以换成背后接数据库的实现，比如 `ledger` 的预订记录存进 PostgreSQL。到那时，context 里放的是"连接数据库的账本对象"，而不是数据库本身。

用一个比喻：节点是厨师，state 是这一道菜的配料和半成品，context 是厨房：

- 冰箱（`ledger`、`offer_book`）存东西，是"数据库"；
- 菜谱（`cfg`）、地图（`topology`）只读；
- 电话（`telemetry`）用来向外面供应商要货；
- 计时器（`rate_model`）用来算时间。

厨房里有冰箱，但厨房不等于冰箱。

---

> state本质就是一张graph下的一条工作记录，最终这条工作流走完这个graph的时候，这个state造成的变更就会被持久化到context，更准确的说，持久化到context中的数据库中？

**前半句对，后半句不对。** state 确实是一条工作记录；但 state 不会在执行结束时"写回"context。**两者之间没有自动同步：节点在执行过程中直接修改 context，而且是立刻生效，不等图走完。**

## 实际发生的事

以一次报价为例，按时间顺序：

```
validate_bundle    → 写 state.request
refresh_if_stale   → 写 state.paths、state.refreshed
                   → 同时直接调用 ctx.ledger.apply(...)        ← 此刻 context 已经变了
find_placements    → 写 state.placements、state.rejections
estimate_finish    → 写 state.offers
respond            → 写 state.response
                   → 同时直接写 ctx.offer_book[...] = ...      ← 此刻 context 又变了
END                → state 作为返回值交给调用方，然后就不再使用
```

所以：

- **state 的去向：** 执行结束后整份交给调用方（`graph.invoke(...)` 的返回值），之后就不用了。它不会被"合并"进 context。
- **context 的变化：** 发生在节点**内部**、执行**途中**，是节点代码自己调用对象方法造成的。LangGraph 完全不知道这些变化。

两者是两条独立的线：节点通过**返回值**改 state，通过**直接调用**改 context。

## 为什么这很重要：没有"走完才生效"

如果真的是"走完 graph 才统一持久化"，那半路失败时什么都不会被写入，也就不需要回滚。但实际情况是 context 的修改立刻生效，所以**中途失败时，前面已经做的修改要靠我们自己撤销**。

这正是第 5a 步 reserve 分支要处理的问题：

```
ledger_pending  → 直接在账本上预扣                  ← 立刻生效，别的请求马上能看到
sense_call      → 调用 SENSE
   ├ ok   → ledger_confirm  转正
   └ fail → ledger_rollback 把刚才的预扣撤销          ← 必须显式写这个节点
```

图 A 里有 `ledger_rollback` 这个节点，就是因为 LangGraph 不会替我们做"整体成功才提交"。我们用账本自己的 pending → confirm / rollback 实现了一个两阶段过程。

预扣立刻生效也是有意设计的（slide 19）：reserve 一预扣，并发进来的下一次报价马上就能看到这部分容量被占了，不会把同一份容量再报给别人。

## LangGraph 真正的"持久化"是另一回事

LangGraph 有一个 checkpointer 机制（`20261013_agentframework.md` 里讨论过）：配置后，它会在每一步之后保存 **state 本身**，用 `thread_id` 区分，进程重启后可以从中断处继续。

但它保存的仍然是 state，与 context 无关；也不会把 state 的内容同步到账本里。我们目前没有用 checkpointer：每个指令都是一次独立的短调用，跨调用需要保留的东西（账本、`offer_book`）都放在 context 里，由我们自己管理。

## 一句话总结


|         | 怎么改        | 什么时候生效  | 执行结束后        |
| ------- | ---------- | ------- | ------------ |
| state   | 节点返回 dict  | 节点返回后合并 | 交给调用方，不再使用   |
| context | 节点直接调用对象方法 | **立刻**  | 一直保留，下次调用继续用 |


---

> 能否理解为state类似一张草稿纸，用于不同node之间的信息传递；context就是真正的试卷。你在草稿纸上记录当前工作流的信息，然后将结论在经历各个node时写进试卷

**"state 是草稿纸、在节点之间传信息"这部分很准确，"写进试卷"的意思也对：节点在执行途中把结果写进 context。** 不过这个比喻有三处要修正，否则以后读第 5a 步时会被误导。

**1. 交给对方的"答案"其实写在草稿纸上。** 给 scheduling agent 的回复是 `state.response`，它随 state 一起交给调用方。context 里写的并不是答案，而是"以后的请求还要用的东西"：账本的预扣、`offer_book`。

**2. 试卷是全班共用的。** 每个请求各有一张自己的草稿纸（state），但 context 只有一份，所有请求都在上面读写。A 请求刚在账本上预扣，B 请求马上就能看到。真正的试卷是一人一份，这里不是。

**3. 写进去的不一定是最终结论，可能还会被擦掉。** 第 5a 步里，`ledger_pending` 先在账本上预扣，SENSE 失败时 `ledger_rollback` 再把它撤销。所以 context 上写的也可能是"暂定"的内容。

修正后的比喻：


|         | 比喻                                                           | 对应                             |
| ------- | ------------------------------------------------------------ | ------------------------------ |
| state   | **每个请求自己的草稿纸**：记中间过程，最后的答案也写在上面，交卷时整张交给调用方                   | `QuoteState`，`response` 字段就是答案 |
| context | **教室里大家共用的白板**：所有请求都会看，也都会在上面写；可能先写个暂定值，失败了再擦掉；下课后（请求结束后）还留着 | `ledger`、`offer_book` 等        |


还有一点：节点不只往白板上"写"，也经常"看"白板。比如 `find_placements` 主要是在读账本，`refresh_if_stale` 还会通过 `telemetry` 往教室外面打电话问情况。

> 带我过一遍placement.py

[placement.py](../../src/lib/network_agent/placement.py) 回答一个问题：**给定账本、一条路径和一条传输需求，能报出哪些方案？** 输出是若干个 `Placement`，或者一个拒绝原因 `RejectReason`。

文件分三块：**数据结构（第 22–47 行）→ 三个辅助函数（第 50–74 行）→ 主函数** `search`**（第 77–119 行）**。下面用 slide 7 贯穿讲解：T1 = 50 TB，窗口 09:00–15:00；主路径容量 100 Gbps，12:00 前被他人占了 60，只剩 40。

## 1. 数据结构（第 22–47 行）

- **常量（第 22–23 行）：** `BITS_PER_BYTE = 8`、`BITS_PER_GBIT = 1e9`。这是单位换算，不是业务参数，所以可以写在代码里。
- **两个类型别名（第 25–26 行）：** `Strategy` 是三条规则的名字，`BlockedBy` 是两种被挡原因。
- `Placement`**（第 29–37 行）：** 一个方案 = 哪条传输、走哪条路径、从几点到几点、多少 Gbps、按哪条规则选出、有没有被挡。它和 `Offer` 的区别是**带着路径**（第 4 步问答"placements 和 offers"一节讲过）。
- `dedupe`**（第 40–47 行）：** 开始时间和速率都相同的方案只留第一个。scheduling agent 看不到路径，两条路径上一模一样的时间和速率，对它来说就是同一个 offer。



## 2. 三个辅助函数（第 50–74 行）

`duration`**（第 50–51 行）：** 给定字节数和速率，算要传多久。

```
50 TB × 8 ÷ (40 × 10⁹) = 10000 秒 ≈ 2 小时 46 分 40 秒
```

`_fits`**（第 54–64 行）：** 判断"从 start 到 end，这条路径每个时间槽都能给出 gbps 吗"。逐个槽检查，有一个槽不够就返回 False。

- 用的是 ledger 的 `slots_covering` 和 `path_available`，和 `ledger.pending()` 是**同一套**槽换算。所以这里判断"放得下"的方案，到 reserve 时调用 `pending()` 也一定放得下，前提是期间账本没变。文档字符串第 10–11 行说的就是这个保证。
- `ignore_own=True` 时，假装我们自己一笔预订都没有，只看 observed。这是给后面的 `blocked` 用的：用来判断"挡住我们的是不是我们自己"。

`_max_rate_at`**（第 67–74 行）：** 从某个开始时间出发、在截止前传完，能维持的**最大速率**是多少。做法是从高到低逐档尝试（第 70 行 `reversed(rates)`），第一个同时满足"赶得上截止"和"容量放得下"的速率就是答案。一档都不行时返回 `None`。

## 3. 主函数 `search`（第 77–119 行），按 slide 7 走一遍

**① 裁剪时间窗（第 79–84 行）**

```
earliest = max(请求的最早开始, 现在, 账本起点)  = max(09:00, 09:00, 09:00) = 09:00
deadline = min(请求的最晚结束, 账本尽头)        = min(15:00, 次日 09:00)    = 15:00
```

不能早于现在开始，也不能超出账本看得到的范围。随后检查两种明显不行的情况：

- 最早开始已经在账本尽头之后 → `beyond_horizon`；
- 窗口已经过去了 → `no_capacity`。

**② 候选速率（第 86–87 行）**

路径上最窄一跳的配置容量是 100，按步长 10 取档：`rates = [10, 20, ..., 100]`。

**③ 候选开始时间（第 88–89 行）**

最早开始时刻，加上窗口内之后的每一个槽边界：09:00、09:15、09:30……14:45。只考虑这些时刻，是因为容量只会在槽边界上变化。

**④ 每个开始时间能维持的最大速率（第 90 行）**

```python
best = {s: r for s in starts if (r := _max_rate_at(...))}
```

`:=` 是"海象运算符"：计算 `_max_rate_at(...)` 的结果，赋值给 `r`，同时把这个值用作 `if` 的判断条件。结果为 `None` 的开始时间会被过滤掉。这一行等价于：

```python
best = {}
for s in starts:
    r = _max_rate_at(...)
    if r:
        best[s] = r
```

slide 7 的结果大致是：


| 开始时间          | 最大速率 | 原因                                        |
| ------------- | ---- | ----------------------------------------- |
| 09:00 … 11:45 | 40   | 12:00 前只剩 40                              |
| 12:00 … 13:45 | 100  | 12:00 后全空；100 Gbps 只要 1 小时 07 分，赶得上 15:00 |
| 14:00 之后      | 没有   | 剩下不到 1 小时，100 Gbps 也传不完                   |


`best` 为空时返回 `no_capacity`（第 91–92 行）。

**⑤ 用三条规则各挑一个（第 103–110 行）**


| 规则               | 代码                                             | slide 7 结果                |
| ---------------- | ---------------------------------------------- | ------------------------- |
| `earliest_start` | `s1 = min(best)`：最早的开始时间，配它的最大速率               | a1：09:00 @ 40 → 11:46:40  |
| `max_rate`       | `top = max(best.values())`，`s2` = 达到 top 的最早时间 | a2：12:00 @ 100 → 13:06:40 |
| `min_rate`       | `r3`：从 s1 出发，**从低到高**找第一个赶得上截止的速率              | a3：09:00 @ 20 → 14:33:20  |


`r3` 那一行（第 106–107 行）用 `next(...)` 取生成器里第一个满足条件的值。10 Gbps 要 11 小时，赶不上；20 Gbps 要 5 小时 33 分，赶得上，就是它。条件里的 `r <= best[s1]` 保证不会超过 s1 时刻能给出的最大速率。由于 `best[s1]` 本身一定满足条件，`next` 一定能找到值，不会报错。

**⑥ 判断被谁挡住（第 94–98 行的** `blocked`**）**

只对 a1、a2 判断，因为它们都取了"能给的最大速率"；a3 的低速是主动选择的，不算被挡（第 110 行直接传 `None`）。

- 速率已经是最高档（a2 的 100）→ 没被挡，`None`。
- 否则用 `ignore_own=True` 再算一次"如果没有我们自己的预订，最多能给多少"：
  - 能给得更多 → 是**我们自己的预订**挡住了 → `own_commitment`；
  - 也给不了更多 → 是**外部流量**挡住了 → `foreign_traffic`。

a1：不算我们自己的预订，09:00 起仍然只有 40（他人占了 60）→ `foreign_traffic`。

这和 ledger 里 `InsufficientCapacity.blocked_by` 的判断逻辑一致，只是这里换成在"速率"上比较。

**⑦ 生成、去重、过滤（第 100–101、108–118 行）**

- `make`：根据开始时间和速率构造 `Placement`，结束时间 = 开始 + `duration`。
- `dedupe`：三条规则可能选出同一个方案。例如网络完全空闲时，"最早开始"和"最高速率"都是 09:00 @ 100，只保留一个。
- 如果请求声明了 `min_useful_rate_gbps`，去掉低于它的方案；全被去掉时返回 `below_min_useful_rate`。

`blocked` 和 `make` 是定义在 `search` **内部**的函数（闭包），可以直接使用外层的 `req`、`path`、`ledger`、`rates`，调用时就不用再一一传参。

## 现在的局限

- **只有恒定速率。** 每个方案全程一个速率；不会给出"12:00 前 40、之后 100"这种多段方案，虽然 `Offer.rate_profile` 是支持多段的。
- **开始时间只取槽边界**（加上最早开始那一刻）。
- `divisible` **字段还没用上。** 能拆分的传输可以拆到多条路径上，那是第 8 步多路径增容的事。
- **三条规则是写死的。** 以后可以放到可替换的 policy 后面，这也是 10/15 会议讨论的"offer 生成"可能用 AI 的位置。
- **计算量是穷举。** 开始时间 × 速率档 × 时间槽 × 链路，demo 规模没有问题，规模变大要优化。

三个都对得上 `search` 的参数：

```python
def search(ledger: CapacityLedger, path: Path, req: TransferRequest, now: datetime, rate_step: float)
#          账本                     路径         传输需求
```



## 1. 账本 = `ledger`，类型是 `CapacityLedger`

就是第 2 步的 [ledger.py](../../src/lib/network_agent/ledger.py)：每条有向链路 × 每个时间槽，记着 observed、own，算出 available。`search` 只**读**它（`path_available`、`observed`、`slots_covering`），不写。

## 2. 路径 = `path`，是 src 到 dst 的**完整**路径

类型是 `Path`，即有向链路 id 组成的元组（[topology.py](../../src/lib/network_agent/topology.py) 第 53 行），从源端点一直到目的端点：

```python
("L1:anl-dtn01>esnet-chi", "L2:esnet-chi>esnet-atl", "L3:esnet-atl>ornl-esgf")
#  第 1 跳                   第 2 跳                   第 3 跳
#  anl-dtn01 ──────────────► esnet-chi ─────────────► esnet-atl ─────────────► ornl-esgf
```

它来自 `topology.paths(tr.src, tr.dst, k)`：`refresh_if_stale` 节点为每条传输找出最多 k 条完整的候选路径，`find_placements` 节点再对每条路径分别调用一次 `search`。

`search` 本身不检查路径是否首尾相连、是否从 src 到 dst。它只把路径看作"要同时满足的一组链路"，对每个时间槽取这组链路的最小可用容量（木桶效应）。所以理论上传一段子路径进去，它也能算，但图里从来不这样用。

## 3. 传输需求 = `req`，类型是 `TransferRequest`

就是第 1 步定义的消息（[schemas.py](../../src/lib/network_agent/schemas.py) 里的 `TransferRequest`），也是 scheduling agent 在 `QuoteRequest.bundle` 里发来的每一项。slide 7 的 T1：

```python
TransferRequest(
    id="T1",                       # 传输 id
    workflow_id="WF-1",            # 属于哪个 workflow
    priority=1,                    # 优先级，越大越重要
    src="anl-dtn01",               # 源端点（拓扑里的节点）
    dst="ornl-esgf",               # 目的端点
    bytes=50 * 10**12,             # 50 TB
    is_estimate=False,             # 大小是否只是估计值
    divisible=False,               # 能否拆成多段 / 多路径
    window=TimeWindow(earliest_start=09:00, latest_finish=15:00),   # 时间窗
    min_useful_rate_gbps=None,     # 可选：低于这个速率的方案没有意义
)
```

它描述的是"要什么"，不包含"怎么走"：src 和 dst 是端点，不是路径；字节数和时间窗是需求，不是速率。选路径、定速率、定开始时间，正是 `search` 的工作。

`search` 实际用到的字段只有：`id`、`bytes`、`window`、`min_useful_rate_gbps`。`src`/`dst` 已经在上一步用来找路径；`priority`、`workflow_id`、`divisible`、`is_estimate` 目前还没用上：

- `priority` 和 `workflow_id` 主要给 scheduling agent 做跨 workflow 仲裁用；
- `divisible` 留给第 8 步多路径拆分；
- `is_estimate` 留给运行时用实际大小 refine。

> EPS_GBPS是啥

`EPS_GBPS = 1e-9`**（10⁻⁹ Gbps）是浮点数比较时用的容差。** EPS 是 epsilon（ε）的缩写，数学里常用来表示"一个很小的量"。

## 为什么需要它

计算机里的小数（float）用二进制存储，很多十进制小数存不精确，加减之后会带一点点误差：

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
```

放到账本里就会出问题。例如可用容量经过几次加减，本来应该正好是 0.3，算出来却是 `0.2999999999999943`；请求要 0.3：

```python
>>> need, avail = 0.3, 100 - 99.9 + 0.2
>>> need > avail          # 不加容差
True                      # 判定"不够"——其实刚好够，只是差了 10⁻¹⁴ 的舍入误差
```

加上容差后，比较的是 `need > avail + EPS_GBPS`：只有超出的部分大于 10⁻⁹ Gbps，才算真的不够。这么小的量远远小于任何有物理意义的带宽，所以既能吸收舍入误差，又不会放过真正的超额。

## 在哪里用到

凡是"带宽够不够"的比较都加了它：


| 位置                   | 比较                          |
| -------------------- | --------------------------- |
| ledger.py 第 151 行    | `pending()`：需要的是否超过可用       |
| ledger.py 第 153 行    | 判断被谁挡住：不算我们自己时够不够           |
| placement.py 第 62 行  | `_fits()`：这个槽放不放得下          |
| placement.py 第 114 行 | 是否达到 `min_useful_rate`      |
| sense.py 第 58 行      | mock SENSE 准入：是否超过 headroom |


它定义在 ledger.py 里，placement.py 和 sense.py 从那里 import，所以全项目用的是同一个容差：账本判断"放得下"和 SENSE 判断"放得下"的标准一致，不会出现一边说够、一边说不够。

## 为什么可以写死在代码里

CLAUDE.md 规定决定实验结果的参数只能来自 config。`EPS_GBPS` 不属于这类参数：它不是业务上的取舍（不像 `slot_seconds` 那样会改变报价结果），只是为了让浮点比较正确的数值技巧。注释"浮点比较容差，不是业务参数"就是在说明这一点。

> 为什么offer里不带path

**因为路径是 network agent 内部的决定，scheduling agent 既不需要知道，也不该依赖它。** offer 里只放对方做决策要用的东西：什么时候开始、多快、什么时候传完、有没有被挡。

## 1. slide 6 的分工原则："传需求，不传方案"

slide 6 原话："Not 'give me 40 Gbps' but 'these 5 TB must start after t1 and end before t2.' How much bandwidth to use, and when, is the network agent's decision, because it is the only one that can see the capacity curve."

两个 agent 各自用自己那一层的语言思考（slide 4）：


|                  | 思考的单位             | 关心的问题                  |
| ---------------- | ----------------- | ---------------------- |
| scheduling agent | DAG、依赖、截止时间、优先级   | 这条传输什么时候能完成？会不会拖累下游任务？ |
| network agent    | 链路、带宽、时间窗、circuit | 走哪条路？占哪些链路的哪些时段？       |


scheduling agent 选 a1 还是 a2，依据的是"什么时候开始、什么时候完成、占多少资源"，和走 L2 还是走 L4/L5 无关。

## 2. 路径以后可能会变，而承诺不变

slide 24 的设计里，故障发生后的恢复是在已有的 circuit 内部改路由或调速率，目标是 30 秒内修复；图 B 的本地修复也可能把流量换到别的路径上。只要还能按时完成，对 scheduling agent 发出的是 `repaired`，承诺照旧成立。

如果 offer 里带了路径，scheduling agent 就可能依赖它，比如记录下来、拿去做判断。一旦我们换了路径，就得通知它、它还得跟着改。不带路径，这部分变化就完全留在 network agent 内部。

## 3. 路径 id 对外面没有意义

`"L2:esnet-chi>esnet-atl"` 是我们自己拓扑里的编号，出了 network agent 就没人认识。跨机构时，各个网络运营方通常也不愿意把内部拓扑暴露给别人。

## 那 reserve 时怎么知道走哪条路？

靠 `offer_id`。`respond` 节点把 `offer_id → Placement`（带路径）记进 context 的 `offer_book`；scheduling agent 回来 reserve 时只报 offer_id，第 5a 步再从 `offer_book` 里查回路径。

```
对外：Offer(offer_id="q1/T1/2", 12:00 @ 100 Gbps, 13:06:40 完成)     ← 不带路径
内部：offer_book["q1/T1/2"] = Placement(path=(L1, L2, L3), ...)       ← 带路径
```

这也解释了 `dedupe` 为什么按 (开始时间, 速率) 去重：对方看不到路径，两条路径上时间和速率完全相同的方案，在它看来就是同一个 offer。

## 将来可能需要补充的情况

有一种需求是 scheduling agent 确实关心路径的：**两条传输不能同生共死**。比如主副本和备份不应该走同一条链路，免得一处故障两条都断。到那时也不必暴露路径本身，可以在请求里加一个约束，比如"与 T1 链路不相交"，由 network agent 在内部满足。这同样符合"传需求，不传方案"。

> “earliest = max(req.window.earliest_start, now, ledger.origin)”
>
> 难道ledger.origin还会更晚吗

**正常运行时不会。这一项是防御性的兜底，正常情况下是多余的。**

## 为什么正常情况下 origin 不会晚于 now

账本创建时，把传入的时刻向下对齐到槽边界作为 origin（第 2 步：09:05 → 09:00）。所以：

```
origin（09:00） ≤ 创建账本的时刻（09:05） ≤ 之后任何一次报价的 now
```

以后加上"推进时间窗"（slide 23 的 advance the frontier），origin 会往前挪，但挪到的也是"当前时刻向下对齐"，仍然不晚于 now。

## 那什么时候会晚于 now

只有**时钟用错**的时候：调用方传入的 `now` 早于账本的起点。例如测试里账本从 09:00 开始，却用 `now=08:00` 发起报价；或者模拟时钟和账本各自起点不一致。

这时如果不加这一项，`earliest` 会是 08:00，接下来调用 `ledger.slots_covering(08:00, ...)` 会直接抛出 `OutOfHorizon`，整次报价失败。加上 `ledger.origin` 之后，`earliest` 被抬到 09:00，报价照常进行。

graphs/protocol.py 第 65 行 `refresh_if_stale` 里有一模一样的写法，作用相同。

## 这样兜底好不好，值得商榷

它的好处是不会崩，坏处是**把错误藏起来了**：`now` 早于账本起点，本身说明调用方的时钟有问题，悄悄抬高之后，这个问题就不容易被发现。

另一种做法是在入口直接检查：如果 `now < ledger.origin` 就报错，让时钟问题立刻暴露；`search` 里则只保留 `max(earliest_start, now)`。两种都合理，前者偏"容错"，后者偏"严格"。

**这是 network agent 为 T1（anl-n02 → ornl-n01）找到的两条候选路线，以及报价时每条路线在各个时段能给出多少带宽。**

## 每一行的含义

**`path1:`、`path2:` 这一行是路线本身。** 箭头上的 `L1`、`L2` 是经过的物理链路，箭头方向就是数据流动的方向：

```
path1（主路径，3 跳）：anl-n02 → esnet-atl → esnet-chi → ornl-n01
                          L1           L2            L3
path2（绕行，4 跳）：  anl-n02 → esnet-atl → esnet-nash → esnet-chi → ornl-n01
                          L1           L4            L5            L3
```

两条路线是 `refresh_if_stale` 节点调用 `topology.paths(anl-n02, ornl-n01, k=3)` 找出来的。上限是 3 条，但这张拓扑上从 anl-n02 到 ornl-n01 只有这 2 条无环路线。区别只在中间一段：path1 直接走 L2，path2 绕经 esnet-nash。两者共用第一跳 L1 和最后一跳 L3。

**缩进的行是这条路线在各时段的可用容量。** 每一行的格式是：

```
时段            可用容量     瓶颈（限制这个值的那一跳）
09:00–12:00     40 Gbps     L2:esnet-atl>esnet-chi
```

- **可用容量**：在这个时段内，整条路线最多还能给 T1 多少带宽。它等于沿途每一跳的"可用 = 观测 − 我们自己已经预订的"取最小值（木桶效应），也就是标题里说的 narrowest hop。
- **瓶颈**：取到最小值的是哪一跳。
- 只列到 15:00，因为 T1 的窗口是 09:00–15:00。
- 可用容量相同的连续时段合并成一行，所以 path2 全天只有一行。

数字是**刷新之后**的：账本在报价前已经从 telemetry 拉了实测值（after refresh），不是拓扑里的配置容量。

## 逐条解读

**path1**

| 时段 | 可用 | 原因 |
| --- | --- | --- |
| 09:00–12:00 | 40 | L2 配置 100，被他人占了 60（`Foreign traffic` 那一行），剩 40；L1、L3 都还有 100，所以瓶颈是 L2 |
| 12:00–15:00 | 100 | 他人占用结束，三跳都是 100 |

12:00 之后显示的"瓶颈 L1"并不表示 L1 有问题。三跳都是 100，打成平手时，程序按链路 id 的字母顺序取了第一个。

**path2**

| 时段 | 可用 | 原因 |
| --- | --- | --- |
| 09:00–15:00 | 40 | L4、L5 配置容量只有 40；path2 不经过 L2，所以完全不受那 60 Gbps 外部流量影响 |

这里的瓶颈同样是平手：L4 和 L5 都是 40，按字母顺序显示 L4。

## 这两条路线和下面的报价结果是什么关系

报价时，`find_placements` 对两条路线**分别**做放置搜索，每条都按三条规则各算出方案，最后合在一起去重：

- path1 算出：09:00 @ 40、12:00 @ 100、09:00 @ 20 → 就是 a1、a2、a3；
- path2 全天只有 40，算出：09:00 @ 40、09:00 @ 40、09:00 @ 20 → 和 path1 的 a1、a3 完全相同，被去重掉。

所以 test1 的三个 offer 都标着 `[path1, ...]`。到 test2 时，path1 早上能给 80，path2 的 09:00 @ 40 不再和任何方案重复，就作为第 4 个 offer 保留了下来。

## 为什么要把路线和容量打印出来

这部分信息**不会**发给 scheduling agent（offer 里不带路径）。打印出来只是为了演示时让人看清楚：offer 上的那些数字是从哪条路、哪个时段、被哪一跳限制而来的。
