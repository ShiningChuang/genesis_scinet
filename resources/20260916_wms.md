- 来源一：`resources/slides/Pegasus_HTCondor_SENSE_Technical_Overview.pptx`（Sourabha 整理，12 页）
- 来源二：Linxuan 与 Sourabha 的 WhatsApp 讨论（2026-09-15 至 09-16）
- 整理时间：2026-09-16
- 文档性质：对 slides 与讨论的结构化整理。slides 的引用来源保留在各节末尾；讨论中的判断若与 slides 不一致，单独标出，**不代表已核实的结论**。

## 一句话结论

现有系统各管一段：**Pegasus 决定"做什么、在哪做"，HTCondor 分配计算槽位，SENSE 预约网络服务，DMM 在 Rucio 场景下做了网络侧闭环**。但没有任何现成组件把 workflow 的依赖与 deadline、计算状态、网络状态**放进同一个决策环**。我们的两个 agent 与 Telemetry Agent 坐在这条缝里。

---

## 1. 三个系统各管什么


| 系统           | 角色          | 做的事                                                 |
| ------------ | ----------- | --------------------------------------------------- |
| **Pegasus**  | 规划 workflow | 把抽象 task 映射到执行站点，插入 transfer / cleanup 作业，产出可执行 DAG |
| **HTCondor** | 运行时资源管理     | DAGMan 释放就绪作业；Schedd 排队；Negotiator 把作业匹配到槽位         |
| **SENSE**    | 网络服务编排      | 按端点、带宽 / QoS、时间窗请求，然后 provision 网络服务                |


决策是一条流水线，**不是一个 scheduler**：

```
抽象 workflow → Pegasus Mapper → 可执行 DAG + .sub → DAGMan → Schedd 队列 → Negotiator → 槽位
   语义            规划：站点/数据/图变换     依赖/重试        持久队列      ClassAd 匹配    执行
```

两处重要澄清：

- **Pegasus 映射到的是候选站点**，不是"17 号机器的 0 号核"。具体机器和槽位由之后的 HTCondor matchmaking 决定
- **SENSE 不在计算分配路径上**。它在传输开始前预约网络连接与容量；真正搬字节的仍是 data mover

> Refs: [P1] §2.3; [P3] Pegasus Mapping 5.1.3; [H2] HTCondor admin manual.



## 2. HTCondor 如何分配计算

作业声明需求，执行点广播资源，Negotiator 撮合。

```
# 作业 .sub
request_cpus = 4
request_memory = 8GB
request_disk = 20GB
requirements = (Arch == "X86_64")

# 槽位 ClassAd（示意）
Name = "slot1@node17"   SlotType = "Partitionable"
Cpus = 32   Memory = 131072   State = "Unclaimed"   Activity = "Idle"
```

三步：**广播**（`condor_startd` 周期性把槽位 ClassAd 发给 Collector）→ **匹配**（Negotiator 从 Collector 取槽位，与排队作业撮合，同时执行策略与优先级）→ **切分并运行**（可分割槽位按请求切出动态槽位，Schedd 认领，Starter 启动作业）。

**讨论中的纠正**：最初的说法是"negotiator 决定最佳 compute / network 资源"。核对后确认 **Negotiator 只匹配计算槽位**，网络不是它的一等资源。

> Refs: [H2]; [H3] Execution Point / partitionable slot; [H4] Job scheduling & ClassAds.



## 3. HTCondor 如何监控计算可用性

`condor_startd` → `condor_collector`（ClassAd 仓库）→ `condor_negotiator`（消费并匹配）。

- **内置属性**：Cpus、Memory、Disk、State、Activity、LoadAvg、认领状态、自定义资源
- **运维视图**：`condor_status` 查 Collector，`condor_q` 查 Schedd 队列——**是调度器与资源状态，不是 WAN 路径遥测**
- **更新语义**：守护进程周期性发送；Startd Cron 可发布动态属性；hook 可强制立即更新

**可以注入自定义网络指标**：

```
STARTD_CRON_JOBLIST = NET
STARTD_CRON_NET_EXECUTABLE = /opt/bin/net_metrics.sh
STARTD_CRON_NET_PERIOD = 5s
# 脚本输出成为 ClassAd 属性
FreeNICMbps = 18400
WAN_RTT_ms  = 3.7

# 作业可以用它们做约束与排序
requirements = (FreeNICMbps >= 10000)
rank = FreeNICMbps - 100*WAN_RTT_ms
```

但**探针要自己写、指标含义要自己定义**，而且这只影响"作业放到哪台机器"，**不产生任何网络预约**。

> Refs: [H2] Collector + Negotiator; [H5] Startd Cron / daemon ClassAd hooks.



## 4. Pegasus 一次运行的端到端流程

规划主要在执行前完成，运行时由 DAGMan + HTCondor 驱动。


| 阶段  | 步骤            | 内容                                                                   |
| --- | ------------- | -------------------------------------------------------------------- |
| 规划  | 1 抽象 DAG      | task、依赖、输入输出逻辑文件名                                                    |
|     | 2 目录查询        | Replica：数据位置；Transformation：可执行文件；Site：候选资源                          |
|     | 3 规划变换        | 复用 / 剪枝 · 站点选择 · 聚簇                                                  |
|     | 4 插入辅助作业      | create-dir · stage_in · stage_inter · stage_out · cleanup · register |
|     | 5 代码生成        | HTCondor DAG + 每个作业的 submit 文件                                       |
| 运行  | 6 DAGMan      | 父节点成功才释放子节点                                                          |
|     | 7 HTCondor 分配 | Schedd 队列 → Negotiator → 槽位 → Starter                                |
|     | 8 监控 / 恢复     | Kickstart 溯源 · monitord 数据库 · 重试 · rescue DAG / replan               |


> Refs: [P1] §§2, 4–7; [P2] Pegasus 5.1.3 Introduction; [P3] Mapping; [P4] Monitoring.



## 5. 数据传输如何处理

Pegasus 把传输表达为 **workflow 里的作业**；默认 `condorio` 模式用 HTCondor File I/O 处理提交主机 ↔ 工作节点这一跳。

```
远端输入存储 ─stage_in 作业(pegasus-transfer)→ 提交主机 ─HTCondor File I/O→ 工作节点
工作节点 ─HTCondor File I/O→ 提交主机 ─stage_out 作业→ 输出存储
```

```
should_transfer_files = YES
when_to_transfer_output = ON_EXIT
transfer_input_files = input.dat, model.bin
transfer_output_files = result.dat

pegasus.data.configuration = condorio   # 或 nonsharedfs / sharedfs
```

**网络语义**：搬运工具使用**已有的 IP 网络**（HTCondor 的可靠 TCP / CEDAR，或 HTTP 等协议插件）。**不预约 L2 电路，也不保证 WAN 带宽。**

**讨论补充**：Mapper 在两个 task 之间需要传输时会插入一个独立的"data transfer job"。这意味着**计算调度与传输调度在结构上已经可以分开**——我们设计里的 S0（task DAG → transfer 集合）与之重合，应直接读 Mapper 产出的可执行 workflow，不再自己拆。

> Refs: [P5] Pegasus Data Transfers 5.1.3; [H6] HTCondor File Transfer; [H7] HTCondor ReliSock.



## 6. "实时指标"有哪些，谁在用

**有多个监控平面，但它们不会自动汇合成一个全局调度器。**


| 层              | 观测什么                                           | 谁消费                                       | 是否用于调度 / 控制                                |
| -------------- | ---------------------------------------------- | ----------------------------------------- | ------------------------------------------ |
| Pegasus        | DAG / 作业状态、时间、退出码、主机、溯源                        | `pegasus-monitord` → 数据库 / 仪表板 / analyzer | **否**。主要用于监控与调试，规划器不用                      |
| HTCondor       | 槽位状态、CPU / 内存 / 磁盘、负载、认领；自定义 ClassAd 属性        | Collector + Negotiator + `condor_status`  | **是**：匹配可使用广播属性 / Requirements / Rank      |
| Prometheus     | 从 exporter 抓取的时序；Node Exporter：CPU、文件系统、网卡字节数等 | PromQL / Grafana / 自定义控制器                 | 本身不是调度器，其他服务可消费                            |
| SENSE / SiteRM | 资源模型、服务状态、暴露的网络能力；部署监控                         | Orchestrator + RM / 监控栈                   | 用于计算与 provision 网络服务；API 不是通用的 RTT / 队列遥测源 |
| DMM 原型         | 主机网卡吞吐 + FTS 传输指标 + Rucio 优先级                  | DMM 控制器                                   | **是**：据实时观测调整 SENSE 带宽与 FTS 并发             |


```
rate(node_network_receive_bytes_total{device="eth0"}[1m]) * 8   # 过去一分钟接收 bit/s
```

"实时"是采样的、周期性的，不是瞬时完美视图；新鲜度与语义取决于 exporter 和更新间隔。

**讨论中的确认**：Pegasus Mapper 的站点选择**不使用任何实时遥测**，只从给定站点列表里挑。

> Refs: [P4]; [H2, H5]; [M1] Prometheus Node Exporter; [D1] Arora et al. 2025 §3.2.



## 7. 已有的"智能调度"先例：DMM

DMM **不是 Pegasus 集成**，而是 Rucio、SENSE、FTS 与遥测之间的控制器。

```
Rucio(传输规则) → DMM ─REST→ SENSE：provision / 调整网络电路
                     ─REST→ FTS：调整活跃传输并发数
      反馈 ← Prometheus / Node Exporter（主机网卡吞吐）
      反馈 ← CERN MonIT / FTS（失败 · 重试 · 性能）
```

- **决策输入**：源 / 目的站点、总传输量、规则优先级、端点容量
- **优化**：LP，在各站点端口容量约束下最大化优先级加权带宽
- **闭环**：周期性查询 Prometheus 监控吞吐，可调整 SENSE 分配与 FTS 并发

> Ref: [D1] Arora et al., "Data Movement Manager (DMM) for the SENSE-Rucio Interoperation Prototype," arXiv:2508.00792v1, §§2–3.



## 8. SENSE：应用实际请求的是什么

SENSE provision 网络服务，**自己不拷贝文件**。

```
POST /instance/{siUUID}
{ "service": "dnc", "alias": "campaign-17-anl-ornl",
  "data": { "type": "Multi-Path P2P VLAN",
    "connections": [{ "name": "Connection 1",
      "terminals": [ {"uri": "urn:example:ANL:port1", "vlan_tag": "any"},
                     {"uri": "urn:example:ORNL:port1", "vlan_tag": "any"} ],
      "bandwidth": { "capacity": "10000", "qos_class": "guaranteedCapped" },
      "schedule": { "duration": "1h" } }] } }
```


| 编码了                                              | 没编码                                                            |
| ------------------------------------------------ | -------------------------------------------------------------- |
| 具体端点 · VLAN / 地址控制 · 带宽容量 · QoS 类 · 时间表 · 可选路径约束 | 可执行文件 · task 依赖 · CPU 需求 · **没有内置的"文件 deadline"字段**；SENSE 不搬文件 |


典型生命周期：

```
GET  /instance                 # 领 siUUID
POST /instance/{id}            # 编译 intent
PUT  /instance/{id}/provision  # 下发
GET  /instance/{id}/status     # 等待 READY
PUT  /instance/{id}/cancel     # 撤销
```

> Refs: [S1] SENSE-O Intent API 2.0.4; [S2] sense-o-py-client `workflow_interact.py`.



## 9. SENSE vs HTCondor：尤其在 deadline 上


| 问题          | HTCondor                                                          | SENSE                                               |
| ----------- | ----------------------------------------------------------------- | --------------------------------------------------- |
| 主要资源        | 计算槽位 + 作业生命周期；内置文件搬运                                              | SENSE 管理域之间的网络服务 / 连通性                              |
| 分配单位        | 作业 ClassAd ↔ 机器 / 槽位 ClassAd                                      | 端点 + 容量 / QoS + 时间表 + 路径约束                          |
| 网络路径        | 用已有 IP 连通性；不预约 WAN 路径                                             | 在支持处可 provision L2 / L3 服务、VLAN / 路径资源              |
| 传输协议        | CEDAR / ReliSock TCP，或 HTTP 等 URL 插件                              | 不是 data mover；FTS / Globus / XRootD / TCP 在预约的服务上传  |
| deadline 语义 | `deferral_time` / `deferral_window` 等作业时间控制；**无保证的文件传输 deadline** | 连接时间窗 + 可预约 / 已分配容量；**上层控制器负责把文件 deadline 换算成所需速率** |
| 带宽保证        | 无原生端到端 WAN 带宽预约                                                   | 可请求 QoS / 带宽分配；具体保证取决于部署、QoS 类与路径                   |
| 实时自适应       | 按当前槽位广播调度；WAN 遥测不是原生调度输入                                          | 服务可修改；DMM 展示了遥测驱动的分配调整                              |


例子：500 GB 须在 10 分钟内到达 → 理论净荷速率 ≈ 6.67 Gb/s。HTCondor 无法预约这个速率；控制器可以向 SENSE 请求约 8–10 Gb/s（若可行），再启动 data mover。

> 注意：SENSE 的 `schedule` 是**网络服务时间窗**，不是 workflow task 的 deadline。必须由 workflow / 控制器把"字节数 + deadline + 计算与运行时约束"翻译成可行的网络请求。

> Refs: [H8] HTCondor deferral; [S1, S2]; [D1].



## 10. 缺失的联合调度器——也就是研究机会

**零件都在，端到端的决策环不在 stock Pegasus + HTCondor 里。**

```
workflow 事实（字节数 · DAG · deadline）─┐
计算事实（HTCondor 槽位广播）           ├→ 联合控制器 / 网络感知调度器
网络事实（Prometheus / SENSE 状态）    ─┘      ├ 选执行站点与资源请求
                                              ├ 预约 / 修改 SENSE 网络服务
                                              └ 启动传输 / 作业；观测；重规划
```


|                | 现状                                                                      |
| -------------- | ----------------------------------------------------------------------- |
| Stock Pegasus  | 有外部 site selector 钩子和 JIT / 重规划，但常规站点映射**不是**基于实时 WAN 流量 / 队列 / RTT 的闭环 |
| Stock HTCondor | 已做动态计算匹配。自定义指标能影响匹配，但**不产生网络预约**                                        |
| DMM 先例         | 证明网络侧可行：优先级 + 遥测 → SENSE 带宽 + FTS 并发。但以 Rucio 为中心，不以 Pegasus 为中心        |


> Refs: [P3] external site selector; [H5]; [D1]; [S1].

## 11. 讨论要点（与 Sourabha，09-15 至 09-16）



### 11.1 起点：agent 是不是只是 WMS 的一部分

Sourabha 最初的担心是：调度、映射、监控 Pegasus 都已提供，我们提出的 agent 看起来是 WMS 的一部分，而非独立实体。

**结论**：重叠是真的，但只在 **workflow 侧**（DAG 映射、执行、任务级监控），这部分本来就不该重做，应复用。**网络侧没有**：带宽预约、时间轴容量账本、slack 推导、按网络容量的跨 workflow 仲裁、counter-offer、带宽下降或计算超时后的重排。

### 11.2 故障处理：Pegasus 有什么，缺什么

- **Pegasus 有**：备选站点、重试、workflow checkpoint、rescue DAG
- **缺的是 workflow 级重排**：Sourabha 读到论文说故障后需要**用户**重新规划 workflow，双方同意"这不是好的故障处理方式"
- **我们的设计**：network agent 先自修（快回路）；修不了则发 `at_risk`，scheduling agent 依据 Workflow Runtime DAG 分析依赖、重排 workflow，再以 quote / hold / commit 下发新方案并释放旧方案

> **待核对的不一致**：slides 第 11 页写 Pegasus "有外部 site selector 钩子和 JIT / 重规划"，第 5 页写"rescue DAG / replan"；而讨论依据的是 2015 年论文"用户需重新规划"。需要核实 Pegasus 5.x 的 replan 到底是自动的还是需人工触发，**不能拿"Pegasus 不会重排"作为主要卖点**。



### 11.3 定位：不只是更好的 scheduler

Sourabha 一度总结为"我们基本是在设计一个更强的 workflow scheduler"。讨论后的定位是：

- **现有 WMS 不与真实网络对话**：不采集运行时网络遥测，也不自动做预约
- 因此我们同时在做 **SENSE 与 WMS 之间的中间层**——这里正是现有系统"断开"的地方



### 11.4 通用性：多个 WMS 共享一张网络

- agent 要**兼容多种 WMS**，Pegasus 只是参考样例，scheduler 必须通用
- 真实网络上同时跑着多个 WMS；**每个 WMS 只看得见自己的 workflow**，而我们的 scheduling agent 能看到所有 workflow 并在它们之间仲裁
- 双方一致同意这是必须强调的点



### 11.5 架构更新：Telemetry Agent 与 Workflow Runtime DAG

Linxuan 修改了 Overview（见 slides 截图 "Every observation goes through one telemetry service"）：

- 新增**采集层**：所有观测经过同一个服务，负责接入、时间对齐、存储、订阅；scheduling agent 与 network agent 通过订阅获取数据
- 新增 **Workflow Runtime DAG**：维护计算、网络、设备三类节点的运行时信息，供 scheduling agent 决策
- 现版本下，带宽下降或 task / 设备超时，scheduling agent 都能据此处理
- Sourabha 认为这让遥测服务的必要性更清楚；**命名定为 "Telemetry Agent"**——既可以只是服务，agent 形式让它能与其他 agent 通信、按需请求额外指标



### 11.6 Sourabha 的底线总结（09-16）

> 现有系统**不基于实时遥测同时预约链路和计算**：要么是链路（DMM + SENSE），要么是计算（Pegasus / HTCondor）。
> 所以目标是构建一个**统一系统**，能预约两者，并处理故障处理、报告等更多功能。

## 12. 对我们设计的影响


| 影响                            | 动作                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| S0 拆解与副本选择与 Pegasus Mapper 重合 | scheduling agent 直接读 Mapper 产出的可执行 workflow（传输作业已插入）                                     |
| 计算侧遥测已有来源                     | Telemetry Agent 的计算侧接 `pegasus-monitord` 与 HTCondor Collector，不重新采集                      |
| HTCondor 可注入自定义 ClassAd 属性    | 可作为把网络状态反馈给计算匹配的一条通道（如 `FreeNICMbps`），但不能替代网络预约                                          |
| DMM 是最近的先例                    | 主 baseline 仍选贪心预约（B1）；需讲清我们相对 DMM 多出的部分：跨 workflow 依赖、deadline 与 slack、计算与网络的联合时间线、多 WMS |
| "agent 是否属于 WMS"              | 是部署选择而非贡献问题；可通过 Pegasus 外部 site selector 等钩子接入，但必须保持对多 WMS 通用                            |




### 一处需要和 KK 对齐的张力

Sourabha 的底线总结是"**统一系统预约链路和计算两者**"。而 0908 会议与我们此前的设计边界是：**规划计算的时间，不分配计算的资源**（GPU 分配归 WMS / 集群调度器）。

两种口径对项目范围影响很大：

- **只规划计算时间**：范围可控，依赖 WMS 提供预计启动时间与排队行为，贡献集中在网络侧与联合时间线
- **同时预约计算**：要和 HTCondor Negotiator 或站点调度器交互，工作量与接入难度显著上升，但更贴近"统一系统"的叙事

建议在下次与 KK 讨论时明确选定其一。
