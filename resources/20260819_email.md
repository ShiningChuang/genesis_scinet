## Revised verdict  
  
For SciNet Phase 1, the best overall choice is:  
  
**PydanticAI core + DBOS Python + PostgreSQL**  
  
Use PydanticAI as a thin, typed reasoning layer—not a multi-agent swarm. Use DBOS as the authoritative service-lifecycle engine.  
  
```text  
Workflow/instrument metadata  
            ↓  
       FastAPI ingress  
            ↓  
 DBOS durable workflow + PostgreSQL  
      ├─ deterministic validation  
      ├─ PydanticAI adviser  
      ├─ approval/policy gate  
      └─ typed SENSE adapter  
            ↓  
   SENSE Orchestrator → ESnet/RMs  
```  
  
PydanticAI’s native DBOS integration checkpoints model calls and external operations while keeping the workflow deterministic and recoverable. DBOS runs in-process and uses PostgreSQL instead of requiring a separate orchestration cluster. [PydanticAI–DBOS integration]([https://pydantic.dev/docs/ai/capabilities/durable_execution/dbos/](https://pydantic.dev/docs/ai/capabilities/durable_execution/dbos/))  
  
This is a better fit now because SENSE and ESnet own feasibility, path engineering, provisioning and network operations. SciNet’s job is to understand scientific demand, submit service intent, evaluate alternatives and measure outcomes. [SENSE architecture]([https://sense.es.net/architecture](https://sense.es.net/architecture))  
  
## Recommended toolset  
  
| Function | Choice |  
|---|---|  
| Agent layer | `pydantic-ai-slim[dbos]` |  
| Lifecycle engine | DBOS Python core |  
| Durable state | PostgreSQL |  
| Contracts | Pydantic v2 and JSON Schema |  
| API ingress/callbacks | FastAPI |  
| SENSE integration | HTTPX with a narrow typed client |  
| MRML/RDF support | RDFLib + pySHACL, only if the API exposes raw semantic models |  
| Authentication | Existing site OIDC/service credentials plus SENSE authorization |  
| Observability | OpenTelemetry exported to an existing Prometheus/Grafana/Tempo stack |  
| Testing | pytest, Hypothesis, Pydantic `TestModel`, Pydantic Evals and a SENSE stub |  
| Feature analysis | Polars or Pandas + DuckDB |  
| Initial forecasting | scikit-learn or XGBoost; PyTorch only after simpler baselines fail |  
| LLM | Small hosted model by default, stronger model only for low-confidence cases |  
  
DBOS provides persisted messages, events and waits, making it suitable for asynchronous SENSE callbacks, operator approval and provisioning status. [DBOS workflow communication]([https://docs.dbos.dev/python/tutorials/workflow-communication](https://docs.dbos.dev/python/tutorials/workflow-communication))  
  
## Agent boundary  
  
Start with one agent, not six:  
  
**Science Intent Adviser**  
  
- Converts workflow demand into a typed `ScienceWorkflowIntent`.  
- Proposes a `SenseServiceIntent`.  
- Ranks alternatives returned during negotiation.  
- Produces a confidence score and explanation.  
  
Add an optional **Outcome Evaluator** later.  
  
These should be deterministic software components, not agents:  
  
- Circuit Lifecycle Manager → DBOS workflow.  
- Authorization and quota checking → ordinary Python.  
- Anomaly thresholds → deterministic monitoring.  
- SENSE submission and polling → idempotent DBOS steps.  
- Recovery and protection → SENSE/ESnet.  
- Forecasting → conventional ML service.  
  
## SENSE tool surface  
  
Use direct typed functions rather than MCP during Phase 1:  
  
- `pull_resource_model`  
- `propagate_service_delta`  
- `commit_service_delta`  
- `query_service_status`  
- `modify_service`  
- `release_service`  
- `record_workflow_outcome`  
  
The published SENSE design distinguishes `propagate`, which validates or negotiates without provisioning, from `commit`, which initiates provisioning. Represent those as separate DBOS states, with explicit approval before `commit`. [SENSE model/delta paper]([https://www.es.net/assets/Uploads/76kkEi9wqPrVdrGK4bSFdg.pdf](https://www.es.net/assets/Uploads/76kkEi9wqPrVdrGK4bSFdg.pdf))  
  
## Do not add initially  
  
Avoid:  
  
- Microsoft Agent Framework, LangGraph or CrewAI.  
- PydanticAI’s general coding/research Harness capability bundle.  
- MCP around the privileged SENSE interface.  
- Kafka, Redis, Neo4j or a vector database.  
- Kubernetes solely for this application.  
- A full topology-level digital twin.  
- Self-hosted LLM inference unless GPU capacity already exists.  
- LLM-controlled provisioning or recovery.  
  
These add cost and attack surface without solving a current SciNet requirement.  
  
## Temporal decision  
  
Use Temporal instead of DBOS immediately if a project partner already operates a supported Temporal service; its marginal cost may then be lower.  
  
Otherwise, reconsider Temporal for Phase 2 if SciNet needs multi-cluster recovery, cross-language workers, advanced workflow visibility or independent multi-site operations. Running Temporal yourself adds deployment, security, monitoring, visibility and upgrade responsibilities. [Temporal self-hosting guide]([https://docs.temporal.io/self-hosted-guide](https://docs.temporal.io/self-hosted-guide))  
  
So the final recommendation is:  
  
> **Phase 1: PydanticAI core + DBOS + PostgreSQL.**  
**> Phase 2: retain PydanticAI and move lifecycle execution to Temporal only when operational requirements justify it.**

> ## Recommendation
>
> Use **Microsoft Agent Framework (Python), specifically graph-based Workflows**, as SciNet’s agentic harness.
>
> Back it with **Temporal OSS** for durable cross-site execution and place **OPA + the digital twin + a deterministic action broker** between every agent decision and the live network.
>
> ```
> Telemetry + workflow metadata
>             ↓
>       SciNet state graph
>             ↓
>  Microsoft Agent Framework
>  planner → predictors → candidate plan
>             ↓
>        Network digital twin
>             ↓
>  verifier → OPA policy gate
>             ↓
>  deterministic action broker
>             ↓
>  P4Runtime / gNMI / MPQUIC / DPU
>             ↓
>  monitor → verify outcome → rollback/learn
>
> ```
>
> Why MAF:
>
> - It combines AutoGen’s multi-agent model with Semantic Kernel’s typed workflows, middleware, state, telemetry, checkpointing, and human approval. Microsoft identifies it as their direct successor. [MAF overview](https://learn.microsoft.com/en-us/agent-framework/overview/)
> - Its workflow engine gives SciNet explicit graphs, typed routing, deterministic supersteps, parallel execution, and reliable checkpoints. [Workflow model](https://learn.microsoft.com/en-us/agent-framework/workflows/workflows)
> - It supports OpenAI, Azure, Anthropic, Ollama, local models, MCP, Python, .NET, and Go; the core is MIT-licensed. [Providers](https://learn.microsoft.com/en-us/agent-framework/agents/providers/), [license](https://github.com/microsoft/agent-framework/blob/main/LICENSE)
> - The Python framework is actively maintained; its changelog shows version 1.13.0 released July 30, 2026. [Changelog](https://github.com/microsoft/agent-framework/blob/main/python/CHANGELOG.md)
>
> Crucially, use **Workflows**, not MAF’s free-form “Harness Agent,” as the top-level controller. Agents should emit typed proposals—not network commands.
>
> ### Required safety boundary
>
> Each proposed action should carry:
>
> - `ScienceIntent`
> - `CandidatePlan`
> - `PredictedImpact`
> - `TwinEvidence`
> - `PolicyDecision`
> - `RollbackPlan`
> - `CommitReceipt`
>
> No live mutation occurs unless the digital twin, deterministic verifier, and policy engine all pass. OPA is well suited because it separates policy decisions from enforcement and provides auditable decision logs. [OPA](https://www.openpolicyagent.org/docs)
>
> Use P4Runtime only through an action broker with leases, idempotency keys, bounded changes, staged commits, and rollback. P4Runtime already provides controller roles, arbitration, batching, and atomicity semantics. [P4Runtime specification](https://p4.org/wp-content/uploads/sites/53/2024/10/P4Runtime-Spec-v1.4.1.html)
>
> ### Durable runtime
>
> Use Temporal as the authoritative execution ledger. It persists workflow state, retries failed activities, and resumes after crashes; its agent architecture explicitly separates deterministic orchestration from nondeterministic LLM and tool calls. [Temporal agent architecture](https://go.temporal.io/platform-hub/ai-engineering/ai-reference-architecture)
>
> MAF’s Durable Task extension is promising and self-hostable, but portions remain preview-grade, so I would not make it SciNet’s Phase-2 foundation yet. [MAF Durable Extension](https://learn.microsoft.com/en-us/agent-framework/integrations/durable-extension)
>
> ### Framework verdict
>
>
> | Candidate                     | Verdict                                                                              |
> | ----------------------------- | ------------------------------------------------------------------------------------ |
> | **Microsoft Agent Framework** | Best overall SciNet fit                                                              |
> | LangGraph                     | Strong runner-up for Python-first research experiments                               |
> | Temporal alone                | Best durable runtime, but not a complete agent framework                             |
> | OpenAI Agents SDK             | Excellent rapid prototyping and tracing; insufficient as the control-plane backbone  |
> | AutoGen                       | Avoid for a new build; MAF supersedes it and its distributed runtime is experimental |
> | NeMo Agent Toolkit            | Add later for profiling/evaluation, not as the primary controller                    |
> | CrewAI / Google ADK           | Better suited to application workflows than safety-critical network operations       |
>
>
> One non-negotiable: SciNet’s **≤5-second detection and ≤30-second recovery loop must not depend on an LLM**. Keep failure detection and pre-approved failover deterministic and local. The agentic layer should optimize, explain, simulate, and update policies—not perform protection switching in the fast path.
