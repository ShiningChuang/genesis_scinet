# Agent 中 LLM 的职责边界（上次 meeting 总结）



## 一、总体框架

**核心问题**：agent 为什么要调用 LLM？调用它做什么？

**三种决策方式共存**

- **确定性算法**：规则明确、可以直接计算的部分。
- **咨询 LLM**：规则覆盖不到的部分。
- **Reinforcement learning**：从运行结果中学习。第一阶段暂不考虑，后续引入。

**Agent 怎样使用 LLM**

- agent 会向 LLM 询问下一步怎么做，但**不是完全照做**，而是结合自身 rules 和 LLM 的回复再做决定。
- 决策所需的信息分三层：
  1. workflow 已经指定的信息；
  2. agent 已知 rules 能覆盖的信息；
  3. 剩下 agent 不知道的部分：agent 整理相关信息交给 LLM，由 LLM 根据见过的情况判断合适的选择。
- 分层升级：能用 rules 处理的用 rules；rules 处理不了的升级给 LLM；LLM 也处理不了的再升级给用户。

## 二、输入侧：把用户需求变成完整的 workflow

处理 operators 交来的需求，产出是一份信息完整的 workflow。

### ① Input normalization

- 用户可能只用自然语言描述需求。
- LLM 把它转成本系统的 workflow schema，即 workflow format 和相应取值。



### ② 约束推断

**(a) 推断用户给不出的参数**

- 用户往往给不出完整信息，例如"在这台 instrument 上，我没法告诉你会产生多少数据、需要多少带宽"。
- 这类信息可以从别人以前在同一台 instrument、其他场景下做过的实验历史中获得。
- LLM 还要结合当前网络状态，找到**既能满足需求、又不影响其他流量**的方案。

**(b) 把隐含约束 formalize**

- 某些设施有隐含约束，例如"样品不能过夜保存"。
- 来源包括设施的 user guide、instrument user manual 和以往信息。
- 这是**站点层面**的事：
  - 每个 site 有自己的 policies，需要 agent 去解析；
  - 每台 instrument 的 user manual 里有大量此类约束；
  - 网络一侧也有类似规则，例如某类 burst 会被如何处理。
- 能从历史信息获取的部分，已由 (a) 覆盖。

**Inferring 与 chasing**

- Inferring：LLM 自行推断。
- Chasing：缺少必需参数时，向 operators 反复追问。
- 二者交替进行：推断 → 向用户 confirm 并追问 → 继续推断。



## 三、Scheduling Agent

**不交给 LLM 的部分**：按 workflow 内部依赖计算 critical path，以及每个任务的 earliest start 和 latest finish。依赖关系在 workflow 中已经写明，用确定性算法即可。

### ③ 跨 workflow 的任务交织

- workflow **内部**的依赖是确定的，但 **workflow 之间**的关系不确定。
- 例子：workflow 1 先提交、deadline 很远；workflow 2 后提交、deadline 很紧。两者的任务如何交织。
- 交给 LLM 的输入：两组任务、各自的 deadline、各自必须保持的内部顺序。
- LLM 的输出：在保持两边内部顺序的前提下，给出交织方式。



### ④ Utility curve

- task/workflow的完成时间偏好往往难以描述，比如"6 PM 前完成价值最高，过了 8 PM 就没用了"。
- 由 LLM 构造对应的价值曲线：
  - 6 PM 前完成：获得全部价值，更早完成没有额外价值；
  - 6–8 PM 完成：价值递减；
  - 8 PM 后：失败。
- 这条曲线取决于具体任务，operators 很难完整给出，确定性算法也很难得到。可能是经验性的，需要从历史数据中学习；可能还和特定的、即时的规则有关。



### ⑤ 修复决策中的 reschedule

- 网络出问题时，Scheduling Agent 设法 reschedule 受影响的 workflows，与 Network Agent 的交互、配合。



## 四、Network Agent

**不交给 LLM 的部分**：在 network capacity ledger 上按带宽做扣减；不做超额分配时，按可用容量严格分配并生成 offer。

### ⑥ Over-provisioning 与 offer 生成

- 为某条链路安排带宽时，需要做 over-provisioning（超额分配），而**允许超额多少，要从历史中学**。
- 确定性算法、RL、咨询 LLM 三种方式都可以用来学习超额程度（第一阶段暂不考虑 RL）
- **Offer 生成分两步**：
  1. 按可用容量做严格分配（确定性）；
  2. 由 LLM 协助处理 over-provisioning。
- 第 2 步的依据：已有的 ledger，加上"这类实验同时运行时，过去多少超额分配是可行的"这一历史经验。



### ⑦ Explaining and negotiation

- Network Agent 报告状态时，例如变成 `at_risk`，或已在本地恢复，由 LLM 把这些信息翻译给 operators。



### ⑤ 修复决策中的本地修复

- 网络出问题时，Network Agent 要判断如何修复。
- 这一步可以由 AI 决定，例如该测量哪个值、检查哪个信号；考虑紧急程度以及对其他workflow的影响后，决定是否需要立刻测量；
- 本地修复不了的影响，由 Scheduling Agent 通过 reschedule 消化。

## 五、Telemetry agent

### ⑧ Probe planning

- Telemetry agent 要决定各类信息的采集频率，分别多久做一次测量。
  - 太频繁，测量本身会干扰真实流量；
  - 太稀疏，拿到的信息会过时。
- 本质是为 telemetry 参数找更好的设定方式。

# **调研别人的 agent 怎样调用 LLM**

> “agentic customer service 的做法：把传统 SOPs 改写成 AOPs（agentic operating procedures），用自然语言写明规则，并按客户类型（例如 medical）区分；此外还有一些基本的 metrics 类规则，以及何时升级处理的规定。”这个信息是否在网上有公开，我们可以借鉴看别人是在什么情况/决策下让agent和LLM交互的，是否有meeting上没有提到的位置。

公开资料里有，但不是会上那个版本。“Agent Operating Procedures (AOPs)”这个说法由做客服 AI 的公司 Decagon 公开使用，AWS 也发布过类似的格式，叫 Agent SOPs。“按客户类型（例如 medical）区分规则”这个细节我没有在公开资料里找到。它大概来自 KK 同事合作的团队，公开资料看不出是哪家公司。

网络管理领域有更接近的案例。拿它们和会上的清单对照，能找到几处会上没讨论到的 LLM 用法和管控方式。

## 1. 公开的 AOP / Agent SOP 资料怎么说

- **Decagon 的 AOPs**：客服团队用自然语言写流程，再编译成经过验证的 workflow。退款、身份核验这类敏感操作留在确定性逻辑里，并且必须通过校验。每个流程都写明什么时候升级给人工，团队用大规模模拟和回归测试来检验流程。
- **AWS 的 Strands Agent SOPs**：每一步用 MUST / SHOULD / MAY 标明 agent 必须遵守的严格程度，流程可以带参数。缺必需参数时，agent 会向用户追问，这接近我们的 chasing missing information。AWS 把这种介于严格和灵活之间的状态称为 “determin-ish-tic”。
- **Fin 的术语表列出的升级触发条件**：置信度低于阈值、请求超出范围、遇到 policy 例外，或触发安全规则时升级。



## 2. 网络与调度领域的案例

**Meta Confucius（SIGCOMM '25）**最接近我们的场景。它是 Meta 生产环境里的多 agent LLM 网络管理框架，已运行两年，接入了 60 多个应用。

- **分工**：LLM 只负责推理，事实性信息来自 runbooks、工具和数据库。
- **翻译**：把自然语言转成网络工具使用的三种格式：topology graph、time series 和 network data model。
- **把关**：输出先过 validator 和 dry run 才给人看；高度敏感的任务必须经人工批准。一个叫 Collector 的组件通过结构化提问向人收集缺失的输入。
- **解析厂商邮件**：一个解析器把厂商的维护通知邮件转成结构化 ticket，每天调用数百次。这和我们说的“把 email 转成 workflow 输入”是同一件事。
- **教训**：
  - 最难的排障问题写不成固定流程，LLM 在这类问题上力不从心；
  - LLM 查不到数据时倾向于编造答案，而不是尽早报错；
  - 在长会话里，用户一开始给出的约束会被丢掉。

**SADE（arXiv 2026，网络排障）**：由固定的 policy 决定走哪个诊断阶段、调用哪些技能，LLM 只在每个阶段内部收集证据和推理。在 523 个故障案例上，root-cause F1 比 ReAct + GPT-5 高 37 个百分点。

**LLM 做 HPC 作业调度（arXiv 2506.02025）**：让 LLM 直接调度作业，并与 FCFS、SJF 和 OR-Tools 对比。LLM 能较好地兼顾多个目标，但计算很慢。这支持不把 LLM 放进调度内环。

**Nada（HotNets '24）与 PolicySmith**：LLM 事先把算法或启发式规则写成代码，代码在模拟中评估后再部署，运行时 LLM 不做任何决策。

## 3. 会上没有覆盖到的地方

1. **LLM 可以事先写规则，而不是在运行中被询问。** 会上默认 agent 在运行中咨询 LLM。Nada 和 PolicySmith 给出了另一种做法：over-provisioning 比例、telemetry 采集频率、何时停止搜索，都可以由 LLM 写成策略代码，在 digital twin 里测试后再部署。这样运行时开销更低，也更容易检查，还能给 digital twin 一个具体角色。Linxuan 提的“由 LLM 设定停止规则”已经朝这个方向走了，可以推广到清单上的其他职责。
2. **谁来检查 LLM 的输出。** 会上没有人提。参照 Confucius，LLM 给出的任务交织方案或 over-provisioning 方案，都应先通过确定性检查（capacity ledger、依赖、deadline），才能变成 offer。检查不通过就退回给 LLM，或者升级给人。
3. **什么时候从推断切换到追问。** 会上把推断缺失参数和向 operators 追问列成两项，但没有说两者之间怎么选。Confucius 的教训是尽早报错：没有历史可以推断时，LLM 应该说“不知道”并触发向 operator 追问，而不是自己编一个值。这个切换条件，正是 KK 那个“rules → LLM → 用户”分层模式里具体的升级条件。
4. **明确的升级触发条件，以及高影响操作需要人工批准。** KK 给出了分层，但没有给出层与层之间的切换条件。公开资料给出的参考是置信度、范围、policy 例外和安全规则。在 SciNet 里，有些操作应当始终需要 operator 批准，例如占用别人 workflow 的带宽，或者打破已经 commit 的预留。
5. **测试 LLM 环节。** Decagon 和 Confucius 都把 benchmark 或回归测试套件当作生产系统的一部分。我们清单上的每一项 LLM 职责，都需要一组 workflow 场景来衡量。
6. **如何从历史中学习。** 会上多次说“从历史中学”，但没说怎么学。Confucius 把过去的交互存下来，再作为上下文检索出来（RAG）。对我们来说，就是检索过去的传输记录和 instrument 运行记录。
7. **异常响应可以照 SADE 的方式分工。** 由固定规则逐层排查（链路 → 路径 → 站点），LLM 只在每一层内部收集证据和推理。这是对清单里“异常响应”一项更具体的落法。

我认为第 1 点和第 3 点最值得带去和 KK 讨论。
